# Plan review

The readers of this page are the agent of a ticket, and the orchestrator for the design-gap rule.

## The repo-files rule

The agent adds this rule to the feedback text where a step, [the add-work rule](run-one-ticket.md#the-add-work-rule) or [the verify-failure rule](verify-failures.md#the-verify-failure-rule) says so. The rule tells the plan session (the session that tasker starts to make the plan) to read only the files in the worktree of the task. A file is outside the worktree when its path is not under the path on the `worktree:` line of `tasker show <issue>`. The plan session must not read or quote a file outside the worktree. If the plan session needs a detail that the issue, the feedback text and the files in the worktree do not give, it asks a plan question. It does not take the detail from another place. If the plan of step 2 of [Run one ticket](run-one-ticket.md#run-one-ticket) needs no changes, the agent does not run a refine only to send this rule. The quote check covers that plan. The repo-files rule and the quote check cover only the plan session, the plans and the review findings. They do not cover the execute session or the diff.

## The fact test

Before the first refine of step 4 of [Run one ticket](run-one-ticket.md#run-one-ticket), the agent tests on the local machine each fact about an outside tool that the plan depends on. Examples are a behavior of git, Node, zod or the operating system. The agent does not rely on the plan session to test these facts. Before each refine, the agent also tests each fact that a plan question asks about, and it answers the question in the feedback text. The agent puts the commands and their results in the feedback text. A fact test that runs the code of the repo runs in the task worktree, after [the update rule](orchestration.md#the-update-rule).

## The issue check

Before the first refine of step 4 of [Run one ticket](run-one-ticket.md#run-one-ticket), the agent makes sure that each claim of the issue is still true in the task worktree, for example in the code and the docs. In the same worktree, the agent also compares each requirement of the issue with the docs and the code, and looks for each conflict. The check covers the base branch of the task as it was at `tasker start`, for example `main`. Right after `tasker start`, the task branch holds no commit of the ticket yet, so the task worktree holds the files of the base commit. If the task branch already holds commits, for example for a parked task that came back, the agent reads the base files without a worktree. After `git fetch --multiple tasker origin`, it runs `git merge-base tasker/<task branch> origin/<base branch>` with the base of [the base rule](run-one-ticket.md#the-base-rule). The output is `<merge base>`. Then `git show <merge base>:<path>` reads one file, `git ls-tree -r --name-only <merge base>` lists the files, and `git grep <pattern> <merge base>` searches. For these read-only commands, a missing path (`git show` exits with 128) or no match (`git grep` exits with 1) is an answer, not a failure. The agent says which files it read from the base commit and how. It says this in the feedback text of the refine of step 4 and in its final report. If step 4 runs no refine, the agent does the issue check before `tasker approve` in step 5. Someone can write an issue long before an agent runs it, and other tickets can land in that time and change its facts. For this check, the issue is the issue body and each comment that starts with `## Change of scope` whose link the orchestrator sent to the agent (see [the stop rule](#the-stop-rule) and [Land the work](land-the-work.md#land-the-work)). A comment of another account is not part of the issue, because any GitHub user can post a comment. A claim is a statement in the issue about the state before the ticket starts. Examples are a statement about the code, the docs or the behavior of tasker, and a measure of an outside tool that the issue gives. A requirement is a statement in the issue about what the ticket must change, for example an item of its Requirements section. A requirement is not a claim. A conflict is a requirement that does not fit a rule of a doc, or a decision that the code or a landed ticket made after someone wrote the issue. For example, the issue asks for a rule that a doc already gives in other words. Or the issue asks for a file or a section that a later ticket moved or renamed. Or the issue asks for a behavior that a later rule forbids. For a measure of an outside tool, the agent measures again on the local machine, as the fact test does. The agent cannot always measure an output of the installed tasker that the issue records. If the agent cannot measure such an output, the ticket and the date that the issue names are the evidence, as [The body of an issue](planning.md#the-body-of-an-issue) of planning.md says. The agent says so in the feedback text of the refine of step 4 and in the comment of step 11. In both places, the agent names the issue as the source of the output. If the issue names no ticket and no date for the output, the agent has no evidence. The agent then reports the claim as a claim that it cannot test, in the feedback text of the refine of step 4 and in its final report. On #240, the agent had no task in `reviewed`, so the agent was unable to measure the output of `tasker dismiss-review`. The issue check does not cover the hints in the prompt of the agent, the plan or the review findings. The fact test and the quote check cover the plan. The issue check runs one time, with one exception. The one exception is a comment that starts with `## Change of scope`: after a stop of the fifth case, after the security report of ["Review findings"](review-findings.md#review-findings), or after a correction of the bullet of [Land the work](land-the-work.md#land-the-work) that covers a change to an issue in flight. After each such comment, the agent does the issue check again for the claims and the requirements of the changed scope. The agent does it before the refine, or the `tasker review <issue> "<feedback>"`, that sends the answer or the text of the comment. The issue check does not run again when the base branch moves after `tasker start`, for example before a `tasker update-branch`. If a false claim or a conflict does not change what the ticket must do, the agent does not stop. For a false claim, the agent puts the current fact in the feedback text of the refine of step 4. For a conflict, the agent says in that feedback text how it resolves the conflict. For example, the plan links to the existing rule instead of a copy, or it uses the new name of a file. If step 4 runs no refine, the agent does not run a refine only to send the current fact. If the plan does not resolve a conflict yet, the plan needs changes, and step 4 runs a refine. If a false claim or a conflict changes what the ticket must do, the fifth case of the stop rule applies. For a false claim, the agent puts the claim, the current fact and the command that shows it in its report of the stop case. For a conflict, the agent puts the requirement, the conflicting rule or decision, and the command or the doc that shows it in that report. In each case, the agent also lists each false claim and each conflict in its final report.

## The stop rule

Each time before the agent runs `tasker approve` in step 5 of [Run one ticket](run-one-ticket.md#run-one-ticket), the agent stops in each of these cases:

- The plan has an open question that the issue does not answer.
- The plan makes a design choice that the issue does not make.
- The plan has a security gap.
- The plan changes a file that the issue does not name, and another task in progress also changes that file. For example, `tasker refine` prints a warning for such a file (see ["Land the work"](land-the-work.md#land-the-work)). This case does not apply when the orchestrator already set a landing order for that file. If the plan does not need the edit, the agent removes it in a refine of step 4, as "Land the work" says, and does not stop.
- A claim of the issue is no longer true, or a requirement of the issue is a conflict, and this changes what the ticket must do (see [the issue check](#the-issue-check)). This case does not apply when the orchestrator already answered for that claim or that conflict.

In each case, the agent reports the case to the orchestrator. The design-gap rule says who answers the first three cases. For the fourth case (a shared file), "Land the work" gives the steps. For the fifth case (a false claim or a conflict), the orchestrator asks the user, because only the user changes the scope of a ticket. If the user changes the scope, the orchestrator posts the change as a comment on the issue. The comment starts with `## Change of scope`. The comment says which requirements change and how, and which items of the issue body no longer apply. The orchestrator does not edit the issue body for a change of scope. On 2026-10-16, the user asked for a comment for the change of scope of #232. The change of scope of #219 also used a comment. The orchestrator sends the link of the comment to the agent in the answer. The bullet of [Land the work](land-the-work.md#land-the-work) about the state read covers that answer. The orchestrator owns the issue bodies, and the agent does not edit them (see [Limits](orchestration.md#limits)). The agent then waits for the answer, as [the answer-wait rule](orchestration.md#the-answer-wait-rule) says. While the agent waits, the task stays in `awaiting_plan_review`. After the answer, the agent puts the answer in the feedback text of the refine of step 4. If the answer is a change of scope, the agent does [the issue check](#the-issue-check) again, as the issue check says. Then the agent copies the full text of the comment whose link the orchestrator sent. The agent puts that text in the feedback text of the refine, or of the `tasker review <issue> "<feedback>"`, that sends the answer. The reason: the plan session reads only the issue body and the repo. The agent copies no other comment. Then the agent continues with step 4 and runs `tasker approve` in step 5. An answer before `tasker approve` costs no review loop, but a later answer costs one or more review loops. The quote check and the security report of ["Review findings"](review-findings.md#review-findings) give more cases that stop before `tasker approve`.

## The design-gap rule

A design gap is a detail that the plan needs and that the issue does not give, in the first or the second case of the stop rule. If the gap has exactly one workable answer inside the intent of the issue, the orchestrator gives that answer to the agent. The orchestrator also tells the user the answer. The user can change the answer before `tasker approve`. In that case, the orchestrator sends the new answer to the agent. If the gap has more than one workable answer, the orchestrator asks the user. A security gap (the third case) always goes to the user.

## The quote check

A plan or a finding quotes a file outside the worktree when it gives text from that file, or when it says that it read that file. "Outside the worktree" has the meaning of the repo-files rule. If a plan or a finding quotes a file outside the worktree, the agent tells the orchestrator. Then the orchestrator tells the user. After this report, the agent can still do the steps that come before `tasker approve` or `tasker accept`. For example, it can run a refine of step 4 or step 8 of [Run one ticket](run-one-ticket.md#run-one-ticket), or dismiss a finding in step 7. If the next command of the agent is `tasker approve` or `tasker accept`, the agent stops and waits for the answer of the orchestrator, as [the answer-wait rule](orchestration.md#the-answer-wait-rule) says. While the agent waits, the task stays in its state, for example `awaiting_plan_review` before `tasker approve`, or `awaiting_work_review` before `tasker accept`. After the orchestrator answers, the agent does the step that the answer gives. If the answer gives no step, the agent continues "Run one ticket" from the step where it stopped.
