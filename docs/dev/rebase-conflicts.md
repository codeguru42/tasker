# Rebase conflicts

This page gives the procedure for a rebase conflict that `tasker update-branch` reports.

The page is for the installed `tasker` that drives the work on this repo. Its commands (`update-branch --take-remote`, `show`, `verify`, `review`, `finish`) are not the commands that this repo builds. For this reason, `skills/tasker/SKILL.md` does not list them. To see the flags of a command, run `tasker <command> --help`.

## Who runs the procedure

The operator does these steps. The operator is the person or the assistant session that drives tasker from a local clone of this repo.

tasker keeps its own clone of this repo under its data root (`dataRoot`). This page calls it the tasker clone. tasker starts some assistant sessions in a worktree of the tasker clone. Such a session must not do these steps. It must stop and report the conflict to the operator.

The operator must not run git commands in the tasker clone. The operator must not change the tasker clone. Only tasker commands change it. The operator reads the tasker clone only with a fetch through a read-only remote. A fetch only reads the tasker clone.

## Procedure

Run each git command in the clone of the operator or in its worktree.

1. Once for each clone of the operator, add a remote named `tasker`: `git remote add tasker <path of the tasker clone>`. The installed tasker keeps the tasker clone at `<dataRoot>/repos/<owner>-<repo>/repo.git`, for example `$HOME/.local/share/tasker/repos/codeguru42-tasker/repo.git`. `tasker show <issue>` prints the worktree of the task, under `<dataRoot>/repos/<owner>-<repo>/worktrees/`. The tasker clone is `repo.git` in the same folder. `docs/dev/data-root.md` describes the tasker that this repo builds, not the installed tasker, so its folders do not apply to this procedure.
2. In the same clone, block each push to this remote: `git remote set-url --push tasker DISABLED-read-only`. As a result, no push can reach the tasker clone.
3. Run `tasker show <issue>`. It prints the base branch of the task as `base branch:`. For most tasks, the base branch is `main`.
4. If the base branch is the branch of another task (a stacked task), stop. A person decides the next step, as step 10 describes.
5. Run `git fetch --multiple tasker origin`. The fetch reads the task branch from the tasker clone. The fetch of `origin` also gets the base branch.
6. Run `git worktree add -b <task branch> <path> tasker/<task branch>`. This makes a worktree with a local task branch.
7. In the worktree, rebase the task branch onto `origin/<base branch>`. Fix the conflicts.
8. In the worktree, run `npm run check`. The command must pass.
9. Push the task branch to `origin` with a normal push: `git push -u origin <task branch>`. Do not force-push. Step 6 makes `tasker/<task branch>` the upstream of the task branch. As a result, a plain `git push` goes to the `tasker` remote and fails, so the operator must name `origin`.
10. If `origin` already has the task branch, the normal push fails. In this case, stop and do not force-push. A person decides the next step. If the operator is a person, that person decides. If the operator is an assistant session, it reports the failed push to the person who runs it.
11. Run `tasker update-branch <issue> --take-remote`. tasker resets its task branch to the task branch on `origin`. Then, before step 12, the operator records `<taken>` in the clone of the operator, not in the worktree. Run `git fetch tasker`. Then run `git rev-parse --verify tasker/<task branch>`. Keep the printed hash as `<taken>` until step 21 ends. The take check of step 17 and step 10 of "Run one ticket", which step 21 runs, use it. If one of the two commands fails, step 11 records no `<taken>`. Continue with step 12. The take check of step 17 then fails. As a result, the worktree, the local task branch and the task branch on `origin` stay.
12. Run `tasker show <issue>`. It prints the state of the task and the next valid commands.
13. If the task is in `executed`, run `tasker verify` and `tasker review` again. Then land the work as usual.
14. If the task is in another state, follow the commands that `tasker show` prints.
15. Keep the worktree and the local task branch until the work lands. After `tasker finish`, run `tasker show <issue>` in the clone of the operator. If `tasker show` prints the line `state: finished`, do steps 16 to 21 in this order. Run them in the clone of the operator, not in the worktree. As a result, the operator deletes nothing before the check of step 17 passes. If the task is in `cleanup_failed`, `tasker finish` stopped before its cleanup ended. In that case, do not do steps 16 to 21. If `tasker show` fails or prints another state, do not do steps 16 to 21. In both cases, the worktree and the local task branch stay. The task branch on `origin` can still exist. A person decides the next step, as step 10 describes.
16. Run `git fetch origin`. The fetch gets the base branch with the landed work. If the fetch fails, stop. The worktree and the local task branch stay. The task branch on `origin` stays. A person decides the next step, as step 10 describes.
17. Make sure that the base branch contains the work of the task branch. First, read two hashes in your clone: `git rev-parse --verify <task branch>` gives `<tip>`, and `git rev-parse --verify origin/<base branch>` gives `<base>`. The step uses `origin/<base branch>` in more than one command, so the shared-clone rule in "Limits" of [docs/dev/orchestration.md](orchestration.md#limits) applies. If a read fails, stop and delete nothing. The worktree and the local task branch stay. The task branch on `origin` stays. A person decides the next step, as step 10 describes. Then run the ancestor check: `git merge-base --is-ancestor <tip> <base>`. The command exits with 0 when the base branch contains the tip. It exits with 1 when the base branch does not contain the tip. It exits with 128 when git does not know one of the two names. If the exit code is 0, the check passes. Continue with step 18. The ancestor check exits with 1 when the work landed as new commits. For example, `tasker update-branch --take-remote` rebased the work again onto a newer base branch, or the work landed as a rebase merge or as a squash. In issue #99, on 2026-10-14, another ticket landed between the push and `--take-remote`, and each of the 8 commits of the pushed branch had the same patch as a landed commit. If the exit code is 1, run the patch check: `git cherry <base> <tip>`. The command lists each commit of the task branch that `<base>` does not contain, one line for each commit, with a sign and the full hash. The sign `-` means that the base branch already has a commit with the same patch. The sign `+` means that it has none. The exit code is 0 in both cases. For example, the same patches print `- <hash>` and `- <hash>`. One changed patch prints `- <hash>` and `+ <hash>`. The patch check passes when the output has at least one line and each line starts with `-`. Then the work landed with the same patches. Continue with step 18. The patch check fails in each of these cases: a line starts with `+`, the output is empty, or `git cherry` exits with a code that is not 0. If the ancestor check exits with a code that is not 0 and not 1, stop at once and do not run `git cherry`. If `git cherry` exits with 0 and a line starts with `+`, the operator runs the take check in the clone of the operator. In the other failure cases of the patch check, the operator does not run the take check. The take check is for a task where a later round of tasker rewrote the commits after the push of step 9. For example, a refine of a review loop folds a fix into an earlier commit with a fixup commit and an autosquash rebase. The local task branch and the task branch on `origin` keep the old commits. As a result, `git cherry` prints `+` for each rewritten commit. In issue #96, on 2026-10-15, the pushed tip was 198ba3a, and the work landed as 574877a. In this step, the pushed tip is `<tip>`. First, read the tip of the task branch on `origin` one time: `git rev-parse --verify origin/<task branch>`. If this hash differs from `<tip>`, `origin` has a commit that tasker did not take. The first fact: `<taken>` from step 11 is the same hash as the pushed tip. Then tasker took the pushed tip. If `<taken>` differs from the pushed tip, the local task branch has a commit that tasker did not take. After `tasker finish`, the tasker clone has no task branch. A plain `git fetch tasker` does not prune `tasker/<task branch>`. For this reason, step 11 reads `<taken>`, and this step does not read it. The second fact: `git merge-base --is-ancestor <landed commit> <base>` exits with 0. Then the landed commit is on the base branch. The landed commit is the full hash that `tasker merge` prints. `tasker show <issue>` of a finished task does not print it. The take check passes when the tip on `origin` is the same hash as `<tip>` and both facts hold. If the take check passes, continue with step 18. Each commit of the pushed tip went into the task branch of tasker at step 11. Each later change is a round of tasker, and tasker landed the result. The take check fails in each of these cases: a hash differs, step 11 recorded no `<taken>`, the operator does not have the landed commit, `git merge-base` exits with 1, or a command of the take check exits with 128. In each failure case of the three checks, stop and delete nothing. The worktree and the local task branch stay. The task branch on `origin` stays. A person decides the next step, as step 10 describes. The patch check compares only the code change (the patch id). It does not compare the commit message or whitespace. A `-` can match any commit of the base branch after the merge base that has the same patch. The check prevents the delete of work that did not land. A difference only in the message or in whitespace loses no work. A rebase with the same patches passes the patch check. A squash of more than one commit makes one new patch, so `git cherry` prints `+` lines, and the patch check fails.
18. Remove the worktree: `git worktree remove <path>`. Do not use `--force`, because `--force` deletes the changes that are not committed. Files that `.gitignore` lists do not stop `git worktree remove`, for example `node_modules/` from `npm ci`.
19. If `git worktree remove` fails, stop. The worktree and the local task branch stay. The task branch on `origin` stays. Report the exact error of git and the output of `git -C <path> status --porcelain --ignored`. For example, git prints `fatal: '<path>' contains modified or untracked files, use --force to delete it` when the worktree holds changed files or files that git does not track. The report helps to find the cause of such a failure. In one case, an agent used `--force` and blamed `node_modules/`. But git removes a worktree that holds only ignored files without `--force`, so the cause is unknown. A person decides the next step, as step 10 describes.
20. Delete the local task branch: `git branch -D <task branch>`. The check of step 17 already makes sure that the base branch contains the work, a commit with the same patch for each commit, or the landed result of tasker after it took the pushed tip. If the command fails, stop. The worktree is gone. The local task branch stays. The task branch on `origin` stays. A person decides the next step, as step 10 describes.
21. Make sure that `origin` has no task branch: do step 10 of "Run one ticket" in [docs/dev/orchestration.md](orchestration.md#run-one-ticket). If the operator is not the agent of a ticket, it runs those commands in the clone of the operator. Where that step says to report to the orchestrator, a person decides the next step instead. Step 10 of this page describes this rule. The operator does not do step 11 of "Run one ticket".
