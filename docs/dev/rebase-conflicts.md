# Rebase conflicts

This page gives the procedure for a rebase conflict that `tasker update-branch` reports.

The page is for the installed `tasker` that drives the work on this repo. Its commands (`update-branch --take-remote`, `show`, `verify`, `review`, `finish`) are not the commands that this repo builds. For this reason, `skills/tasker/SKILL.md` does not list them. To see the flags of a command, run `tasker <command> --help`.

## Who runs the procedure

The operator does these steps. The operator is the person or the assistant session that drives tasker from its own local clone of this repo.

tasker keeps its own clone of this repo under its data root (`dataRoot`). This page calls it the tasker clone. tasker starts some assistant sessions in a worktree of the tasker clone. Such a session must not do these steps. It must stop and report the conflict to the operator.

The operator must not run git commands in the tasker clone. The operator must not change the tasker clone. Only tasker commands change it. The operator reads the tasker clone only with a fetch through a read-only remote. A fetch only reads the tasker clone.

## Procedure

Run each git command in the clone of the operator or in its worktree.

1. Once for each clone of the operator, add a remote named `tasker`: `git remote add tasker <path of the tasker clone>`. The installed tasker keeps the tasker clone at `<dataRoot>/repos/<owner>-<repo>/repo.git`, for example `$HOME/.local/share/tasker/repos/codeguru42-tasker/repo.git`. `tasker show <issue>` prints the worktree of the task, under `<dataRoot>/repos/<owner>-<repo>/worktrees/`. The tasker clone is `repo.git` in the same folder. `docs/dev/data-root.md` describes the tasker that this repo builds, not the installed tasker, so its folders do not apply to this procedure.
2. In the same clone, block each push to this remote: `git remote set-url --push tasker DISABLED-read-only`. As a result, no push can reach the tasker clone.
3. Run `tasker show <issue>`. It prints the base branch of the task as `base branch:`. For most tasks, the base branch is `main`.
4. If the base branch is the branch of another task (a stacked task), stop. A person decides the next step, as step 10 describes.
5. Run `git fetch --multiple tasker origin`. The fetch reads the task branch from the tasker clone. The fetch of `origin` also gets the base branch.
6. Run `git worktree add -b <task branch> <path> tasker/<task branch>`. This makes a worktree with a local task branch.
7. In the worktree, rebase the task branch onto `origin/<base branch>`. Fix the conflicts.
8. In the worktree, run `npm run check`. The command must pass.
9. Push the task branch to `origin` with a normal push: `git push -u origin <task branch>`. Do not force-push. Step 6 makes `tasker/<task branch>` the upstream of the task branch. As a result, a plain `git push` goes to the `tasker` remote and fails, so the operator must name `origin`.
10. If `origin` already has the task branch, the normal push fails. In this case, stop and do not force-push. A person decides the next step. If the operator is a person, that person decides. If the operator is an assistant session, it reports the failed push to the person who runs it.
11. Run `tasker update-branch <issue> --take-remote`. tasker resets its task branch to the task branch on `origin`.
12. Run `tasker show <issue>`. It prints the state of the task and the next valid commands.
13. If the task is in `executed`, run `tasker verify` and `tasker review` again. Then land the work as usual.
14. If the task is in another state, follow the commands that `tasker show` prints.
15. Keep the worktree and the local task branch until the work lands. After `tasker finish`, run `tasker show <issue>` in the clone of the operator. If `tasker show` prints the line `state: finished`, do steps 16 to 21 in this order. Run them in the clone of the operator, not in the worktree. As a result, the operator deletes nothing before the check of step 17 passes. If the task is in `cleanup_failed`, `tasker finish` stopped before its cleanup ended. In that case, do not do steps 16 to 21. If `tasker show` fails or prints another state, do not do steps 16 to 21. In both cases, the worktree and the local task branch stay. The task branch on `origin` can still exist. A person decides the next step, as step 10 describes.
16. Run `git fetch origin`. The fetch gets the base branch with the landed work. If the fetch fails, stop. The worktree and the local task branch stay. The task branch on `origin` stays only if `tasker finish` did not delete it. Step 21 finds out. A person decides the next step, as step 10 describes.
17. Make sure that the base branch contains the tip of the task branch: `git merge-base --is-ancestor <task branch> origin/<base branch>`. The command exits with 0 when the base branch contains the tip. It exits with 1 when the base branch does not contain the tip. It exits with 128 when git does not know one of the two names. The check passes when the work lands with its own commits, for example by a fast-forward. The check fails when the work lands as a squash or as a rebase merge, because these make new commits. If the exit code is not 0, stop and delete nothing. The worktree and the local task branch stay. The task branch on `origin` stays only if `tasker finish` did not delete it. Step 21 finds out. A person decides the next step, as step 10 describes.
18. Remove the worktree: `git worktree remove <path>`. Do not use `--force`, because `--force` deletes the changes that are not committed. Files that `.gitignore` lists do not stop `git worktree remove`, for example `node_modules/` from `npm ci`.
19. If `git worktree remove` fails, stop. The worktree and the local task branch stay. The task branch on `origin` stays only if `tasker finish` did not delete it. Step 21 finds out. If git prints `fatal: '<path>' contains modified or untracked files, use --force to delete it`, run `git -C <path> status`. The worktree holds changed files or files that git does not track. For any failure, a person decides the next step, as step 10 describes.
20. Delete the local task branch: `git branch -D <task branch>`. The check of step 17 already makes sure that the base branch contains the work. If the command fails, stop. The worktree is gone. The local task branch stays. The task branch on `origin` stays only if `tasker finish` did not delete it. Step 21 finds out. A person decides the next step, as step 10 describes.
21. `tasker finish` deletes the task branch on `origin`. `tasker finish --help` says: "close out a task whose work has landed on the base branch: remove its worktree and local branch, delete its branch on origin, and mark the issue done when configured". As a result, `origin` usually no longer has the task branch at this step. Find out if `origin` still has the task branch, with a read-only command: `git ls-remote --exit-code --heads origin refs/heads/<task branch>`. Give the full ref, because a short name also matches a longer branch name that ends with it, for example `x` matches `feature/x`. The command exits with 0 when `origin` has the task branch. It exits with 2 when `origin` does not have the task branch. It exits with 128 when git cannot reach `origin`, for example when the path of `origin` does not exist. If the exit code is 2, the cleanup is complete. If the exit code is 0, delete the task branch on `origin`: `git push origin --delete <task branch>`. If the push succeeds, the cleanup is complete. If the push fails, stop. The worktree and the local task branch are gone. The task branch on `origin` stays. A person decides the next step, as step 10 describes. If the exit code of `git ls-remote` is another value, stop. The worktree and the local task branch are gone. The task branch on `origin` can still exist. A person decides the next step, as step 10 describes.
