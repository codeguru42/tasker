# Orchestration

This page gives the rules for an orchestrator. The orchestrator is the assistant session that picks tickets, starts one agent for each ticket, moves the cards, sets the landing order and writes memory.

A ticket is an issue on the project board. An agent is an assistant session that the orchestrator starts for one ticket. The agent runs the steps of "Run one ticket" for that ticket. The user is the person who runs the orchestrator. A task is the record that tasker keeps for one ticket. tasker moves the task from state to state, for example from `awaiting_plan_review` to `approved`.

Memory is the files where an assistant keeps notes between sessions. Memory is not in the repo.

tasker also starts its own sessions for plan, execute and review. They run in a worktree of the tasker clone. They are not agents and they do not run the steps on this page.

The orchestrator and its agents run tasker from the local clone of the orchestrator. For one ticket, the agent of that ticket is the operator that [docs/dev/rebase-conflicts.md](rebase-conflicts.md) names.

Every `tasker` command on this page is the installed `tasker`: the `tasker` command on the PATH from a global install. It is not the tasker that this repo builds. For this reason, `skills/tasker/SKILL.md` does not list its commands. See the `npm link` bullet under Limits.

## Pick the tickets

The orchestrator does all the steps of this section.

- Take tickets only from the Todo column of the project board, and only from the current milestone. Do not start a ticket from a later milestone.
- Start a ticket only as [the stacking rule](#the-stacking-rule) says. No orchestrator that knows of an open broken-test issue starts a ticket, except that issue itself (see the broken-test rule in [A failed CI run](#a-failed-ci-run)).
- The priority rule: among the tickets that can start, the orchestrator starts a ticket with `priority: high` first. Then it starts a ticket with `priority: medium`, then a ticket with no priority label, then a ticket with `priority: low`. Two tickets of the same priority have no order. To read the labels, run `gh issue list --milestone "<milestone>" --state open --label "priority: high" --limit 1000 --json number`. Run the same command for the other labels. If a command fails, the orchestrator tells the user the command and the error, and it starts no ticket until the read works. A ticket that is on none of the three lists has no priority label. The rule covers the tickets of the milestone of the orchestrator. It changes no other rule of this section: a ticket with a label still waits as [the stacking rule](#the-stacking-rule) says, and it still waits for the shared-file rule and the move rule. A rule that stops a start still wins, for example the ban of [A failed CI run](#a-failed-ci-run), step 1 of [The handoff](#the-handoff) or a hold of the user. The ticket of a parked task that comes back to Todo of the current milestone takes its place by its label (see [the defer rule](#the-defer-rule)). When the orchestrator reads the board again after a landing, it applies the rule again. Then a ticket with `priority: high` or `priority: medium` that joined the milestone and can start takes the next free agent before the tickets with no label.
- Each time a ticket lands, read the board again: the open issues of the milestone and the issues that block them. A new issue can join a milestone while a run is in progress. In one milestone, a new issue stayed in Todo for hours, because the orchestrator read the board only at the start. Then do [the re-read rule](#the-re-read-rule).
- Run at most 3 agents at the same time, one ticket for each agent.
- Do not run two tickets at the same time when both edit the same shared file, for example a file under `test/helpers/` or `docs/dev/code-conventions.md`. Start the second ticket after the first one lands. If a ticket can start except for this bullet, because it shares a file with a task in flight of the same milestone, [the link offer](#the-link-offer) applies. This bullet covers two tickets of the milestone of the orchestrator. For a task in flight of another milestone, [the overlap rule](#the-overlap-rule) applies instead. For a stacked ticket and its parent, [the stacking rule](#the-stacking-rule) wins.
- The move rule: a moving ticket is a ticket that moves or splits a whole shared file, for example the split of `test/helpers.ts` into the folder `test/helpers/` on #140. The orchestrator starts a moving ticket only after each task in flight that changes that file has landed. This rule covers the tasks of every milestone, except a parked task (see [the defer rule](#the-defer-rule)). For the start of a moving ticket, this rule wins over the last sentence of the bullet before it. [The overlap rule](#the-overlap-rule) gives the steps that list the tasks in flight and their files. The reason: a moving ticket changes each line of the file. As a result, a ticket that lands later in that file causes a rebase conflict in each commit, or one more refine before `tasker approve`. [The stacking rule](#the-stacking-rule) gives one exception for a parent.
- If a task in flight that changes the file of a moving ticket is far from landing, for example in `awaiting_plan_review`, the orchestrator asks the user. The user decides whether the orchestrator waits or starts the moving ticket now. The orchestrator follows [A decision of the user](working-with-the-user.md#a-decision-of-the-user). If the user answers "start now", the orchestrator sets a landing order between the moving ticket and that task in flight, as [Land the work](#land-the-work) says. For that moving ticket and that task in flight, the answer of the user wins over the sentence "Start the second ticket after the first one lands." of the shared-file bullet above. For a task in flight of another milestone, [the overlap rule](#the-overlap-rule) applies.
- When a ticket starts, the orchestrator moves its card to In progress. `tasker start` does not move the card. The board moves the card to Done when `tasker finish` closes the issue.
- When the Todo column of the milestone is empty, stop and tell the user. Do not write the issues of the next milestone. This bullet does not cover a long-running orchestrator (see [The handoff](#the-handoff)).

### The stacking rule

A blocker is an issue that blocks the ticket. The orchestrator can start a ticket when each blocker is closed or is ready to stack. A blocker of another milestone counts the same way.

A blocker is ready to stack when its issue is open, its task is in the same repo, and `tasker show <blocker issue>` prints one of these states: `awaiting_work_review`, `reviewing`, `reviewed` or `accepted`. `tasker start` then bases the new task on the branch of the blocker.

The orchestrator waits in these cases:

- The blocker is in `executed`, `verifying`, `merging`, `landed`, `finishing` or `cleanup_failed`. Such a blocker is minutes from a ready state or from its close. A start now makes a task without the work of the blocker.
- The blocker is in any other state.
- Two or more blockers of the ticket are open. The ticket waits until at most one is open, because `tasker start` refuses two ready blockers.

If the orchestrator plans to start a ticket on a blocker that is not ready to stack yet, [the parent-hold rule](#the-parent-hold-rule) applies.

The orchestrator reads the states at four moments:

- Each time it reads the board
- Before each start
- After a report of a ready state
- After a new link of [the link offer](#the-link-offer)

A report of a ready state says that a task is in `awaiting_work_review`, `reviewing`, `reviewed` or `accepted`. The report can come from an agent or from another orchestrator. A report from another orchestrator comes through the messages of [the hold rule](#the-hold-rule) or of [the stacked-ticket rule](#the-stacked-ticket-rule). The sender sends only the reports that those rules already give, and a refused message or a missing answer is out of scope (#164).

After a report of a ready state, the orchestrator lists the open issues that the task blocks: `gh issue view <issue> --json blocking -q '.blocking.nodes[] | select(.state == "OPEN") | .number'`. If the output is empty, no ticket waits on the task, and the step is complete. For each issue of the list, the orchestrator reads the milestone: `gh issue view <blocked issue> --json milestone -q '.milestone.title'`. The orchestrator keeps the tickets of its own milestone. If such a ticket can start by this rule and by the other rules of [Pick the tickets](#pick-the-tickets), the orchestrator starts it. If a command fails, the orchestrator tells the user the command and the error. Then no ticket starts at that moment, and no task changes. The tickets wait until the next read of the board or the next start.

The broken-test ban of the second bullet of [Pick the tickets](#pick-the-tickets) still wins. See [A failed CI run](#a-failed-ci-run).

Two exceptions apply to a stacked ticket and its parent:

- The shared-file bullet does not stop the start, because the stacked task builds on the change of the parent. For each other task in flight, the bullet stays.
- The move rule still wins. A moving ticket does not start while another task in flight changes its file. The parent alone does not block a stacked moving ticket, because the stacked task holds the change of the parent.

### The stacked-ticket rule

A stacked ticket is a ticket that `tasker start` based on the branch of a blocker. Its parent is the ticket of that blocker. The stacked orchestrator is the orchestrator of the stacked ticket. The parent orchestrator is the orchestrator of the parent.

Before a stacked ticket starts, [the parent-hold rule](#the-parent-hold-rule) can hold the parent. For the output of `tasker start` when the parent is not ready to stack, see [the facts of the installed tasker](#the-facts-of-the-installed-tasker).

When a stacked ticket starts, the stacked orchestrator does these steps:

1. Set a landing order with the parent as the earlier ticket, as [Land the work](#land-the-work) says. Do this also when the parent belongs to another orchestrator.
2. Tell the stacked agent that the ticket is stacked, and name the parent.
3. For a file that the parent changes, tell the stacked agent that the fourth case of [the stop rule](#the-stop-rule) does not apply, because the stacked task builds on that change.

These rules apply to a stacked ticket and its parent. The user decided them on 2026-10-16.

- This rule wins over [the Docs rule](#the-docs-rule) and over the sentence "A ticket of an earlier milestone lands first" of [the overlap rule](#the-overlap-rule). The stacked orchestrator sets the landing order with the parent first, and the wait rules apply. The Docs rule still covers each other shared file.
- The pair has no swap, because `tasker merge` refuses a stacked task. The bullet "If the orchestrator changes the landing order" and the bullet "Only the user changes a landing order of the overlap rule" do not apply to the pair.
- If the user postpones the parent (see [the defer rule](#the-defer-rule)), the stacked task cannot land. The stacked orchestrator then asks the user to choose: wait, or run `tasker abort` on the stacked task.
- At the start of a stacked ticket, the parent is in `awaiting_work_review` or a later state, so [the hold rule](#the-hold-rule) does not apply at once. If a refine of step 8 moves the parent back to `awaiting_plan_review`, the hold rule applies as written.
- If the parent belongs to another orchestrator, the stacked orchestrator uses the messages of the hold rule. When the stacked ticket starts, the stacked orchestrator sends one message with `SendMessage` to the parent orchestrator, as the hold rule does when the hold starts. Then the parent orchestrator sends two reports to the stacked orchestrator with `SendMessage`. The first report comes when the parent task is in `awaiting_work_review` or a later state. The second report comes when the issue of the parent closes. A refused request or a missing answer is out of scope (#164).

### The parent-hold rule

This rule covers the parent of a stacked ticket before the stacked ticket starts. A ready state is a state of the list in [the stacking rule](#the-stacking-rule). The agent of the parent moves its task out of a ready state with the refine of step 8, `tasker review <issue> "<feedback>"` of [the add-work rule](#the-add-work-rule), `tasker update-branch` or `tasker merge`. `tasker merge` moves the task from `accepted` to `merging` and `landed`. On #215, a refine of step 8 moved the parent out of a ready state before the agents of two stacked tickets ran `tasker start`. `tasker start` refused both of them (see [the facts of the installed tasker](#the-facts-of-the-installed-tasker)).

When the orchestrator plans to start a stacked ticket on a parent that is not ready yet, the orchestrator tells the agent of the parent to hold. The hold of a parent that belongs to another orchestrator is out of scope. The hold lasts until the orchestrator tells the agent of the parent that the hold ended. A message to an agent that has ended starts the agent again (see "Terms" in "Quota"). If the agent of the parent gets the message while a command runs, the agent lets the command end and keeps the hold. If the agent of the parent gets the message while it waits for an answer or a next step, it keeps the hold and ends its turn again.

While the hold runs, the agent of the parent continues "Run one ticket". After `tasker verify` passes, the agent of the parent continues with `tasker review`, because `reviewing` and `reviewed` are ready states. The agent of the parent also runs `tasker dismiss-review` and `tasker accept`, because the task stays in a ready state.

Before a command that moves the task out of a ready state, the agent of the parent sends a report with `SendMessage`, as [the address rule](#the-address-rule) says. The report gives the state of the task and says that the agent holds. Then the agent of the parent gives its final answer, as [the answer-wait rule](#the-answer-wait-rule) says. If `SendMessage` fails, the agent of the parent puts the report in its final answer. The task keeps its state, for example `reviewed`, `awaiting_work_review` or `accepted`.

This report is a report of a ready state of the stacking rule. The orchestrator then does the steps of the paragraph of [the stacking rule](#the-stacking-rule) that starts "After a report of a ready state".

While the hold runs, the agent of the parent waits in place of the command at each of these places:

- The refine of step 8 of [Run one ticket](#run-one-ticket)
- `tasker review <issue> "<feedback>"` of the add-work rule, also when [the diff read](#the-diff-read) finds work
- `tasker update-branch` of step 9 and of the diff read
- The early update of [Review findings](#review-findings)
- `tasker update-branch` of the bullet of [Land the work](#land-the-work) that starts "If a refine, or the `tasker review <issue> "<feedback>"` of the add-work rule, must change a file"
- `tasker update-branch` of the bullet "When the issue of the earlier ticket is closed" of Land the work
- `tasker update-branch` of [the comeback rule](#the-comeback-rule)
- `tasker merge` of step 9

The orchestrator reads `tasker show <stacked issue>` of each stacked ticket after each report of the agent of that stacked ticket, for example the run-end report of `tasker plan` (see "When there is no reset time yet" in "Quota"). Before `tasker start`, the stacked ticket has no task, so the orchestrator waits for such a report before the read. The read does not follow a stop report of step 2 of "Run one ticket", because such a report ends the hold at once. If `tasker show <stacked issue>` fails, the orchestrator tells the user the command and the error. The hold stays, and no task changes.

The orchestrator ends the hold in these cases:

- `tasker show <stacked issue>` of each stacked ticket prints the branch of the parent on its `base branch:` line, in the form `refs/heads/<parent branch>` of [the base rule](#the-base-rule).
- The start of a stacked ticket fails. A stop report of step 2 from the agent of a stacked ticket counts as a failed start. The orchestrator then ends the hold at once, with no read of `tasker show <stacked issue>`. Examples are the refusal `blocking issue is still open`, after which no task exists, and a missing `based on <key>'s branch` note, after which the stacked task stays in `workspace_ready`.
- The issue of the parent closes.

The orchestrator reads the state of the issue of the parent with `gh issue view <parent issue> --json state -q .state`. It does this read after each report of the agent of the parent or of the agent of a stacked ticket. It also does this read each time it reads the board after a landing ([Pick the tickets](#pick-the-tickets)). The command prints `CLOSED` for a closed issue. If the command fails, the orchestrator tells the user the command and the error. The hold stays, and no task changes.

When the hold ends, the orchestrator reads the state of the parent task with `tasker show <parent issue>`, as the bullet of Land the work that starts "Before the orchestrator sends added work or an answer" says. If `tasker show <parent issue>` fails, the orchestrator tells the user the command and the error. The hold stays, and no task changes. Otherwise, the orchestrator tells the agent of the parent that the hold ended. If the hold ended because the start of a stacked ticket failed, the orchestrator also reports the failure to the user. After the message that the hold ended, the agent of the parent continues "Run one ticket" from the command where it stopped.

### The link offer

This rule covers a ticket of the milestone of the orchestrator. The ticket can start, except for the shared-file bullet of [Pick the tickets](#pick-the-tickets). The ticket shares a file with a task in flight of the same milestone, and it has no blocked-by link to the issue of that task. A ticket that waits for another reason gets no offer until it can start except for the shared file. Examples are a blocker that is not ready to stack, and two or more open blockers. A link to a task of another milestone is out of scope. [The overlap rule](#the-overlap-rule) covers that case.

The orchestrator offers the user a link: the ticket is blocked by the issue of that task. The orchestrator follows [A decision of the user](working-with-the-user.md#a-decision-of-the-user).

- If the user approves, the orchestrator runs `gh issue edit <ticket> --add-blocked-by <issue of the task>`. If `gh issue edit` succeeds, the orchestrator reads the states of the blockers of the ticket at once. If the ticket can start by [the stacking rule](#the-stacking-rule) and by the other rules of [Pick the tickets](#pick-the-tickets), the orchestrator starts it. Otherwise, the ticket waits. For example, [the stacking rule](#the-stacking-rule) makes the ticket wait while the task is not ready to stack. When the task is ready to stack, the ticket can start as a stacked ticket on the task. For that pair, [the stacking rule](#the-stacking-rule) wins over the sentence "Start the second ticket after the first one lands." of the shared-file bullet. [The stacked-ticket rule](#the-stacked-ticket-rule) then sets the landing order, with the task first.
- If `gh issue edit` fails, the orchestrator tells the user the command and the error. The ticket has no new link.
- If the user declines, or if `gh issue edit` fails, the shared-file bullet applies, and the ticket starts after the task lands. The stacking rule still applies to the other blockers of the ticket. After that answer or that failure, the orchestrator makes no new offer for that ticket and that task. The user can still ask for the link at any time.
- In each case, the move rule of [Pick the tickets](#pick-the-tickets) still wins. For a stacked ticket, the second exception of [the stacking rule](#the-stacking-rule) says this.

The offer comes only when the ticket can start except for the shared file. As a result, the ticket has no other open blocker, or one other open blocker that is ready to stack. If the ticket has no other open blocker, the steps of the approve case apply. If the ticket has one, and the user approves, the ticket has two open blockers. It waits until at most one is open, as [the stacking rule](#the-stacking-rule) says. Then the stacking rule applies to the blocker that stays open.

### The re-read rule

The orchestrator works from the current docs. The docs are `AGENTS.md` and the docs that `AGENTS.md` names. The last read is the commit of `main` from which the orchestrator last read the docs.

At the start of its session, the orchestrator does the fetch and the fast-forward of [the doc-read rule](#the-doc-read-rule). Then it runs `git rev-parse --verify HEAD` in its local clone. The hash that this command prints is the first last read. Then the orchestrator reads the docs.

Each time the orchestrator reads the board after a landing, it does these steps in its local clone. The steps change no task.

1. Run `git fetch origin`, as [the doc-read rule](#the-doc-read-rule) says.
2. Read the tip of `main` one time: `git rev-parse --verify origin/main`. This rule calls the hash `<tip>`. Use `<tip>`, not `origin/main`, in the next steps, as [the shared-clone rule](#the-shared-clone-rule) says.
3. Run `git diff --name-only <last read>..<tip> -- AGENTS.md docs/ skills/`. The output lists each file that changed since the last read. If the output is empty, no doc changed, and the steps are complete. The last read stays.
4. If the output lists a file, do the branch check and the merge of [the doc-read rule](#the-doc-read-rule). Use `<tip>` in place of `origin/main` in the merge.
5. Before the next step of your work, read again each file of the list that is `AGENTS.md` or a doc that `AGENTS.md` names. If `AGENTS.md` is on the list, also read each doc that `AGENTS.md` names for the first time. Then `<tip>` is the new last read.

If a command of [the doc-read rule](#the-doc-read-rule) fails before a doc read of the orchestrator, the orchestrator tells the user the command and the error. This applies to the first read at the start of the session and to each later doc read. If a command of the steps above fails, the orchestrator also tells the user the command and the error. A branch name other than `main` in the branch check also counts as a failure. If the orchestrator must read a doc, it then reads the doc as its local clone holds it, and it continues its work. The last read stays. At the start of the session, the orchestrator then runs `git rev-parse --verify HEAD` before it reads the docs, and that hash is the first last read. The orchestrator does the steps above again at the next landing.

### The notice rule

This rule covers a ticket of the milestone "Docs" (see [docs/dev/planning.md](planning.md)). It applies when the landing of the ticket changes one of the docs of the re-read rule, for example `docs/dev/orchestration.md`. A notice is a message about such a landing from the orchestrator of the ticket to the other orchestrators. The user gives the session of each orchestrator a name of the form `orchestrator-<milestone>`, for example `orchestrator-m6`, `orchestrator-m7` or `orchestrator-docs`. The other orchestrators are all the sessions with such a name except the session of the orchestrator of the ticket.

The orchestrator of the ticket does these steps:

1. When the final report of the agent of the ticket arrives, read the files that landed in that report.
2. If no file of the report is one of the docs of the re-read rule, send no notice.
3. List the sessions with the session list of your tools, for example `ListAgents`. Each session whose name starts with `orchestrator-`, except your own session, is another orchestrator. A session with another name, for example `planner-m7`, gets no notice.
4. Send one notice to each other orchestrator with `SendMessage`. Take the landed commit and the sections that changed from the same report. The notice names them in one or two lines.

   For example: Landed `<commit>` on `main`. `docs/dev/orchestration.md` changed in "Pick the tickets" and "Land the work".

The notice does not depend on the re-read rule. If the re-read rule fails at this landing, the orchestrator of the ticket still sends the notice, and it tells the user the failed command and the error, as the re-read rule says. If the session list or a message fails, the orchestrator of the ticket tells the user the tool and the error, and it continues its work. A session that does not answer gets no second notice. The re-read rule covers that session at its next landing.

The notice is information. When the other orchestrator gets a notice, it does the steps of the re-read rule before its next step. It takes the rule from the doc, not from the notice.

The re-read rule and the notice rule do not cover the agents. Each new agent reads the docs when it starts.

### The defer rule

To defer a ticket means that the user moves its issue to a later milestone, for example "Future". This rule covers a deferred ticket that has a task in flight. A parked task is the task of such a ticket. On 2026-10-14, the user moved #34 from M5 to "Future" while its task was in `awaiting_plan_review`. The user did not want the task aborted, because `tasker abort` deletes the work of the agent. When the user defers a ticket that has a task in flight, the orchestrator does these steps:

1. Tell the agent of the ticket to stop. A message to an agent that has ended starts it again (see "Terms" in "Quota"). The agent stops after its current `tasker` command ends. It runs no other `tasker` command. Before its final report, it removes the task worktree as [the own-worktree rule](#the-own-worktree-rule) says. The remove changes no task, and the task keeps its state. Then it gives its final report.
2. Leave the task in its state. Do not run `tasker abort`, unless the user tells you to.
3. Delete the jobs of the agent, as "Delete the job" in "Quota" says.
4. Move the issue to the milestone that the user names: `gh issue edit <number> --milestone "<milestone>"`.
5. Move the card of the ticket to Todo. The ticket waits in Todo of its new milestone.
6. Post a comment on the issue that starts with `## Parked task`, with the findings of the final report, so that the next agent can start from them. Examples are the state of the task, the open plan questions, the answers so far and the facts that the agent tested.
7. List the open issues that the deferred issue blocks: `gh issue view <number> --json blocking -q '.blocking.nodes[] | select(.state == "OPEN") | .number'`. For each issue of the list, read its milestone: `gh issue view <blocked issue> --json milestone -q '.milestone.title'`. The command prints an empty line when the issue has no milestone. Keep the issues outside the new milestone of the deferred issue, also the issues with no milestone. If no issue is left, this step is complete. Otherwise, ask the user which of these links to remove. Most often the user removes all of them, so propose "remove all" as the default. Milestone numbers do not give the order of the milestones, so the user decides. For each link that the user names, run `gh issue edit <blocked issue> --remove-blocked-by <number>`. Then that issue can start, as [the stacking rule](#the-stacking-rule) says.

If a `gh` command of these steps fails, tell the user, and do the other steps. The task keeps its state.

A parked task stays in flight in `tasker status`. A task in flight is a parked task when the card of its ticket is in Todo, because the card of a ticket that runs is in In progress. To read the column of the card, run `gh issue view <number> --json projectItems -q '.projectItems[].status.name'`. The command prints `Todo` for a parked task. [The overlap rule](#the-overlap-rule), the move rule and the fourth case of [the stop rule](#the-stop-rule) leave out a parked task.

When the ticket comes back to the current milestone, the orchestrator starts a new agent for it, as [Pick the tickets](#pick-the-tickets) says. The agent follows [the comeback rule](#the-comeback-rule).

## The prompt of an agent

The orchestrator writes the prompt of each agent.

- The prompt of an agent gives only the context of its ticket. The context is the issue key, the milestones that are off limits for the agent, the landing order (see "Land the work"), for a stacked ticket, its parent (see [the stacked-ticket rule](#the-stacked-ticket-rule)), the quota slot and whether the agent has a job (see "Quota"), the folder of the agent for its files (see the folder bullet of "Limits"), and the hints for its first refine.
- When the orchestrator starts an agent, the orchestrator names the session of the agent after the issue key of its ticket. The orchestrator sets the session name with the `name` option of the Agent tool, for example `name: "codeguru42-tasker-108"`.
  - The list of the options of the Agent tool does not show `name`, but the tool accepts it. The `description` option is not the session name. The M7 orchestrator tested `name` on 2026-10-15. An Agent call with `name: "codeguru42-tasker-nametest"` started the agent with no error. A SendMessage with `to: "codeguru42-tasker-nametest"` reached that agent, and the agent answered. The report of the agent came back from `codeguru42-tasker-nametest`.
  - The session name has the form `<owner>-<repo>-<number>`, for example `codeguru42-tasker-108` for `codeguru42/tasker#108`. The Agent tool refuses a name that does not match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` (tested on 2026-10-14). The issue key itself does not match. The Docs orchestrator tested this on 2026-10-15. An Agent call with `name: "codeguru42/tasker#143"` failed before the agent started, with the error `name must start with a letter or digit and contain only letters, digits, underscores, or hyphens (max 64 chars)`. This error gives the same rule as the pattern. No later session tests the issue key as a name again.
  - The orchestrator uses the session name for each message to the agent, for each resume message and in the prompt of each quota job. The first bullet of this section already puts the issue key in the prompt of the agent. The prompt of each quota job gives the full issue key too, so that each one can be matched to the task. The reason: several orchestrators run at the same time. A name such as `agent-1` or a bare number does not say which ticket or which repo the session belongs to. The full key is unique, so the reports, the messages and the jobs can be matched to the task.
  - One agent runs one ticket, so one name belongs to one task. If the orchestrator starts a second session for the same ticket, the orchestrator adds a suffix, for example `codeguru42-tasker-108-2`, and says so in the prompt of the new agent.
  - If an agent already runs with no name, the orchestrator does not restart the agent only to give it a name. The reason: a new agent does not have the context of the old agent, for example the plans that it read and its review loops. For an agent with no name, the orchestrator puts the full issue key in the text of each message, each resume message and each quota job prompt, in place of the session name. The orchestrator names each new agent.
- Before the agent starts, the orchestrator makes the folder of the agent for its files (see the folder bullet of "Limits"). In one case, a background command of an agent wrote into a missing folder and failed.
- The orchestrator writes in the prompt that the comment of step 11 of "Run one ticket" is the only write of the agent on GitHub issues, labels and the project board (see "Limits"). In one case, a strong "never run a gh write" line in the prompt of an agent made the classifier of auto mode block the comment of step 11 (see [the tool-block rule](#the-tool-block-rule)).
- For all the rules, the prompt points to this page and to the docs that `AGENTS.md` names. No other base prompt exists.
- When the orchestrator learns a new rule for agents, it does not put the rule only in a prompt. It adds the rule to the body of a ticket that has not started, where the rule fits. Or it proposes a docs issue to the user. A rule that only one ticket needs can go in the prompt of that ticket.

## Run one ticket

The agent of the ticket runs steps 1 to 11. Each step gives the state of the task after its command succeeds.

1. Run `tasker doctor`. Then read the issue with `gh issue view <number>`, and compare the issue body with the prompt of the agent. If the body differs from the prompt, report each change to the orchestrator. The body can change while the agent works. Each `tasker` command of steps 1 to 11 follows [the command rules](#the-command-rules).
2. If `tasker status --issue <issue>` already lists a task for the ticket, for example a parked task that came back (see [the defer rule](#the-defer-rule)), follow [the comeback rule](#the-comeback-rule) instead of this step. Run `tasker start <issue>`. The task goes to `workspace_ready`. Read the output of `tasker start`, also stderr. The note `based on <key>'s branch` confirms a stacked task. If the note and the prompt do not agree (the prompt names a parent and the note is missing, or the note is present and the prompt names no parent), stop and report to the orchestrator. The task stays in `workspace_ready`. If `tasker start` refuses with `blocking issue is still open`, stop and report to the orchestrator. No task exists. Then make the task worktree as [the own-worktree rule](#the-own-worktree-rule) says. If the make fails, stop and report. The task stays in `workspace_ready`. The make changes no task. Then run `tasker plan <issue>`. The task goes to `awaiting_plan_review`.
3. Read the plan with `tasker show-plan` and `tasker show-questions`. Compare the plan with the Requirements and the Docs sections of the issue. Then apply [the stop rule](#the-stop-rule) and do [the quote check](#the-quote-check).
4. If the plan needs changes, run `tasker refine <issue> "<feedback>"`. Add the repo-files rule to the feedback text. Before the first refine, do [the fact test](#the-fact-test) and [the issue check](#the-issue-check). The task goes to `awaiting_plan_review` again. Then do steps 3 and 4 again until the plan needs no changes. Put the answers to the plan questions in the feedback text. `tasker plan` takes no feedback.
5. Run `tasker approve`. The task goes to `approved`. Run `tasker execute`. The task goes to `executed`. Run `tasker verify`. If the verify commands pass, the task goes to `awaiting_work_review`. If they fail, follow the verify-failure rule. Run `tasker review`. When the review has findings, the task goes to `reviewed`. When it has none, the task stays in `awaiting_work_review`. If the review has no findings, go to step 9.
6. Read the findings with `tasker show-review`. Decide for each finding if it is real. Then do [the quote check](#the-quote-check).
7. Dismiss each finding that is not real, with a reason: `tasker dismiss-review <issue> --finding N "<reason>"`. The task stays in `reviewed` while a finding is still open. If you dismiss all the findings, the task goes to `awaiting_work_review`, and you go to step 9.
8. If real findings are still open, run one `tasker refine <issue> "<feedback>"`. It acts on all the open findings. Add the repo-files rule to the feedback text. The task goes to `awaiting_plan_review`. After the refine, do steps 3 and 4 for the new plan. Then do steps 5 to 8 again, starting with `tasker approve`. The "Review findings" section limits the number of loops.
9. Run each `tasker` command of this step as [the plain-form rule](#the-plain-form-rule) says. The rule also covers the `tasker` commands that change a task in the other steps. Before each `tasker accept` of this step, also the one after `tasker update-branch`, do [the diff read](#the-diff-read). Run `tasker accept`. The task goes to `accepted`. `tasker accept` refuses when the branch does not contain the tip of `origin/main`. In that case, run `tasker update-branch`. The task goes to `executed`. Then run `tasker verify` and `tasker review` again as in step 5. If `tasker verify` fails, follow the verify-failure rule. If that review has findings, go to step 6. Otherwise, run `tasker accept` again. Run `tasker merge`. The task goes to `landed`. Then do [the CI wait](#the-ci-wait). The task stays in `landed`. If the CI wait passes, run `tasker finish`. The task goes to `finished`, and the issue closes. If a run failed, step 12 of the CI wait runs `tasker finish`. If the CI wait stops, do not run `tasker finish`, and do not do steps 10 and 11.
10. After `tasker finish`, make sure that `origin` has no task branch of the ticket. Do not rely on `tasker finish` for this. Do this step after each `tasker finish`. At the end of this step, whatever its result, remove the task worktree as [the own-worktree rule](#the-own-worktree-rule) says. Each "then do step 11" of this step comes after that remove. The remove changes no task, and the task keeps its state, for example `finished`. In each case of this step that says "delete nothing" or "delete nothing more", report to the orchestrator, and then do step 11. In such a case, unless the case says otherwise, the task branch on `origin` can still exist, and the task keeps its state. If the agent followed [docs/dev/rebase-conflicts.md](rebase-conflicts.md) and did not do its steps 15 to 20 yet, it does those steps first. If a step of that page stops before step 21, do not do the rest of this step. The shared failure paragraph before step 15 of that page names what stays behind, with the difference that the step names, and the task keeps its state. Report to the orchestrator. Then do step 11. After steps 15 to 20, step 21 of that page sends the agent back to this step. The agent then does the rest of this step and does not do steps 15 to 20 again. Run each command of this step in the local clone of the orchestrator. Run `tasker show <issue>`. It prints the task branch on the `branch:` line and the base branch on the `base branch:` line. If `tasker show` fails, delete nothing. If `tasker show` does not print the line `state: finished`, delete nothing. For example, the task is in `cleanup_failed`. In each case that follows, the task stays in `finished`. Run `git fetch origin`. If the fetch fails, delete nothing. Find out if `origin` has the task branch, with a read-only command: `git ls-remote --exit-code --heads origin refs/heads/<task branch>`. Give the full ref, because a short name also matches a longer branch name that ends with it. For example, `x` matches `feature/x`. The command exits with 0 when `origin` has the task branch. It exits with 2 when `origin` does not have the task branch. It exits with 128 when git cannot reach `origin`, for example when the path of `origin` does not exist. If the exit code is 2, the step is complete, and the task stays in `finished`. If the exit code is not 0 and not 2, delete nothing. While `origin` has the task branch, `git fetch origin` updates `origin/<task branch>`. A fetch without `--prune` keeps `origin/<task branch>` after `origin` deleted the branch. For this reason, the read of the tip and the next check run only after the exit code 0 of `git ls-remote`. If the exit code is 0, read the tip of the task branch on `origin`: `git rev-parse --verify origin/<task branch>`. The command prints the full hash of 40 characters of the tip. This step calls it `<commit>`. If the command fails, delete nothing. Then read the tip of the base branch: `git rev-parse --verify origin/<base branch>`. This step calls the hash `<base>`. If the command fails, delete nothing. The next checks use `<commit>` and `<base>`, and the delete uses `<commit>`, not the refs, as [the shared-clone rule](#the-shared-clone-rule) says. Make sure that the base branch contains `<commit>`: `git merge-base --is-ancestor <commit> <base>`. This is [the ancestor check](rebase-conflicts.md#the-ancestor-check) of [docs/dev/rebase-conflicts.md](rebase-conflicts.md), with `<commit>` as `<tip>`. That check gives the exit codes and the meaning of exit code 1. If the exit code is 1, do [the patch check](rebase-conflicts.md#the-patch-check) of that page, with `<commit>` as `<tip>` and the same `<base>`. Do only the patch check and the take check, and do not do step 17 itself or steps 18 to 21 of that page. If `git cherry` exits with 0 and a line starts with `+`, and the agent followed [docs/dev/rebase-conflicts.md](rebase-conflicts.md) for this task, do [the take check](rebase-conflicts.md#the-take-check) of that page. The agent is then the operator of that page and recorded `<taken>` at its step 11. Use `<commit>` as the pushed tip, the same `<base>` and the landed commit that `tasker merge` printed. Use only the two facts of the take check. Step 17 of that page already compared the local tip before step 20 deleted the local task branch. If the agent did not follow that page for this task, do not do the take check. If the patch check fails and the take check does not pass, delete nothing. For example, a fact does not hold, or a command of the take check fails. The task branch on `origin` stays. If the exit code is not 0 and not 1, delete nothing. The task branch on `origin` stays. If the exit code is 0, or the exit code is 1 and the patch check or the take check passes, delete the task branch on `origin` with a lease: `git push --force-with-lease=refs/heads/<task branch>:<commit> origin --delete <task branch>`. With the lease, git deletes the branch only when the branch on `origin` is still at `<commit>`. As a result, the delete cannot remove a commit that someone pushed to the task branch after the check. If the push succeeds, it exits with 0, and git prints `- [deleted]  <task branch>`. The step is complete, and the task stays in `finished`. If the push fails, for any reason, delete nothing more. For example, if someone pushed a new commit to the task branch after the check, the push exits with 1, and git prints `! [rejected]  (delete) -> <task branch> (stale info)`. The task branch on `origin` stays with the new commit. If someone deleted the branch after the check, the push exits with 1, and git prints `error: unable to delete '<task branch>': remote ref does not exist`. For another failure, the task branch on `origin` can still exist.
11. After `tasker finish`, post a comment on the issue that starts with `## Decisions made during implementation`. List the choices that the issue did not state, with the reasons. Name each detail that the issue did not give. A list item of the comment has no bold text at its start. The agent writes the comment in its final form before it posts it, because GitHub keeps the history of each edit.

### The final report

At the end of its work on the ticket, the agent gives a final report to the orchestrator. The agent gives the final report as its final answer, not with `SendMessage`. The work of the agent on the ticket ends after step 11, or when the orchestrator tells the agent to stop, for example in step 1 of [the defer rule](#the-defer-rule). A final answer that the agent gives before the end of its work is not the final report. That final answer gives the state of the task, says if the agent stopped, and says that the agent waits. Examples are the final answer of [the answer-wait rule](#the-answer-wait-rule) and the end of the turn after a quota stop in "What the agent does" in "Quota". The report gives these items:

- The result: the landed commit, the number of review loops, the files that landed and, for each doc that landed, the sections that changed. If the work of the agent ended before `tasker finish`, for example after the orchestrator told the agent to stop, the result gives the state of the task and the reason for the stop.
- Each finding that the agent dismissed, with its reason.
- The edge cases that the agent left out (see "Review findings").
- Each claim of the issue that was no longer true and each conflict (see [the issue check](#the-issue-check)). For a false claim, the bullet gives the current fact and the command that shows it. For a conflict, it gives the requirement, the conflicting rule or decision, the command or the doc that shows it, and the resolution: the change in the feedback text of the refine of step 4, the text of the plan that already resolves the conflict, or the answer of the user. If the task branch already held commits at the issue check, also the files that the agent read from the base commit and how.
- Each task worktree or local task branch that stays, with its path. [The own-worktree rule](#the-own-worktree-rule) says when one stays.
- The lessons.

The orchestrator sorts the lessons. A lesson that is a rule for the repo or for agents goes where the new-rule bullet of "The prompt of an agent" says.

### The comeback rule

This rule covers a ticket that already has a task in flight when its agent starts, for example a parked task that came back (see [the defer rule](#the-defer-rule)). The task already exists, so the agent does not run `tasker start` or `tasker plan`. If the issue has a comment that starts with `## Parked task` (step 6 of the defer rule), the agent reads the last such comment. Then it runs `tasker show <issue>`. Then the agent does steps 1 to 5 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md), as the diff read does. The clone then has the read-only `tasker` remote, and step 5 of that page fetches both remotes. Then the agent makes the task worktree as [the own-worktree rule](#the-own-worktree-rule) says. The branch-exists case can apply. The make changes no task. If the task is in `quota_blocked`, `interrupted` or `awaiting_quota_approval`, the agent follows "What the agent does" in "Quota", and it does not do the rest of this rule. Otherwise, the agent runs `git merge-base --is-ancestor origin/<base branch> tasker/<task branch>` with the base of [the base rule](#the-base-rule). If the exit code is 1, the base branch moved. In that case, if `tasker show <issue>` lists `update-branch`, the agent runs `tasker update-branch`. If `tasker show <issue>` does not list `update-branch`, the agent does not run it. The diff read before `tasker accept` finds the move later. If `tasker update-branch` reports a rebase conflict, the agent follows [docs/dev/rebase-conflicts.md](rebase-conflicts.md), as "Land the work" says. If a step of that page stops, a command fails, or the exit code is not 0 and not 1, the agent stops and reports to the orchestrator. The task keeps its state. Otherwise, the agent continues "Run one ticket" from the state that `tasker show <issue>` prints. After `tasker update-branch`, "Land the work" gives the next commands for the states that it names. For another state, for example `failed`, the agent follows the commands that `tasker show <issue>` prints.

### The base rule

This rule covers each command of this page that uses `origin/<base branch>`. A stacked task is a task that `tasker start` based on the branch of its parent (see [the stacked-ticket rule](#the-stacked-ticket-rule)).

Before each such command, the agent reads the `base branch:` line of `tasker show <issue>`. The agent does these steps:

1. If the line has a plain name, use `origin/<base branch>` as the command says.
2. If the line has the form `refs/heads/<parent branch>`, the task is stacked. Right before the command, run `git fetch tasker`. Then use `tasker/<parent branch>` in place of `origin/<base branch>`. If the step already ran `git fetch tasker` or `git fetch --multiple tasker origin` right before the command, it needs no second fetch.
3. If a step uses `tasker/<parent branch>` in more than one command, read its hash one time with `git rev-parse --verify`, as [the shared-clone rule](#the-shared-clone-rule) says.

A `tasker update-branch` with no conflict moves a stacked task onto the base of the parent after the parent lands.

An agent of a stacked task meets a landed parent at `tasker verify` in `executed`. It also meets a landed parent at `tasker refine` in `awaiting_plan_review`, after `tasker finish` of the parent. [The facts of the installed tasker](#the-facts-of-the-installed-tasker) say what happens in each case.

These steps use the base: the comeback rule, the diff read, the issue check, the broken-commit steps, the commit check, the same-patch rule, and steps 3 to 5 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md) when those rules do them.

Step 4 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md) does not stop for a stacked task when the diff read, the comeback rule or the commit check does the steps of that page. The manual fix and the procedure for a rebase conflict keep the stop.

### The add-work rule

If the task is in `awaiting_work_review` and the agent must add work, the agent runs `tasker review <issue> "<feedback>"`. The agent adds the repo-files rule to the feedback text. The task reaches `awaiting_work_review` after a review with no findings in step 5 or step 9, or after the agent dismisses all the findings in step 7. In this state, `tasker refine` refuses to run. The work can come from the orchestrator, for example. After `tasker review <issue> "<feedback>"`, the task goes to `refining`, and tasker makes a new plan revision. Then the task goes to `awaiting_plan_review`. Then the agent does steps 3 and 4 for the new plan, and steps 5 to 8 again, starting with `tasker approve`.

### The diff read

Each time before the agent runs `tasker accept` in step 9, the agent reads the full diff of the task branch against the base branch. The agent does this also after a review with no findings. In one milestone, this read found real duplication and false doc text on four tickets where the review found nothing. In the local clone of the orchestrator, the agent does steps 1 to 5 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The clone gets the read-only `tasker` remote, and the agent reads the base branch. The fetch of step 5 reads the tasker clone through the read-only `tasker` remote, and it changes nothing there. Then the agent does [the update rule](#the-update-rule) in the task worktree. The agent reads whole files of the task there. Then the agent runs `git diff origin/<base branch>...tasker/<task branch>` with the base of [the base rule](#the-base-rule). The task branch is on the `branch:` line of `tasker show <issue>`. The agent reads the full diff. The agent also searches each test file of the diff for a helper name that is defined two times, for example in the test file and in `test/helpers/`. A clean review missed such copies on more than one ticket. Such a copy is a duplication. If the agent finds a duplication, a fact that the docs lost, or a doc sentence that is false, it adds the work with the add-work rule. "Review findings" limits the number of loops. Right before `tasker accept`, after the agent read the diff, the agent fetches again, as [the base rule](#the-base-rule) says: `git fetch --multiple tasker origin` for a stacked task, and `git fetch origin` for a plain base. Then it runs `git merge-base --is-ancestor origin/<base branch> tasker/<task branch>` with the base of the base rule. This command uses `origin/<base branch>` one time, so it needs no hash read. If the exit code is 0, the task branch contains the tip of the base branch, and the agent runs `tasker accept`. If the exit code is 1, the base branch moved, for example `origin/main`. The agent does not run `tasker accept`. It runs `tasker update-branch` and continues step 9 as it says after `tasker update-branch`. The last fetch and `git merge-base` are commands of the diff read. An exit code of `git merge-base` that is not 0 and not 1 is a failure. A failed step of the update rule is a failed command of the diff read. If a step or a command of the diff read fails or stops, the agent stops, runs no `tasker accept` and reports to the orchestrator. The task stays in `awaiting_work_review`, and nothing changes in the repo or the worktrees of tasker. The report to the orchestrator takes the place of the person who decides on that page.

### The measure rule

This rule covers an issue that asks for a measure of the work, for example a test loop with a count of failures. The agent of the ticket takes the measure itself. It takes the measure in each diff read, after it reads the full diff and before the last fetch of the diff read. The agent takes the measure in the task worktree, after the update of the diff read. The result of the measure is an answer, not a failure of the diff read. For example, a count of failures, or a test command that exits with a code that is not 0, is a result. The agent records the result and continues the diff read. A command of the measure that cannot start, for example because `npm ci` fails, is also a failed command of the diff read. The diff read then stops, as it says, and the task stays in `awaiting_work_review`. The agent does not rely on the execute session for the numbers. No read-only `tasker` command prints the last message of that session, and the agent does not read a transcript of tasker (see the read bullet of [Limits](#limits) and [the own-worktree rule](#the-own-worktree-rule)). On #111, the agent measured the loops of the test again in its own worktree of the task branch. The agent gives the commands and the numbers of the last measure in the comment of step 11.

### The CI wait

After `tasker merge` in step 9, the agent of the ticket waits for the CI runs of the landed commit. `tasker verify` runs on the local machine, and the `Check` workflow on GitHub can still fail. For example, the local Node version can differ from the Node version of CI. The runs that count are the runs of the `Check` workflow on `main` for the landed commit, because they test the merged result. The agent runs each command of the CI wait in the local clone of the orchestrator. During the whole CI wait, the task stays in `landed`. The step numbers in the list below name the steps of the CI wait, not the steps of "Run one ticket". The agent does these steps:

1. Right after `tasker merge`, run `git fetch --multiple tasker origin`. The `tasker` remote is the read-only remote of the diff read. Then run `git rev-parse tasker/<task branch>`. The task branch is on the `branch:` line of `tasker show <issue>`. `tasker merge` lands the work as a fast-forward, so the tip of the task branch is the landed commit. The command prints the landed commit as a full hash of 40 characters. Use the full hash in the next steps, because `gh run list --commit` finds no run for a short hash.
2. Make sure that `main` contains the landed commit: `git merge-base --is-ancestor <landed commit> origin/main`. The check also passes when other tickets landed on top of the landed commit after `tasker merge`. If the exit code is not 0, `origin/main` does not contain the work of the ticket. In that case, report this to the orchestrator and stop.
3. Find the run with this command: `timeout 300 bash -c 'while :; do n=$(gh run list --workflow Check --branch main --commit <landed commit> --json databaseId -q length) || exit 2; [ "$n" != 0 ] && exit 0; sleep 30; done'`. GitHub can start the run some seconds after the push, so the list can be empty at first. The command reads the list every 30 seconds for at most 5 minutes. It exits with 0 when the list has a run. If it exits with 124, no run showed after 5 minutes. In that case, report to the orchestrator that no run showed, and stop. If it exits with 2, `gh run list` failed. In that case, report the error to the orchestrator and stop.
4. Run `gh run list --workflow Check --branch main --commit <landed commit> --json databaseId,status,conclusion`. If the command fails, report the error to the orchestrator and stop. The run id of each run is its `databaseId`. The list can have more than one run, because GitHub can record one push twice and start a run for each record. Take the runs in the order of the list. For each run, do step 5 of the CI wait. When step 5 or step 6 finds that the run passed, do step 5 for the next run of the list.
5. Wait for the run: `timeout 580 gh run watch <run id> --exit-status`. A `Check` run takes about 2 minutes, but it can take longer than one tool call of the agent. The agent cannot run a foreground `sleep`, so it waits with `timeout`. Exit code 0 means that the run passed. Exit code 124 means that the run is still in progress. In that case, run the same command again. The 30-minute limit counts from the first `gh run watch` of the CI wait, for all the runs of the list together. If a run is not complete when the 30 minutes end, report to the orchestrator and stop. Any other exit code means that the run failed, or that `gh` failed. In that case, go to step 6 of the CI wait.
6. Run `gh run view <run id> --json status,conclusion,url,jobs`. If the command fails, report the error to the orchestrator and stop. If `status` is `completed` and `conclusion` is `success`, the run passed. If `status` is not `completed`, `gh run watch` failed and the run is still in progress. In that case, do step 5 of the CI wait again. If `status` is `completed` and `conclusion` is not `success`, the run failed. In that case, go to step 7 of the CI wait.
7. If a run failed, do not fix the failure, and do not wait for the other runs of the list. Read the names of the failed jobs and steps from `jobs` (the entries with the `conclusion` `failure`). Read the names of the failed tests from `gh run view <run id> --log-failed`. With gh 2.101.0, `--log-failed` labels each line `UNKNOWN STEP`, so the step names come from `jobs`. If `gh run view --log-failed` fails, write down the error for the report of step 11 of the CI wait, and go to step 8 of the CI wait.
8. Run the failed tests on the local machine, on the landed commit, in the task worktree. Do not change `main`. Do [the update rule](#the-update-rule) in the task worktree. Then compare `git rev-parse --verify HEAD` with the full hash of step 1 of the CI wait. After `tasker merge`, the tip of the task branch is the landed commit, as step 1 says. If a step of the update rule fails, or HEAD is not the landed commit, write down the error, skip the local run, and go to step 9 of the CI wait. Otherwise, run `node --version`. Then run `npm ci` as the npm ci bullet of "Limits" says. Then run `npm test -- <test file> -t "<test name>"` for each failed test. The report gives the Node version, because the Node version of CI can differ. The local run is evidence only, and a failure in this step does not stop the CI wait. If `npm ci` or the test command cannot run, write down the error, and go to step 9 of the CI wait. The commands of this step change no task.
9. Rerun the failed jobs of the run one time: `gh run rerun <run id> --failed`. Do not rerun a second time. Exit code 0 means that GitHub accepted the rerun. Any other exit code means that the rerun did not start, and nothing changed on GitHub. With gh 2.101.0, the command exits with 0 when GitHub accepts the rerun. It exits with 1 when GitHub refuses it, for example while the run is still running, or when the run does not exist. If the rerun did not start, write down the error, and go to step 10 of the CI wait. If the rerun started, wait for it as steps 5 and 6 of the CI wait do. A new 30-minute limit counts from the first `gh run watch` of the rerun. When step 5 or step 6 finds that the rerun passed, or step 6 finds that it failed, go to step 10 of the CI wait, not to step 7. If the rerun is not complete when the 30 minutes end, go to step 10 of the CI wait. If `gh run view` fails in step 6, that is a stop, as step 6 says.
10. Decide the verdict. The verdict is flaky when the rerun passes. The verdict is broken for every other result: the rerun fails again, the rerun does not start, or the rerun does not complete in its 30 minutes. The local run of step 8 of the CI wait is evidence for the report. It does not change the verdict.
11. Report to the orchestrator: the run URL (`url`), the names of the failed jobs, steps and tests, and the verdict. The report also gives the result of the rerun: passed, failed again, did not start (with its error), or did not complete in 30 minutes. It also gives the result of the local run with the Node version, and each error of steps 7 to 9 of the CI wait. Then wait for the answer of the orchestrator, as [the answer-wait rule](#the-answer-wait-rule) says. While the agent waits, the task stays in `landed`. This wait is not a stop. The steps of the orchestrator are in "A failed CI run".
12. When the orchestrator answers with the number of the new issue, run `tasker finish`. The task goes to `finished`, and the issue closes. Then do steps 10 and 11 of "Run one ticket". The comment of step 11 also names the failed run, the verdict and the new issue.

The CI wait passes only when each run of the list passed in step 5 or step 6 of the CI wait. A rerun that passes in step 9 of the CI wait does not make the CI wait pass. The agent still does steps 10 to 12 of the CI wait. Other agents can land on `main` during the wait. The agent waits only for the runs of its own landed commit, not for a later run on `main`. If a git command of the CI wait fails, the agent reports the error to the orchestrator and stops. To stop means that the agent does not run `tasker finish` and does not do steps 10 and 11 of "Run one ticket". The agent runs no other `tasker` command until the orchestrator tells it the next step. In each case where the agent stops, the task stays in `landed`. The wait of step 11 of the CI wait is not a stop. If the agent gets a resume message while the task is in `landed` (see "When the job fires" and "What the agent does" in "Quota"), the rule depends on what the agent did before. If the agent did not run `gh run rerun` yet, it does the CI wait again from step 1 of the CI wait. If it ran `gh run rerun` and did not send the report of step 11 yet, it does not run `gh run rerun` again. If the rerun did not start, it goes to step 10 of the CI wait with the result "did not start". Otherwise, it waits for the rerun as step 9 says, with a new 30-minute limit from its first `gh run watch` after the resume. Then it goes on with step 10. If it sent the report of step 11, it does not do the CI wait again. It waits for the answer of the orchestrator, as [the answer-wait rule](#the-answer-wait-rule) says. If it got the number of the new issue, it goes on with step 12 of the CI wait.

### The repo-files rule

The agent adds this rule to the feedback text where a step, the add-work rule or the verify-failure rule says so. The rule tells the plan session (the session that tasker starts to make the plan) to read only the files in the worktree of the task. A file is outside the worktree when its path is not under the path on the `worktree:` line of `tasker show <issue>`. The plan session must not read or quote a file outside the worktree. If the plan session needs a detail that the issue, the feedback text and the files in the worktree do not give, it asks a plan question. It does not take the detail from another place. If the plan of step 2 needs no changes, the agent does not run a refine only to send this rule. The quote check covers that plan. The repo-files rule and the quote check cover only the plan session, the plans and the review findings. They do not cover the execute session or the diff.

### The fact test

Before the first refine of step 4, the agent tests on the local machine each fact about an outside tool that the plan depends on. Examples are a behavior of git, Node, zod or the operating system. The agent does not rely on the plan session to test these facts. Before each refine, the agent also tests each fact that a plan question asks about, and it answers the question in the feedback text. The agent puts the commands and their results in the feedback text. A fact test that runs the code of the repo runs in the task worktree, after [the update rule](#the-update-rule).

### The issue check

Before the first refine of step 4, the agent makes sure that each claim of the issue is still true in the task worktree, for example in the code and the docs. In the same worktree, the agent also compares each requirement of the issue with the docs and the code, and looks for each conflict. The check covers the base branch of the task as it was at `tasker start`, for example `main`. Right after `tasker start`, the task branch holds no commit of the ticket yet, so the task worktree holds the files of the base commit. If the task branch already holds commits, for example for a parked task that came back, the agent reads the base files without a worktree. After `git fetch --multiple tasker origin`, it runs `git merge-base tasker/<task branch> origin/<base branch>` with the base of [the base rule](#the-base-rule). The output is `<merge base>`. Then `git show <merge base>:<path>` reads one file, `git ls-tree -r --name-only <merge base>` lists the files, and `git grep <pattern> <merge base>` searches. For these read-only commands, a missing path (`git show` exits with 128) or no match (`git grep` exits with 1) is an answer, not a failure. The agent says which files it read from the base commit and how. It says this in the feedback text of the refine of step 4 and in its final report. If step 4 runs no refine, the agent does the issue check before `tasker approve` in step 5. Someone can write an issue long before an agent runs it, and other tickets can land in that time and change its facts. A claim is a statement in the issue body about the state before the ticket starts. Examples are a statement about the code, the docs or the behavior of tasker, and a measure of an outside tool that the issue gives. A requirement is a statement in the issue body about what the ticket must change, for example an item of its Requirements section. A requirement is not a claim. A conflict is a requirement that does not fit a rule of a doc, or a decision that the code or a landed ticket made after someone wrote the issue. For example, the issue asks for a rule that a doc already gives in other words. Or the issue asks for a file or a section that a later ticket moved or renamed. Or the issue asks for a behavior that a later rule forbids. For a measure of an outside tool, the agent measures again on the local machine, as the fact test does. The issue check does not cover the hints in the prompt of the agent, the plan or the review findings. The fact test and the quote check cover the plan. The issue check runs one time, with one exception. If the orchestrator edits the issue body after a stop of the fifth case, the agent does the issue check again for the claims and the requirements of the new body. The agent does it before the refine of step 4 that sends the answer. The issue check does not run again when the base branch moves after `tasker start`, for example before a `tasker update-branch`. If a false claim or a conflict does not change what the ticket must do, the agent does not stop. For a false claim, the agent puts the current fact in the feedback text of the refine of step 4. For a conflict, the agent says in that feedback text how it resolves the conflict. For example, the plan links to the existing rule instead of a copy, or it uses the new name of a file. If step 4 runs no refine, the agent does not run a refine only to send the current fact. If the plan does not resolve a conflict yet, the plan needs changes, and step 4 runs a refine. If a false claim or a conflict changes what the ticket must do, the fifth case of the stop rule applies. For a false claim, the agent puts the claim, the current fact and the command that shows it in its report of the stop case. For a conflict, the agent puts the requirement, the conflicting rule or decision, and the command or the doc that shows it in that report. In each case, the agent also lists each false claim and each conflict in its final report.

### The stop rule

Each time before the agent runs `tasker approve` in step 5, the agent stops in each of these cases:

- The plan has an open question that the issue does not answer.
- The plan makes a design choice that the issue does not make.
- The plan has a security gap.
- The plan changes a file that the issue does not name, and another task in progress also changes that file. For example, `tasker refine` prints a warning for such a file (see "Land the work"). This case does not apply when the orchestrator already set a landing order for that file. If the plan does not need the edit, the agent removes it in a refine of step 4, as "Land the work" says, and does not stop.
- A claim of the issue is no longer true, or a requirement of the issue is a conflict, and this changes what the ticket must do (see [the issue check](#the-issue-check)). This case does not apply when the orchestrator already answered for that claim or that conflict.

In each case, the agent reports the case to the orchestrator. The design-gap rule says who answers the first three cases. For the fourth case (a shared file), "Land the work" gives the steps. For the fifth case (a false claim or a conflict), the orchestrator asks the user, because only the user changes the scope of a ticket. If the user changes the scope, the orchestrator edits the issue body. The orchestrator owns the issue bodies, and the agent does not edit them (see Limits). The agent then waits for the answer, as [the answer-wait rule](#the-answer-wait-rule) says. While the agent waits, the task stays in `awaiting_plan_review`. After the answer, the agent puts the answer in the feedback text of the refine of step 4. Then the agent continues with step 4 and runs `tasker approve` in step 5. An answer before `tasker approve` costs no review loop, but a later answer costs one or more review loops. The quote check and the security report of "Review findings" give more cases that stop before `tasker approve`.

### The design-gap rule

A design gap is a detail that the plan needs and that the issue does not give, in the first or the second case of the stop rule. If the gap has exactly one workable answer inside the intent of the issue, the orchestrator gives that answer to the agent. The orchestrator also tells the user the answer. The user can change the answer before `tasker approve`. In that case, the orchestrator sends the new answer to the agent. If the gap has more than one workable answer, the orchestrator asks the user. A security gap (the third case) always goes to the user.

### The quote check

A plan or a finding quotes a file outside the worktree when it gives text from that file, or when it says that it read that file. "Outside the worktree" has the meaning of the repo-files rule. If a plan or a finding quotes a file outside the worktree, the agent tells the orchestrator. Then the orchestrator tells the user. After this report, the agent can still do the steps that come before `tasker approve` or `tasker accept`. For example, it can run a refine of step 4 or step 8, or dismiss a finding in step 7. If the next command of the agent is `tasker approve` or `tasker accept`, the agent stops and waits for the answer of the orchestrator, as [the answer-wait rule](#the-answer-wait-rule) says. While the agent waits, the task stays in its state, for example `awaiting_plan_review` before `tasker approve`, or `awaiting_work_review` before `tasker accept`. After the orchestrator answers, the agent does the step that the answer gives. If the answer gives no step, the agent continues "Run one ticket" from the step where it stopped.

### The verify-failure rule

This rule applies to each `tasker verify` on this page, in step 5, in step 9 and after `tasker update-branch` in "Land the work". If `tasker verify` fails, the task goes to `failed`. In `failed`, `tasker show <issue>` lists `refine`, `update-branch`, `retry` and `abort`. A fix of a failed `tasker verify` does not count as a loop of "Review findings". The limits of this rule count each refine and each retry after the last `tasker verify` that passed, for any cause. If the task is in `failed` after a command other than `tasker verify` or `tasker retry`, this rule does not apply. In that case, the agent follows the paragraph after this list, which starts "If a command fails". The agent reads the output of `tasker verify` and finds the cause of the failure. Then the agent does the first case of this list that applies:

- If the failure comes from the code and the agent already sent the refine of the next case, the agent stops. The agent reports to the orchestrator that it stopped, and the task stays in `failed`.
- If the failure comes from the code, the agent runs one `tasker refine <issue> "<feedback>"`. `tasker refine` accepts a task in `failed` only when the task has a plan revision. The feedback gives the cause of the failure. It tells the plan to go through the commits of the task branch one at a time. It also tells the plan to fix each broken commit in that commit, not in a new commit on top. More than one commit can be broken, so the refine fixes all of them. The broken-commit steps give the git commands for this feedback. The agent adds the repo-files rule to the feedback text. The task goes to `awaiting_plan_review`. Then the agent does steps 3 and 4 for the new plan, and steps 5 to 8 again, starting with `tasker approve`. As the other choice, the agent does not refine. The agent stops for a manual fix and reports to the orchestrator that it stopped. The task stays in `failed`. If the orchestrator then tells the agent to do the manual fix, the agent follows the broken-commit steps. For a failure from the code, the agent does not run `tasker retry`, because the same check fails again on the same code. The agent also does not run `tasker retry --resume-execute`. That flag resumes execute with no new feedback, so the plan does not get the cause of the failure.
- If the agent already ran `tasker retry`, the agent stops and reports to the orchestrator that it stopped. If the `tasker verify` that `tasker retry` ran failed, the task stays in `failed`. If `tasker retry` itself failed, the task stays in the state that `tasker show <issue>` prints.
- If the failure does not come from the code, the agent runs `tasker retry <issue>` one time. For example, a test failed one time for a reason outside the code. `tasker retry` accepts a task in `failed`. By default, `tasker retry` runs `tasker verify` again on the same code. If that verify passes, the agent runs `tasker show <issue>`, and the task is in the state that it prints. Then the agent runs the command that comes after `tasker verify` in the place that ran it. In each place on this page, that command is `tasker review`.

If a command fails or the task is in another state, run `tasker show <issue>` and follow the commands that it prints.

To find the next command, use these:

- `tasker --help` lists the commands.
- `tasker <command> --help` shows the states where the command is valid.
- `tasker show <issue>` shows the state of the task and the next commands.

### The plain-form rule

This rule applies to each `tasker` command that the agent runs and that changes a task. Examples are `start`, `plan`, `refine`, `approve`, `execute`, `verify`, `review`, `dismiss-review`, `accept`, `merge`, `finish`, `update-branch`, `retry` and `resume`. The agent runs each such command alone in its own Bash call (one call of the Bash tool of the agent). The call has the plain form: `tasker <command> <issue>` and the options of the command, for example `tasker accept codeguru42/tasker#81`. The issue key has no quotes. No `cd` comes before the command, no pipe comes after it, and no other command is in the same call. A feedback text goes in as one argument, as in `tasker refine <issue> "<feedback>"`. Inside double quotes, the shell expands backticks and `$`. Put the feedback text in single quotes, or keep backticks and `$` out of it.

The reason: the repo file `.claude/settings.json` allows `Bash(tasker *)`. A Bash call matches this permission rule only when the call is one `tasker` command. Claude Code sends a call that does not match to the classifier of its auto mode (the check that allows or denies a tool call). The classifier can deny the call. For example, the classifier denied `tasker accept 'codeguru42/tasker#81' 2>&1 | tail -5`, but it allowed `tasker accept codeguru42/tasker#81`.

If the classifier denies a `tasker` command in the plain form, the agent does not try another form. The agent stops and reports the exact text of the denial to the orchestrator. The orchestrator tells the user. The command did not run, so the task keeps its state. The agent runs no other `tasker` command until the orchestrator tells it the next step.

The plain-form rule does not cover these:

- A read-only `tasker` command, which does not change a task. Examples are `tasker show`, `tasker status`, `tasker show-plan`, `tasker show-review`, `tasker show-quota` and `tasker doctor`. Such a command can have a pipe, for example `tasker show-quota | jq` in "Quota".
- A change to `.claude/settings.json`. The rule does not change the permission rules of the repo.

### The tool-block rule

A tool block is a denial of a tool call by the permission rules or by the classifier of auto mode. [The plain-form rule](#the-plain-form-rule) covers a denied `tasker` command in the plain form. If any other tool block stops the agent, the agent reports the exact text of the denial to the orchestrator. The orchestrator tells the user. The orchestrator does not run the blocked action for the agent, unless the user tells it to.

### The command rules

These rules apply to each `tasker` command that the agent runs, also to a read-only one. They add to the plain-form rule and do not change it.

- Give the full issue key, for example `codeguru42/tasker#90`. A bare number such as `90` fails with `no repo configured for 90`, for example in `tasker show 90`. `tasker status --issue 90` does not fail. It prints `no tasks match the given filters` and exits with 0, so a check with a bare number finds no task.
- Never wrap a `tasker` command in `timeout`. At the end of the time, `timeout` sends SIGTERM, and tasker moves the task to `interrupted`. On 2026-10-13, `timeout 595 tasker execute` stopped an execute run this way, and `tasker resume` had to continue it.
- Run a long `tasker` command in the background. The long commands include `plan`, `refine`, `execute`, `review` and `resume`. The agent sets the `run_in_background` option of its Bash tool. The call keeps the plain form.
- To wait for the end of a long command, wait for the report of the Bash tool that the background job of the command ended. Do not wait with a loop that reads the state in `tasker status`. Such a loop is not reliable. For example, a review run can end in `awaiting_work_review` or in `reviewed`, so a loop that waits while the state is `reviewing` cannot tell the end from the start. The Bash tool gives its report after a Bash call of the agent ends. While the agent waits, it runs a short wait in another Bash call, for example `timeout 100 bash -c 'while :; do sleep 15; done'`. This call always exits with 124. If no report came, the agent runs the same wait again. After the report, the agent reads the state with `tasker show <issue>`. When the orchestrator starts the agent again, the agent follows "What the agent does" in "Quota".
- When the output of a read-only `tasker` command goes into a pipe, start the call with `set -o pipefail`. As a result, a failed `tasker` command stops the chain. To keep only some lines, use `sed -n`, for example `sed -n '1,20p'`, not `head`. With `pipefail`, `head` can make the pipe exit with 141 when tasker succeeded, because `head` stops reading early.

### The facts of the installed tasker

- `tasker plan` can fail with "planning returned no structured output; the assistant produced no plan object". The task goes to `failed`. This failure does not come from the code. One `tasker retry <issue>` plans again.
- `tasker start` can wait about 10 minutes on `git ls-remote` over ssh and then fail with a git transport error. If `tasker doctor` then passes, the agent runs `tasker start` again.
- `tasker update-branch` prints `origin/<branch> does not exist; nothing to sync from` for a task branch that was never pushed. This output is normal.
- `tasker merge` prints `landed: <commit> on origin/main`. `tasker finish` prints that it marked the issue done on the tracker, and it closes the issue.
- `tasker start` can print a GraphQL warning that the assign of the issue on the tracker failed. The warning does no harm.
- `tasker start` refuses a ticket whose parent is not [ready to stack](#the-stacking-rule). It exits with 1 and prints `<parent issue key>: blocking issue is still open`. No task exists after the refusal.
- `tasker verify` refuses a stacked task whose parent has landed. It prints `task <id>'s parent <parent issue key> has landed on origin/main; run tasker update-branch <issue key> to move this task onto it first`. The task stays in `executed`. `tasker update-branch` rebases only the commits of the task onto the base of the parent.
- A stacked task in `awaiting_plan_review` loses its base when `tasker finish` of the parent deletes the branch of the parent. `tasker refine` then fails with exit code 1 and an `unknown revision` error of `git diff`, and it changes nothing. `tasker update-branch` moves the task onto the base of the parent, and the task stays in `awaiting_plan_review`. tasker marks the plan as stale, so a refine comes before `tasker approve`, also when the new base changes no fact of the plan.

### The run times

An agent picks the wait for a long command (see the wait bullet of [the command rules](#the-command-rules)) from these usual run times. The times come from the tickets of this repo.

- `tasker start`: a few seconds. For the wait of about 10 minutes on ssh, see [the facts of the installed tasker](#the-facts-of-the-installed-tasker).
- `tasker plan`: about 1 to 2 minutes for a small issue, and about 4 to 6 minutes for a large issue.
- `tasker refine`: about 1 to 4 minutes.
- `tasker execute`: about 1 to 2 minutes for 2 to 4 todos, and about 8 to 15 minutes for 20 to 30 todos.
- `tasker verify` (`npm run check`): seconds.
- `tasker review`: about 25 seconds to 2 minutes.
- A docs ticket: about 1 to 2 minutes for each of plan, refine and execute.

### The broken-commit steps

These steps give the git commands for a failure from the code in the verify-failure rule. A broken commit is an implementation commit that fails `npm run check`, or the tip of the task branch when it fails `npm run check`. The tip has no next commit, so it must pass, whatever its prefix. The cause commit of a broken commit is the commit that adds the cause of its failure. It is the broken commit itself, an earlier broken commit, or an earlier commit that the check skips, for example a `test:` commit that adds a test configuration. It is never under the last commit that passed the check, or under the base commit. The Commits section of [docs/dev/rules.md](rules.md) defines an implementation commit and gives the rule. The fix of a broken commit goes into its cause commit, not into a new commit on top. The steps do not change the limits or the cases of the verify-failure rule.

The base commit is the commit under the first commit of the task branch. `tasker update-branch` moves the task branch onto a newer base, so the base commit changes. For this reason, each [commit check](#the-commit-check) of the agent finds the base commit again. The refine feedback gives the base commit of the last commit check, and the session steps use the base commit of the feedback. The one exception is the refine of step 4 after a `tasker update-branch`: there the base commit comes from `git merge-base` directly, not from a commit check.

In the refine of the verify-failure rule, the agent first does the commit check on the local task branch, in the task worktree. If the commit check finds no broken commit, each implementation commit and the tip pass, so the failure does not come from the code. The agent does not send the refine. It follows the cases of the verify-failure rule for a failure that does not come from the code. Otherwise, the feedback names each broken commit of the check, by its hash and its subject. The commit check names each broken commit, but not its cause commit. A named `feat:`, `fix:` or `refactor:` commit is not the cause when its failure comes from an earlier commit that the check skips. For this reason, the feedback also names the commits that the check skipped under each broken commit, back to the last commit that passed the check or to the base commit. These commits and the earlier broken commits of the list are the other candidates for the cause commit. It gives the base commit of the check. If the agent runs `tasker update-branch` after it sends the refine and before `tasker approve`, the agent does not run the commit check again. The hashes and the base commit in the feedback are then out of date. The session finds the broken commits again with its own commit check, so the names in the feedback only describe the failure. In the refine of step 4, the agent gives the new base commit: the agent runs `git fetch --multiple tasker origin`, then `git merge-base tasker/<task branch> origin/<base branch>` with the base of [the base rule](#the-base-rule). If a command fails, the agent stops and reports to the orchestrator, and the task stays in `awaiting_plan_review`. This refine of step 4 is part of the same fix, not a new refine of the verify-failure rule, so the limits of that rule do not change. Then the agent continues as usual. `tasker verify` runs after `tasker approve` and `tasker execute`, as the steps of "Run one ticket" say. If that `tasker verify` fails, the agent follows the verify-failure rule, which looks for broken commits again. If it passes, the agent continues as usual. The feedback tells the session (the execute session that tasker starts) to fix the cause commits with these steps:

1. Do [the session check](#the-session-check). The result is the list of broken commits, oldest first. If the session check stops, stop and report, as the session check says.
2. If the list is empty, the session ends. Each commit passes, whatever repaired it, for example an earlier fix or `tasker update-branch`.
3. On the task branch, take the oldest commit on the list. In the first round, find its position. The position of a commit is the number that `git rev-list --count <base commit>..<commit>` prints (1 for the first commit after the base commit). A later commit has a higher position. The hashes change after each autosquash, so the session compares positions, not hashes. If the command fails, stop and report. The task branch stays as it was. In later rounds, keep the position that step 5 found. Then read the failure of the oldest commit and find its cause commit, as the definition above says. Stage the fix and run `git commit --fixup=<cause commit>`. This also applies when the cause commit is the tip or a `test:` commit. If the command fails, stop and report. The staged fix stays, and git makes no fixup commit.
4. At once, run `GIT_SEQUENCE_EDITOR=: git rebase --autosquash <base commit>` on the task branch. `GIT_SEQUENCE_EDITOR=:` makes sure that the rebase does not wait for an editor. With git 2.47.3, the `--autosquash` flag works without `-i`, and the rebase does not depend on the `rebase.autoSquash` configuration. The rebase squashes the fixup commit into the commit that it names. As a result, the fix is part of the history before the session looks at the next commit. If the rebase fails, for example with a conflict, run `git rebase --abort`, then stop and report. The branch goes back to its state before the rebase, with the fixup commit on top.
5. Do step 1 again. A commit that is not on the new list needs no fix. If the new list is empty, go to step 2. Otherwise, find the position of the oldest commit on the new list with the command of step 3, and keep it for the next round. If the oldest commit on the new list is not later on the branch than the oldest commit of the list before, the session stops and reports. The fixes so far stay in their commits. Otherwise, do steps 2 to 5 again. The position test ends the session after at most as many rounds as the task branch has commits after the base commit.

If the session stops, the execute run fails. The agent then follows the verify-failure rule as it already says. For a task in `failed` after a command other than `tasker verify` or `tasker retry`, that rule sends the agent to the paragraph that starts "If a command fails".

After the refine, the agent continues as the verify-failure rule says. When the `tasker verify` after the fix passes, the agent does the commit check before `tasker review`, unless the agent ran `tasker update-branch` after the failed `tasker verify`. This check runs only because a `tasker verify` failed before the fix. When `tasker verify` passes and no failed `tasker verify` came before it, the agent runs no commit check. After `tasker update-branch`, the agent runs no commit check until `tasker verify` fails. `tasker verify` runs after `tasker update-branch` as step 9 and "Land the work" say. If the commit check fails, the agent stops and reports the list of broken commits to the orchestrator. The agent does not run another refine, because the verify-failure rule permits one refine. The task stays in `awaiting_work_review`.

### The session check

The session check runs the rebase of the commit check directly on the task branch. The check commands only run the tests and change no commit. The last paragraph of [the commit check](#the-commit-check) gives the facts of this rebase during and after its run. At the end, HEAD is on the task branch. If the rebase stops for another reason, `git rebase --abort` puts the task branch back at its tip, with HEAD on the task branch.

If the session stops in the middle of the rebase, the worktree stays in the rebase. Step 2 covers this case when the session goes on.

The session does these steps in its worktree, on the task branch, with the base commit of the feedback:

1. Do steps 5, 6 and 8 of [the commit check](#the-commit-check): the `git rebase --exec` command, the notes and `git rebase --continue`, and the tip check. Step 2 takes the place of step 7 of the commit check. If the rebase exits with 0, the result is the list of broken commits, oldest first. The list can be empty. Then no rebase is in progress, so step 2 does nothing, and step 3 does not stop. If the rebase stops for another reason, or another error occurs, for example the rebase does not start or a command of step 8 of the commit check cannot run, go on with step 2.
2. If a rebase is still in progress after step 1, run `git rebase --abort`. A rebase is in progress when the folder `$(git rev-parse --git-path rebase-merge)` exists. If the abort fails, stop and report. The worktree stays in the rebase, and the task branch stays at its tip.
3. If step 1 ended with such a stop or error, stop and report. The task branch stays at its tip, with HEAD on the task branch.

### The manual fix

The agent does the manual fix only when the orchestrator tells it to, after the stop for a manual fix in the verify-failure rule. The agent never changes the tasker clone (the clone of this repo that tasker keeps, see [docs/dev/rebase-conflicts.md](rebase-conflicts.md)) or its worktrees by hand (see [the own-worktree rule](#the-own-worktree-rule)). The agent does these steps:

1. Do steps 1 to 6 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The agent works in the task worktree. Step 6 of that page uses it. [The local-commit rule](#the-local-commit-rule) holds from step 2 of this list. If a step fails, stop and report to the orchestrator. The task stays in `failed`.
2. Do the commit check on the local `<task branch>` to find the broken commits and the base commit. If the check finds no broken commit, report this to the orchestrator. The orchestrator gives the next step. If the check stops with an error, stop and report to the orchestrator. In both cases, the worktree and the local task branch stay, and the task stays in `failed`.
3. In the worktree, do the session steps of [the broken-commit steps](#the-broken-commit-steps) on the local `<task branch>`, with the base commit of the last commit check. If the session steps stop, stop and report to the orchestrator. The worktree and the local task branch stay, and the task stays in `failed`.
4. Do the commit check on the local `<task branch>` again. This check also covers step 8 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md), because it checks the tip. If the check lists a broken commit, fix the cause commits of the listed commits one time with step 3, with the base commit of this check. Then do the commit check one more time. If that check still lists a broken commit, stop and report the list to the orchestrator. If a check stops with an error, stop and report to the orchestrator. In each of these cases, the worktree and the local task branch stay, and the task stays in `failed`. Nothing reached tasker yet.
5. Do steps 9 to 21 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md): the push to `origin`, `tasker update-branch <issue> --take-remote`, the next commands, and the cleanup after `tasker finish`.

### The commit check

The commit check makes sure that each implementation commit and the tip of the task branch pass `npm run check`. It gives the list of broken commits and the base commit. The agent does it in the task worktree, on the local task branch:

1. Do steps 1 to 4 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The clone gets the read-only `tasker` remote, and the agent reads the base branch. If a step fails, stop and report to the orchestrator. Nothing changes.
2. Run `git fetch --multiple tasker origin`. If the fetch fails, stop and report to the orchestrator. Nothing changes.
3. Work in the task worktree, on the local task branch. This step makes no worktree. Outside the manual fix, do [the update rule](#the-update-rule). In the manual fix, the local-commit rule holds, so run no update. If a step fails, stop and report to the orchestrator. Nothing changes.
4. In the task worktree, find the base commit: `git merge-base HEAD origin/<base branch>` with the base of [the base rule](#the-base-rule). If the command fails, stop and report to the orchestrator.
5. Run `git rebase --exec 'L=$(git rev-parse --git-path npm-ci-lock); { cmp -s "$L" package-lock.json || { npm ci && cp package-lock.json "$L"; }; } && case "$(git log -1 --format=%s)" in feat:*|fix:*|refactor:*) npm run check ;; esac' <base commit>`. The command runs after each commit. It runs `npm ci` when `package-lock.json` differs from the copy of the last install. It keeps that copy in the git folder of the worktree (`git rev-parse --git-path npm-ci-lock`), so `git status` stays clean. Then it runs `npm run check` after each implementation commit. The rebase skips `test:` and `docs:` commits. If `npm ci` fails, the command fails after that commit, and step 6 notes that commit. Because the branch already starts on the base commit, the rebase keeps the same commits.
6. If the rebase stops and prints `warning: execution failed`, the command failed after the commit that `git log -1 --format='%h %s'` names. Note that commit as a broken commit. Then run `git rebase --continue`, and the rebase checks the next commits. Do this step again each time the rebase stops this way. A commit after a broken commit can fail only because of the earlier commit. The session fixes the oldest broken commit first and then runs the check again, so a fix of the earlier commit can also remove a later commit from the list.
7. If the rebase stops for another reason, run `git rebase --abort`. The worktree goes back to the branch at the old tip. Then stop and report the error to the orchestrator. If the abort fails, the ref of the branch is still at the old tip, and the worktree stays in the rebase. Stop and report the output of `git -C <path> status`.
8. When the rebase exits with 0, it kept the same commits, and the worktree is at the tip. If the tip is not an implementation commit, run `npm run check` one time in the worktree. The worktree already has the packages of the tip, because the rebase ran the command after the tip too. If `npm run check` fails, note the tip as a broken commit.
9. The commit check passes when it noted no broken commit. Otherwise, the check fails and gives the list of broken commits and the base commit of step 4. The step that ran the check gives the next step.

During the rebase, HEAD is detached inside the task worktree, and the branch ref stays at the old tip. When the rebase ends, it keeps the same commits, so the branch is at the same tip.

## Review findings

- One loop is one `tasker review` and the work on its findings. The agent runs at most 5 review loops.
- The same-patch rule: this rule covers a task in `awaiting_work_review` when the agent of the ticket runs `tasker update-branch`. The agent reads two patch ids in the local clone of the orchestrator, with the remotes of [the diff read](#the-diff-read). A patch id is the first field of the output of `git patch-id --stable` for the diff of the task branch against its base. The output has the form `<patch id> 0000000000000000000000000000000000000000`. The first patch id: while the task is in `awaiting_work_review`, right before `tasker update-branch`, the agent runs `git fetch --multiple tasker origin`. Then it runs `set -o pipefail; git diff origin/<base branch>...tasker/<task branch> | git patch-id --stable` with the base of [the base rule](#the-base-rule). The second patch id: after `tasker update-branch`, while the task is in `executed` and before `tasker verify`, the agent runs the same two commands again. The three dots diff against the merge base. As a result, the first patch id uses the old base, and the second patch id uses the new base. The agent must run the fetch before each read.
- The same-patch review is the first `tasker review` after that `tasker update-branch` when the two patch ids are the same. A same-patch review does not count as a loop, also when it has findings. For this one review, the same-patch rule wins over the loop definition of the first bullet. If the same-patch review has no findings, the task stays in `awaiting_work_review`. If it has findings, the task goes to `reviewed`, and the agent works on them with steps 6 to 8 of "Run one ticket". After the 5th loop, the bullet "After the 5th loop" wins. If a real finding of a same-patch review is still open, the agent stops as that bullet says. If the agent dismisses all the findings in step 7, the task goes to `awaiting_work_review`. In each case, the agent then continues as the place that ran `tasker update-branch` says. Work can follow the same-patch review, for example the refine of step 8 or the work of the add-work rule. Then the next `tasker review` counts as a loop.
- The review after `tasker update-branch` counts as a loop in each of these cases. The two patch ids differ, for example because the rebase solved a conflict. `tasker update-branch` reported a rebase conflict. An output of `git patch-id` is empty, because an empty output gives no patch id. The agent did not read the first patch id. A command of this rule fails, for any reason. A failed command of this rule changes nothing in the repo or in the worktrees of tasker, and the task keeps its state. The work changes between `tasker update-branch` and the review, for example with a refine after a failed `tasker verify`.
- The limit of 5 loops counts all other reviews, as before. For a task in `reviewed`, the bullet of "Land the work" that starts "If the task was in `reviewed`" gives the count. On #92, `main` moved two times during the review loops. Each `tasker update-branch` from `awaiting_work_review` forced a new review, and each review counted as a loop. As a result, 2 of the 5 loops had no change to the work.
- The early update: this rule covers a task in `reviewed` when the earlier ticket of a landing order shares a file with the task. Before each refine of step 8, the later agent reads the state of the issue of the earlier ticket one time with `gh issue view <number> --json state -q .state`. If the state is `CLOSED` and the later agent did not run `tasker update-branch` after the close, it runs `tasker update-branch` first. This rule adds to the bullet of "Land the work" that starts "If a refine, or the `tasker review <issue> "<feedback>"` of the add-work rule, must change a file". The review right after this update and the review before it count as one loop, as the bullet of "Land the work" that starts "If the task was in `reviewed`" says. The review after the refine of step 8 is the next loop. So the early update costs no extra loop. If the later agent ran the early update after the close, the bullet "When the issue of the earlier ticket is closed" does not apply. The later agent then continues step 9 of "Run one ticket" from `tasker accept`. The diff read before `tasker accept` finds a later move of the base branch. Without the early update, the update runs later from `awaiting_work_review`, and there a review after a rebase conflict counts as a loop. On #129, such a review was loop 5, so a finding in it got no fix.
- The no-loop-left rule: this rule covers a task in `awaiting_work_review` after the 5th loop, when a step needs `tasker update-branch`, for any reason. The agent reports to the orchestrator before `tasker update-branch`. The agent runs no `tasker update-branch` and no `tasker accept`. The task stays in `awaiting_work_review`. The orchestrator asks the user. This rule wins over each step that runs `tasker update-branch` from `awaiting_work_review`, for example step 9 and [the diff read](#the-diff-read), and the bullet "When the issue of the earlier ticket is closed" of "Land the work". A same-patch review costs no loop (the same-patch rule of this section). For example, if the patch ids differ or the rebase has a conflict, the review counts as a loop (the bullet "The review after `tasker update-branch` counts as a loop"). As a result, after the 5th loop, such a review is over the limit.
- After the 5th loop, if a real finding is still open, or the diff read finds work, the agent stops and reports to the orchestrator. The agent runs no refine, no `tasker review <issue> "<feedback>"` and no `tasker accept`. The task keeps its state, for example `reviewed` or `awaiting_work_review`. The orchestrator reports to the user.
- On the 5th loop, the agent dismisses cosmetic findings with a reason.
- If a finding is an edge case outside the issue, and it is not a security gap and not a bug in the core path, the agent dismisses it in step 7. The core path is the main use that the issue describes. The reason says that the edge case is outside the issue. The agent lists the finding in its final report, and the ticket does not grow. A refactor or duplication finding is not such an edge case.
- If a finding contradicts an exact rule of the issue, the agent dismisses it in step 7. The reason quotes that rule of the issue.
- The security report: if the agent dismisses a finding in step 7 because the finding contradicts the issue, and the finding points to a possible security gap, the agent also reports the gap to the orchestrator in the same step. A security gap is a way to harm the user or the system. For example, text of a third party, such as an issue body, reaches a prompt as an instruction. The report gives the finding, the rule of the issue and the risk. The orchestrator tells the user, because the decision belongs to the user. Then the agent stops before its next `tasker approve` or `tasker accept` and waits for the answer, as [the quote check](#the-quote-check) and [the answer-wait rule](#the-answer-wait-rule) say. If the user decides to close the gap, the orchestrator first edits the issue body, as for the fifth case of the stop rule. Then the agent adds the work with the step that fits the state of the task: the refine of step 4 or step 8, or the add-work rule. If the report comes in the 5th loop, a decision to close the gap counts as a real finding that is still open, and the second bullet of this section applies. The security report does not cover a security gap in a plan before `tasker approve`. The third case of the stop rule covers that gap.
- A refactor or duplication finding is not cosmetic. The agent refines a refactor finding in the ticket that added the code. The agent fixes a duplication finding (the same code or text in more than one place) at once, in the ticket that adds the duplicated code. The finding comes from a review or from [the diff read](#the-diff-read). The agent fixes a finding from a review with the refine of step 8, and a finding from the diff read with the add-work rule. The agent does not dismiss a real duplication finding.
- When the agent sends a fix in the refine text, it writes "apply everywhere it fits". Otherwise the next review finds the same problem in other places.

The missed-finding rule: a review or the diff read can miss a refactor or duplication finding. When someone finds it later, the fix goes to the first place of this list that applies:

1. The ticket that adds the code, inside the 5 review loops of this section. While that ticket is open, the orchestrator does not move the fix into another ticket. On #71, on 2026-10-13, the user replaced the extra loop after the last loop with "up to 5 loops, then report".
2. If that ticket already landed, a ticket that changes the same code. For a ticket in progress, the orchestrator tells its agent to add the fix to its next refine. For a ticket that has not started, the orchestrator edits its issue body.
3. If no such ticket exists, the orchestrator files a new issue to fix it.

## Land the work

The steps to land a ticket are in "Run one ticket". This section gives the rules between tickets.

- After `tasker approve`, each agent sends the orchestrator the list of files that the plan changes. `tasker refine` and `tasker approve` also print a warning when another task in progress changes the same file.
- If the edit of a shared file is not required, the agent removes it in a refine. If it is required, the orchestrator sets the landing order.
- When the orchestrator sets the landing order, it tells the later agent which ticket must land first. The earlier ticket is the ticket that must land first. The later agent is the agent of the ticket that lands after it. The earlier agent is the agent of the earlier ticket.
- The later agent does the steps of "Run one ticket" up to `tasker accept` in step 9. Before it runs `tasker accept`, it waits until the issue of the earlier ticket is closed. While the later agent waits, the task is in `awaiting_work_review`.
- The start state is the state of the earlier task before a wait on a landing order of the overlap rule. Before the orchestrator tells the later agent to wait, it reads this state with `tasker show <issue>`. The orchestrator reads it before each wait, also before a new wait. If the earlier task is far from landing, for example in `awaiting_plan_review`, the orchestrator tells the user. If the start state is before `awaiting_work_review`, [the hold rule](#the-hold-rule) also applies. If `tasker show <issue>` fails, the orchestrator tells the user, and the start state is unknown.
- To wait, the later agent reads the state of the issue of the earlier ticket one time: `gh issue view <number> --json state -q .state`. If the state is `OPEN`, the later agent reads it again every 30 seconds until it is `CLOSED`. The later agent waits at most 60 minutes from the first read.
- If the state is still `OPEN` 60 minutes after the first read, the later agent stops waiting. To stop waiting means that the later agent stops reading the issue state.
- If the earlier agent stops before the issue of the earlier ticket closes, the orchestrator tells the later agent to stop waiting. Then the later agent stops waiting. For example, the earlier agent stops after its last loop of "Review findings". Or it reports a rebase conflict that it does not fix (see [docs/dev/rebase-conflicts.md](rebase-conflicts.md)). Or it stops in the CI wait, for example when no run showed.
- This bullet covers two tickets of the orchestrator. If the earlier agent stops to wait for a decision of the user, the orchestrator changes the landing order at once. It changes the order as the bullet "If the orchestrator changes the landing order" says. It does not let the later agent wait until the end of its 60 minutes. In one milestone, two waits of 60 minutes were lost this way. For a landing order of the overlap rule, the bullet "Only the user changes a landing order of the overlap rule" applies.
- If the later agent stops waiting, for either reason, it does not run `tasker accept`. The task stays in `awaiting_work_review`. The later agent reports to the orchestrator that it stopped waiting, and why. Then the later agent runs no other `tasker` command until the orchestrator tells it the next step.
- After the later agent reports that it stopped waiting, the orchestrator decides the next step and tells the user. For a landing order between two tickets of the orchestrator, the orchestrator tells the later agent to wait again. Or it changes the landing order so that the later ticket lands first. For a landing order of the overlap rule, [the stuck-task rule](#the-stuck-task-rule) gives the next step.
- Only the user changes a landing order of the overlap rule, because the earlier ticket belongs to another orchestrator. If the user swaps the order, the user tells each orchestrator the new order. Each orchestrator tells its own agent, as the overlap rule says. Then the two tickets swap roles, as the sentences of the bullet "If the orchestrator changes the landing order" from "Then the two tickets swap roles." say. The first sentence of that bullet, where the orchestrator tells both agents, covers only two tickets of the orchestrator. If the user postpones the earlier ticket, the user does this through the orchestrator of that ticket. That orchestrator does the steps of [the defer rule](#the-defer-rule). The task of the earlier ticket becomes a parked task, and the paragraph of [the defer rule](#the-defer-rule) that starts "A parked task stays in flight" applies. The user tells the orchestrator of the later ticket that the earlier ticket is postponed, as in the swap case. That orchestrator then tells the later agent to continue step 9 of "Run one ticket" from `tasker accept`. Another orchestrator can relay a change of a landing order from the user. Then the orchestrator that gets the relay asks its own user to confirm the change before it tells its agent, as [A decision of the user](working-with-the-user.md#a-decision-of-the-user) says. Until the user confirms, the old order stays: the landing order before the relay. The reason: a message from another session is not an answer of the user. The relayed order can also differ from an answer that the user gave before to the orchestrator that gets the relay. When the user confirms, the orchestrator that gets the relay tells its agent the new order, as the overlap rule says. The orchestrator that gets the relay also tells the other orchestrator with `SendMessage` that its user confirmed.
- If the orchestrator tells the later agent to wait again, or to start the wait under the hold rule, the later agent starts a new wait as in the "To wait" bullet. The new limit is 60 minutes from the new first read. The task stays in `awaiting_work_review`.
- If the orchestrator changes the landing order, it tells both agents the new order. Then the two tickets swap roles. The ticket that was the later ticket becomes the earlier ticket, and its agent becomes the earlier agent. The ticket that was the earlier ticket becomes the later ticket, and its agent becomes the later agent. From then on, "earlier" and "later" name the roles in the new landing order. If the new earlier agent waits before `tasker accept`, its task is in `awaiting_work_review`, and it continues step 9 of "Run one ticket" from `tasker accept`. Otherwise, it continues its steps of "Run one ticket", and it does not wait before `tasker accept`. Step 9 gives the state after each command. Before the new later agent runs `tasker accept` in step 9, it follows the wait rules of this section, from the bullet "The later agent does the steps of ...". The orchestrator changes a landing order only between two of its own tickets. For a landing order of the overlap rule, the bullet "Only the user changes a landing order of the overlap rule" applies.
- When the issue of the earlier ticket is closed, the later agent runs `tasker update-branch`. The task goes from `awaiting_work_review` to `executed`. For a stacked task, this `tasker update-branch` moves the task onto the base of the parent if the update has no conflict, and the task is then no longer stacked. The later agent then reads the `base branch:` line again, as [the base rule](#the-base-rule) says. Then the later agent continues step 9 of "Run one ticket" from its `tasker verify`. If `tasker verify` fails, the later agent follows [the verify-failure rule](#the-verify-failure-rule).
- The later agent of a stacked task never runs `tasker merge` before the issue of the parent is closed, because `tasker merge` refuses a stacked task.
- If a refine, or the `tasker review <issue> "<feedback>"` of the add-work rule, must change a file that another ticket changed and landed after this task started, the agent runs `tasker update-branch` first. Otherwise the new work uses the old text of the file, and the rebase at landing can conflict.
- If the task is in `reviewed` (a refine of step 8) or in `awaiting_work_review` (work for the add-work rule), `tasker update-branch` moves the task to `executed`. Then the agent runs `tasker verify`. If the verify passes, the task goes to `awaiting_work_review`, and the agent runs `tasker review`. If it fails, the agent follows [the verify-failure rule](#the-verify-failure-rule).
- The new review is a full review pass. It reports the open findings again as still open, and it can also report new findings.
- If the new review has findings, the task goes to `reviewed`, and the agent goes to step 6. Steps 6 to 8 then read, dismiss and refine all the open findings. If the agent must also add work (the task was in `awaiting_work_review`), the agent puts that work in the feedback of the refine of step 8. If the agent dismisses all the findings in step 7 instead, the task goes to `awaiting_work_review`, and the agent follows the add-work rule instead of going to step 9.
- If the new review has no findings, the task stays in `awaiting_work_review`, and `tasker refine` refuses to run. In that case, if the agent still must make the change, it follows [the add-work rule](#the-add-work-rule). Otherwise, the agent goes to step 9.
- If the task was in `reviewed`, the review before `tasker update-branch` and the review after it count as one loop of "Review findings".
- If the task is in `awaiting_plan_review` (a refine of step 4), `tasker update-branch` keeps the task in `awaiting_plan_review`. Then the agent runs the refine of step 4.
- If `tasker update-branch` reports a rebase conflict, the agent follows [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The agent does not copy that procedure.
- Before the orchestrator sends added work or an answer to an agent, the orchestrator reads the state of the task with `tasker show <issue>`. The orchestrator runs this command itself. It does not send a message to the agent only to learn the state, because a message to an agent that has ended starts the agent again (see "Terms" in "Quota"). The message with the work or the answer names the state that the orchestrator found. The state can change while a message waits, and the next command then depends on the new state.
- When the orchestrator edits an issue body while the agent of that ticket runs, the orchestrator sends all the edits together, before the next refine of the agent. On #117, edits that arrived one by one cost extra refines.

### The overlap rule

Several orchestrators can run at the same time, for example one for each milestone. Before a ticket starts, and each time an agent sends the list of files after `tasker approve`, the orchestrator compares the files with each task in flight of every milestone, not only of its own milestone. Before the start, the files are the files that the issue names. `tasker status` lists the tasks in flight, and `tasker show-plan <issue>` gives the files of each plan. `gh issue view <number> --json milestone` gives the milestone of a task.

For a shared file, the overlap rule sets a landing order. A ticket of an earlier milestone lands first. A ticket of the same milestone or of no milestone follows the bullets of [Land the work](#land-the-work). For a ticket of the milestone "Docs" and a ticket of a numbered milestone, [the Docs rule](#the-docs-rule) applies instead. Each orchestrator tells its own agent the landing order, also when its ticket lands first. For a stacked ticket and its parent, [the stacked-ticket rule](#the-stacked-ticket-rule) wins over the sentence "A ticket of an earlier milestone lands first".

### The Docs rule

This rule covers only a shared file between a ticket of the milestone "Docs" and a ticket of a numbered milestone. The orchestrator of each ticket still does the compare of the overlap rule. For these two tickets, the orchestrator of each ticket sets no landing order for the shared file. The orchestrator of each ticket sends no landing order to the other orchestrator. When the orchestrator of a ticket finds such a shared file, it tells its own agent that the Docs rule covers that file and that the fourth case of the stop rule does not apply to that file. If the agent already stopped under the fourth case for that file, this message is the answer, and the agent continues with step 4. For these two tickets, the Docs rule wins over the second sentence of the bullet "If the edit of a shared file is not required". The first sentence of that bullet still applies. Each ticket lands when it is ready. If the other ticket lands first, the agent of the ticket that lands second runs `tasker update-branch` as [the diff read](#the-diff-read) says. For these two tickets, these rules do not apply: the bullet "When the orchestrator sets the landing order", the wait rules, the bullet "When the issue of the earlier ticket is closed", the early update of [Review findings](#review-findings) and, for the shared file, the fourth case of [the stop rule](#the-stop-rule). The wait rules are the bullets of [Land the work](#land-the-work) from "The later agent does the steps of ..." to "If the orchestrator changes the landing order", [the hold rule](#the-hold-rule) and [the stuck-task rule](#the-stuck-task-rule). These bullets include the start-state bullet ("The start state is ..."), the bullet "To wait" and the bullet "Only the user changes a landing order of the overlap rule". The user decided this rule on 2026-10-15. For a stacked ticket and its parent, [the stacked-ticket rule](#the-stacked-ticket-rule) wins over this rule.

### The hold rule

This rule covers a landing order of the overlap rule when the start state is before `awaiting_work_review`, for example `awaiting_plan_review` or `executing`. The later orchestrator is the orchestrator of the later ticket. The later orchestrator tells the later agent not to start the wait of the "To wait" bullet. The later agent stops before `tasker accept` and reports to the later orchestrator. The later task stays in `awaiting_work_review`. When the hold starts, the later orchestrator sends one message with `SendMessage` to the orchestrator of the earlier ticket. The message asks for a report when the earlier task reaches `awaiting_work_review` or a later state, and when the issue of the earlier ticket closes. The orchestrator of the earlier ticket sends each of these reports to the later orchestrator with `SendMessage`. If a message of this rule fails, the orchestrator that sends it tells the user, as [the notice rule](#the-notice-rule) says for a failed message. The later orchestrator reads the state of the earlier task again with `tasker show <issue>` when the orchestrator of the earlier ticket or the user reports a change. It also reads it each time it reads the board after a landing ([Pick the tickets](#pick-the-tickets)). When the earlier task is in `awaiting_work_review` or a later state, the later orchestrator tells the later agent to start the wait. When the issue of the earlier ticket is closed, the later orchestrator tells the later agent to continue as the bullet "When the issue of the earlier ticket is closed" says. On #129, a wait of 60 minutes ran out while the earlier task #95 stayed in `awaiting_plan_review`.

### The stuck-task rule

This rule covers a landing order of the overlap rule, after the later agent reports that it stopped waiting. The orchestrator reads the state of the earlier task again with `tasker show <issue>`. If the state is the same as the start state, the orchestrator asks the user. If the start state is unknown, or if `tasker show <issue>` fails, the orchestrator also asks the user. The user can swap the landing order, postpone the earlier ticket, or tell the later agent to wait again. The orchestrator does not tell the later agent to wait again without the user. If the state changed, the orchestrator can tell the later agent to wait again, and it tells the user. If the new state is before `awaiting_work_review`, the hold rule applies instead of a new wait. The stuck-task rule does not cover a later agent under the hold rule, because that agent started no wait and has no 60-minute limit. On #101, the later agent waited two hours, in two waits of 60 minutes, for #34 of another milestone. During that time, #34 stayed in `awaiting_plan_review`.

## A failed CI run

This section gives the steps of the orchestrator after an agent reports a failed run in step 11 of [the CI wait](#the-ci-wait). The orchestrator does all the steps for each failed run that an agent reports. The repo has three priority labels: `priority: high`, `priority: medium` and `priority: low`. An issue of a failed CI run gets `priority: high`. The priority rule of [Pick the tickets](#pick-the-tickets) makes that issue start before the tickets with a lower priority.

1. File a new issue: `gh issue create --title "<title>" --body-file <file> --label "priority: high" --milestone "<milestone in progress>"`. The milestone in progress is the current milestone of "Pick the tickets". The body gives the run URL, the failed tests, the verdict and the evidence of the agent (the result of the rerun and of the local run). The body asks for the cause and a fix. It must not ask only for a retry or a longer timeout. If `gh issue create` fails, no issue exists. Tell the user. The agent keeps waiting, and the task stays in `landed`.
2. If the verdict is broken, the new issue blocks all further work. List the open issues: `gh issue list --state open --limit 1000 --json number,milestone`. An issue has not started when `tasker status` lists no task for it. Leave out the new issue itself. For each issue that has not started, in every milestone, run `gh issue edit <number> --add-blocked-by <new issue>`. Tell the user at once. If an edit fails, the issues already edited keep the link, and the rest have no link. Tell the user the numbers of the issues without a link.
3. If the verdict is flaky, the new issue blocks nothing.
4. Send the agent the number of the new issue. The bullet of "Land the work" that reads the state with `tasker show <issue>` first applies to this message.

The broken-test rule: a broken-test issue is the new issue of step 1 when the verdict is broken. The rule has two actors: the orchestrator that files the broken-test issue, and each other orchestrator. The notice rule defines the other orchestrators (see [the notice rule](#the-notice-rule)).

After step 2, the orchestrator that filed the broken-test issue sends a broken-test notice to each other orchestrator. It sends a notice for the verdict broken only. The notice gives the number of the broken-test issue. The orchestrator lists the other orchestrators with step 3 of the notice rule and sends the notice with `SendMessage`, as step 4 of the notice rule says. If the session list or a message fails, the orchestrator tells the user, as [the notice rule](#the-notice-rule) says for a failed message. When another orchestrator gets a broken-test notice, it keeps the number of the issue and follows the ban.

The ban: an orchestrator that knows of an open broken-test issue starts no ticket, except the broken-test issue itself. The orchestrator knows of the issue because it filed the issue or because it got the notice. Before each start, the orchestrator reads the state of the issue with `gh issue view <number> --json state -q .state`. The command prints `OPEN` for an open issue and `CLOSED` for a closed issue. When the output is `CLOSED`, the ban ends. If the command fails, the orchestrator starts no ticket and tells the user the command and the error.

The ban covers only the start of a ticket. A task in flight is not a start, so the ban does not stop it. The rule gives no steps for two broken-test issues open at the same time. A second failed run most likely has the same cause, and the open broken-test issue covers the fix.

## Quota

The quota belongs to the whole account. If a task stops in `quota_blocked`, the orchestrator and all the agents also have no tokens. No session can act until the quota resets. For this reason, the orchestrator must plan the resume before the quota runs out. The orchestrator does this with up to two cron jobs for each agent: a five-hour job and a seven-day job.

### Terms

- The reset time is the time when the quota of the account becomes available again. The quota resets at the exact reset time.
- A cron job (a job, on this page) is a prompt that the orchestrator schedules for a time. A one-shot job fires one time and then deletes itself. A job fires only while the orchestrator is idle. A job lives only in the session of the orchestrator.
- The five-hour job is the job for the five-hour reset time. The seven-day job is the job for the seven-day reset time. On this page, "an agent has a job", "has no job" and "an agent without a job" mean the five-hour job. A seven-day job alone does not count.
- An agent is running while it works on its turn. An agent has ended when its turn is over, for example after a tasker command stops in `quota_blocked` or `interrupted`. A message to an agent that has ended starts the agent again, and the agent keeps its context.
- `tasker show-quota` prints the last quota event of each repo as a JSON list. It has no `--json` flag. Each entry has `repo`, `provider`, `receivedAt` and `event`. `event` is the raw `rate_limit_event` of the assistant. For example:

  ```json
  [{"repo":"codeguru42/tasker","provider":"claude-code","receivedAt":"2026-10-12T00:23:23.713Z",
    "event":{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","rateLimitType":"five_hour","resetsAt":1791778800,
      "unifiedWindows":{"five_hour":{"utilization":0.39,"resetsAt":1791778800},"seven_day":{"utilization":0.39,"resetsAt":1792206000}}}}}]
  ```

- To read the reset time, the orchestrator takes the entry with the latest `receivedAt`, because all repos share the quota of the account. Then it reads `event.rate_limit_info.unifiedWindows.five_hour.resetsAt`. The value is in Unix seconds. The orchestrator converts it with `date -d @<seconds>`. For example:

  ```bash
  tasker show-quota | jq -r 'max_by(.receivedAt).event.rate_limit_info.unifiedWindows.five_hour.resetsAt'
  ```

- The orchestrator reads the seven-day reset time from the same entry, at `event.rate_limit_info.unifiedWindows.seven_day.resetsAt`. The value is in Unix seconds. For example:

  ```bash
  tasker show-quota | jq -r 'max_by(.receivedAt).event.rate_limit_info.unifiedWindows.seven_day.resetsAt'
  ```

- The event is the last one that tasker saw, so its reset time can be in the past. A reset time in the past, or no entry, means "no reset time yet". A seven-day reset time in the past, or no entry, means "no seven-day reset time yet".
- The assistant sends a quota event early in each run, also when the usage is low. As a result, a reset time is known soon after a run starts.
- If a task is in `quota_blocked`, `tasker show <issue>` prints the reset time of that stop in a line `resets at: <ISO time>`.

### The delay of each agent

Each running agent has a slot and a delay. The delay is the number of minutes between a reset time and the job of the agent for that reset. The delays prevent a resume of all the agents at the same time.

- There are 3 slots, one for each agent that can run at the same time. Slot 1 has a delay of 0 minutes. Slot 2 has a delay of 1 minute. Slot 3 has a delay of 2 minutes.
- If the reset time falls on :00 or :30, the delay of each slot is 1 minute longer: 1, 2 and 3 minutes. The cron scheduler can fire a one-shot job on :00 or :30 up to 90 seconds early. That fire is before the reset, so it has no tokens, and the job is then gone.
- The job time of a job is its reset time plus the delay of the agent. The reset time falls on a full 10 minutes, for example 11:30. So the job time is a full minute.
- If the reset time is not a full minute, the orchestrator must round the job time up to the next full minute.
- When the orchestrator starts an agent, the orchestrator must give the agent the free slot with the lowest number.
- When the orchestrator schedules a job for an agent, a five-hour job or a seven-day job, the agent keeps the same slot.
- The agent keeps its slot until the orchestrator frees it, as "Delete the job" says. Then the next agent that starts takes the slot.

### Schedule a job when an agent starts

1. When the orchestrator starts an agent, the orchestrator must run `tasker show-quota` and read the reset time, as "Terms" says. The orchestrator also applies [the seven-day rule](#the-seven-day-rule).
2. If there is a reset time, the orchestrator must schedule a one-shot five-hour job for the job time of that agent. The orchestrator also follows the schedule-all rule in "When there is no reset time yet".
3. If there is no reset time yet, the orchestrator starts the agent without a job and tells the agent that it has no job. For example, there is no reset time before the first run in the project. "When there is no reset time yet" gives the next steps.

- When the orchestrator schedules a job, the prompt of the job must name the issue and the agent. The prompt must tell the orchestrator to do the steps of "When the job fires".
- The orchestrator must keep the id of each job of a ticket. A ticket has at most one five-hour job and one seven-day job.
- For a seven-day job, the orchestrator must keep the seven-day reset time of the job with its id.
- Each id, and the time stored with it, lives until its one-shot job fires or until CronDelete deletes it. A one-shot job deletes itself when it fires. After that, the ticket has no job of that kind.
- A job that has not fired is a job whose id still lives.

### The seven-day rule

Each time the orchestrator runs `tasker show-quota` and reads the reset time, as "Terms" says, the orchestrator also reads the seven-day reset time and applies this rule. This holds whether or not a five-hour reset time exists.

- If the seven-day reset time is in the future, the orchestrator schedules a seven-day job for each agent that has none, except an agent that the schedule-all rule leaves out (see [When there is no reset time yet](#when-there-is-no-reset-time-yet)), however far away the reset is. The job is a one-shot job for the job time of the seven-day reset. The delay and the rounding come from [The delay of each agent](#the-delay-of-each-agent).
- The reason: after the seven-day quota runs out, no session has tokens for a later read. As a result, the orchestrator schedules the job at the first read that gives the time.
- The prompt of the job names the issue, the agent and the window `seven_day`. The prompt tells the orchestrator to do the steps of "When the job fires".
- If the ticket has a seven-day job that has not fired, and the seven-day reset time did not change, the orchestrator schedules no second one. To compare, the orchestrator uses the seven-day reset time that it stored with the job id.
- If the seven-day reset time changed, the orchestrator deletes the old seven-day job with CronDelete. Then the orchestrator schedules the new one.

The rule has three failure cases:

- If `tasker show-quota` fails, or the `jq` read of `seven_day` gives `null`, there is no seven-day reset time yet. No seven-day job changes. If `tasker show-quota` itself fails, the orchestrator tells the user the command and the error.
- If CronCreate of a seven-day job fails, the orchestrator tells the user the tool and the error. The agent has no seven-day job. The next read tries again, because the rule schedules a seven-day job for each agent that has none.
- If CronDelete of the old seven-day job fails, the orchestrator tells the user the tool and the error. The old job and its id stay. The orchestrator does not schedule the new job at that read. The next read tries again, because the time still differs.

### When there is no reset time yet

- Each agent must tell the orchestrator each time a tasker run ends. If an agent has no job, the agent must also tell the orchestrator each time a tasker run starts. The runs are `tasker plan`, `tasker refine`, `tasker execute`, `tasker review` and `tasker resume`.
- If the orchestrator gets a run-start report and the ticket already has a job that has not fired, the orchestrator does not schedule another job.
- While any agent has no job and the schedule-all rule does not leave it out, the orchestrator runs `tasker show-quota` and reads the reset time each time an agent without a job reports that a tasker run starts. The orchestrator also does this each time any agent reports that a tasker run ends. If there is no reset time, nothing else changes.
- The schedule-all rule: each time the orchestrator runs `tasker show-quota` and reads a reset time, as "Terms" says, the orchestrator also schedules a job for each agent without a job. The rule leaves out an agent whose last job fired in a case of "When the job fires" that scheduled no new job for that agent. The orchestrator schedules no job for a left-out agent under the schedule-all rule or under the seven-day rule. A fire of either job, in a case that schedules no new job, leaves the agent out. If a case of "When the job fires" says that the orchestrator schedules the next job, the agent of the fired job is no longer left out. This applies from the start of the paragraph after the list. As a result, that paragraph schedules the next five-hour job, and the seven-day rule covers the agent at the read of that paragraph. The agent stays left out until the orchestrator starts it as "Schedule a job when an agent starts" says, or until the end condition above. A message to the agent does not end this.
- When the orchestrator schedules the job of an agent that had no job, the orchestrator tells the agent that it has a job. If the agent gets this message, the agent stops the run-start reports. The agent keeps the run-end reports.
- If the orchestrator must tell an agent that it has a job or that it has no job, and the agent is running, the orchestrator tells the agent at once. If the agent has ended, the orchestrator does not send a message only for this. The orchestrator puts this information in the next message that it sends to that agent, for example the resume message.
- If the quota runs out before the orchestrator schedules a job, no job resumes the agent. In that case, the orchestrator tells the user when the orchestrator has tokens again.

### When the job fires

When a job of a ticket fires, a five-hour job or a seven-day job, the orchestrator runs `tasker status --issue <issue>` and `tasker show <issue>`. The steps are the same for both jobs. Then exactly one of these cases applies:

- If the task is in `quota_blocked` and the `resets at:` line is missing or in the past, the orchestrator sends the agent a resume message with SendMessage. Then the orchestrator schedules the next job, as the paragraph after this list says. The task stays in `quota_blocked` until the agent runs `tasker resume`.
- If the task is in `quota_blocked` and its `resets at:` time is in the future, the stop is in a longer window, for example `seven_day`. The orchestrator does not resume the agent. The orchestrator tells the user. The job of this case is the seven-day job for the job time of that `resets at:` time, and the orchestrator schedules it one time. For a seven-day job of the ticket that has not fired, [the seven-day rule](#the-seven-day-rule) applies: the same time means no new job, and another time means delete and replace. The seven-day job of the ticket for that `resets at:` time counts as the job that this case schedules, also when the orchestrator keeps an existing job. As a result, this case never leaves the agent out of the schedule-all rule. The task stays in `quota_blocked`. After such a stop, the user can get more quota, for example with a new plan of the account. When the user reports more quota, the orchestrator sends the agent a resume message at once, as in the first case, and does not wait for the job. tasker does not hold the task until its `resets at:` time, so `tasker resume` works before that time. Then the orchestrator schedules the next job, as the paragraph after this list says. The seven-day job stays. That paragraph reads both reset times with `tasker show-quota`.
- If the task is in `interrupted`, the orchestrator sends the agent a resume message, as in the first case. Then the orchestrator schedules the next job, as the paragraph after this list says. The task stays in `interrupted` until the agent runs `tasker resume`.
- If the task is in `awaiting_quota_approval`, the quota use passed the approval threshold. The orchestrator tells the user and does not resume the task. The orchestrator does not run `tasker approve-credits` (see "Limits"). The orchestrator does not schedule another job for that task. The task stays in `awaiting_quota_approval` until the user decides.
- If the task is in `failed` or `landed`, the orchestrator reads the last report of the agent. In `landed`, the agent does [the CI wait](#the-ci-wait). If that report does not say that the agent stopped, the orchestrator schedules the next job, as the paragraph after this list says. The agent keeps its slot. A report of a failed run (step 11 of the CI wait) is not a stop, so the agent keeps its slot also then. If the agent stopped, the orchestrator schedules no new job and tells the user. The orchestrator frees the slot only in a case of "Delete the job".
- If the task is in `finishing`, `cleanup_failed`, `finished` or `cancelled`, or `tasker status --issue <issue>` lists no task, the orchestrator schedules no new job. The orchestrator frees the slot of the agent, as "Delete the job" says. By default, `tasker status` lists only the tasks in flight, so it does not list a `finished` or `cancelled` task.
- If the task is in a state that no other case names, the task did not stop for the quota. For example, the task is in `planning`, `executing`, `awaiting_plan_review` or `reviewed`. The orchestrator schedules the next job, as the paragraph after this list says. The agent keeps its slot.

If a case says that the orchestrator schedules the next job, the orchestrator first applies the resume rule. The resume rule: if the case sent no resume message, the agent has ended (see "Terms"), and the agent does not wait for an answer or a next step from the orchestrator, the orchestrator sends the agent a resume message, as in the first case. The agent waits for the orchestrator after a stop, a question or a request for the next step, until the orchestrator sends the answer or the next step. The reason: the quota can end the session of the agent between two `tasker` commands, and then no other case resumes the agent. Then the orchestrator runs `tasker show-quota` and reads the reset time, as "Terms" says. The orchestrator also applies [the seven-day rule](#the-seven-day-rule). If there is a reset time, the orchestrator schedules the next five-hour job for the job time of that agent, but only if the ticket has no five-hour job that has not fired. The orchestrator also follows the schedule-all rule in "When there is no reset time yet". If there is no reset time yet, the orchestrator tells the agent that it has no job. Then "When there is no reset time yet" applies to that agent.

### What the agent does

- If a tasker command of the agent stops in `quota_blocked` or `interrupted`, the agent ends its turn. The agent does not wait, sleep or schedule anything. The task stays in that state.
- If the orchestrator tells the agent to resume, the agent runs `tasker status --issue <issue>`.
- If the task is in `quota_blocked` or `interrupted`, the agent runs `tasker resume <issue>`. The task goes back to the state before the run that stopped, and tasker runs the same command again. After that command, the task reaches the state that "Run one ticket" gives for its step. Then the agent continues with the next step of "Run one ticket".
- If the task is in `awaiting_quota_approval`, the agent does not run `tasker resume` or `tasker approve-credits`. The agent reports to the orchestrator.
- If the task is in a different state, the agent does not run `tasker resume`. The agent continues from that state.

### Delete the job

- When the agent reports that it ran `tasker finish`, for example in its final report, the orchestrator must delete each job of that ticket whose id still lives with CronDelete. A task in `landed` keeps its jobs and its slot until then, unless another bullet of this section applies, for example after a stop in the CI wait. A report of a failed run is not a stop, so the jobs stay until `tasker finish`.
- When the orchestrator cancels an agent, the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- If an agent stops for another reason and the orchestrator does not start it again, the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- When the user defers a ticket that has a task in flight (see [the defer rule](#the-defer-rule)), the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- In each of these cases, the orchestrator frees the slot of the agent. This also applies when the agent has no job. The schedule-all rule also leaves out this agent until the orchestrator starts it again, as "Schedule a job when an agent starts" says.
- If CronDelete fails, the orchestrator tells the user the tool and the error. The job stays. When the job fires, the case of "When the job fires" for its state applies. An example is the case of a finished task, which schedules nothing.

### Do not use these

- The orchestrator must not use `/loop` or ScheduleWakeup for the wait. One wake-up waits at most one hour. A wake-up before the reset has no tokens to act.
- An agent cannot make a job, because the agent does not have the tool for that. Only the orchestrator schedules jobs.

## The handoff

A long-running orchestrator is the orchestrator of a milestone that stays open while other sessions add issues to it, for example "Docs" (see [docs/dev/planning.md](planning.md)). In a handoff, the old orchestrator gives its work to a new orchestrator in a new session.

The rules of this section cover only a long-running orchestrator. An orchestrator of a numbered milestone stops when the Todo column of its milestone is empty, as [Pick the tickets](#pick-the-tickets) says. The rules of this section do not cover it.

A handoff starts in one of two ways:

- The old orchestrator sees that about 20% of its context is used. Then it starts the handoff itself and tells the user.
- The user asks for a handoff. The user can ask at any time.

After the start, the old orchestrator does these steps:

1. Start no new ticket.
2. Wait until each task in flight lands. For each landing, do the usual steps: delete the jobs (see [Delete the job](#delete-the-job)), do [the re-read rule](#the-re-read-rule) and do [the notice rule](#the-notice-rule). The reason: a job lives only in the session of the orchestrator (see [Terms](#terms)). If a task is still in flight at the handoff, nobody resumes it after a quota stop.
3. Write the handoff file `$HOME/Documents/tasker/handoff/<date>-<role>.md`, for example `2026-10-15-docs-orchestrator.md`. If a file with that name exists, add a number, for example `2026-10-15-docs-orchestrator-2.md`.
4. Give the path of the file in the reply to the user.

The old orchestrator puts these items in the handoff file:

- The prompt for the new session, in a code block. The prompt names the milestone, the session name and the first step: the start of the re-read rule. The prompt also names the docs to read and the state at the handoff. Its last step is to watch the board for new issues.
- The state at the handoff: the tasks in flight of other milestones that share a file with an open issue of the milestone, the parked tasks and the other sessions.
- What the old orchestrator did, and each decision of the user from its session.
- A table of the open issues of the milestone, with the columns issue, topic, blockers and files.

The old orchestrator puts no rule in the handoff file. The rules stay in the docs, and the prompt points to them.

The user pastes the prompt as the first message of the new session. The user names the session `orchestrator-<milestone>`, for example `orchestrator-docs`, as [the notice rule](#the-notice-rule) says. The new orchestrator then starts with the re-read rule.

## Limits

These limits apply to the orchestrator and to the agents, except where a bullet or a rule names one actor.

- The agent reads the output of a task only with the `tasker show` commands, for example `tasker show`, `tasker show-plan`, `tasker show-verify` and `tasker show-review`. The agent never reads a transcript or a log file of tasker directly (see [the own-worktree rule](#the-own-worktree-rule)).
- To read the commits of a task branch, the agent runs `git fetch tasker` in the local clone of the orchestrator. If the clone has no `tasker` remote, the agent adds it as [the own-worktree rule](#the-own-worktree-rule) says. Then the agent runs `git log` or `git show` on `tasker/<task branch>`. For a diff of the task, the agent uses the command with three dots of [the diff read](#the-diff-read). If a command fails, the agent stops and reports the error to the orchestrator. Nothing changes.
- A new worktree has no `node_modules`, and the local clone can have none. The task worktree lives long, and an update can change `package-lock.json`. Before a test on the local machine that runs the code of the repo, the agent runs `npm ci` in the task worktree when it has no `node_modules`. The agent also runs `npm ci` when `package-lock.json` differs from the copy of the last install. Use the copy of the commit check: `L=$(git rev-parse --git-path npm-ci-lock); cmp -s "$L" package-lock.json || { npm ci && cp package-lock.json "$L"; }`.
- The agent uses only the issue, the files of the repo, its own tests on the local machine and the answers of the orchestrator as sources. If the issue does not give a detail that the work needs, the agent asks the orchestrator. Then the agent waits for the answer, as [the answer-wait rule](#the-answer-wait-rule) says. Before `tasker approve`, [the stop rule](#the-stop-rule) and [the design-gap rule](#the-design-gap-rule) give the steps and say who answers. After `tasker approve`, the orchestrator asks the user. When the agent asks the orchestrator a question, the agent gives the options, with its suggestion for each.
- The agent changes only its own issue. On GitHub issues, labels and the project board, the comment of step 11 of "Run one ticket" is the only write of the agent. The agent does not edit an issue body, a label or the project board. This rule does not cover the git commands and the `tasker` commands of the steps on this page, for example `tasker merge` and the delete of the task branch in step 10. On GitHub Actions, the rerun of step 9 of the CI wait (`gh run rerun <run id> --failed`) is the only write of the agent.
- If tasker stops for a quota, follow "Quota". Never run `tasker approve-credits`.
- Do not run `npm link` or a global install from a task worktree. The global `tasker` runs the tickets, and the install replaces it.
- Only the orchestrator writes memory, so that two agents do not write the same file. Agents report what they learn to the orchestrator in their final report (see [the final report](#the-final-report)). For this reason, an agent does not run a skill that writes memory, for example `/session-review`.
- The orchestrator and each agent load the simple-english skill and follow the simple-english bullet of [Docs](rules.md#docs) of rules.md.
- The folder of an agent is `$HOME/Documents/tasker/agents/<session name>`. The session name is the name of the session of the agent from "The prompt of an agent", for example `codeguru42-tasker-43`. The task worktree of [the own-worktree rule](#the-own-worktree-rule) is `../tasker-worktrees/<session name>`, relative to the root of the local clone of the orchestrator. That path is a folder with the session name in the folder `tasker-worktrees`, next to the local clone of the orchestrator. The task worktree is not in the folder of the agent and not in the clone. The orchestrator makes the folder of the agent before the agent starts, as "The prompt of an agent" says. The agent keeps each other file that it writes in the folder of the agent, for example the feedback files and the notes. Two agents that run at the same time keep their files in different folders. Before an agent runs `tasker refine` or `tasker review <issue> "<feedback>"` with feedback text from a file, the agent makes sure that the file holds the text for its own ticket. If two agents use the same file name, the refine or the review of one ticket can send the text of another ticket. The folder of the agent stays after the work. The agent removes only the task worktree, as the own-worktree rule says.
- Do not use `pkill` or `killall`. To stop a process that it started, the orchestrator or the agent uses `kill` with the process id that it saved. `pkill` matches by name, so it can stop a process of another session of the same user.
- Never print a credential, for example an access token, a password or a key. If a command gives a credential, store its output in a shell variable, for example `token="$(gh auth token --hostname github.com --user <account>)"`. Do not print the variable. To make sure that the command succeeded, use its exit code or a test of the variable that prints nothing, for example `[ -n "$token" ]`. Pass the variable to later commands, for example `GH_TOKEN="$token" gh api user`. Do not put the credential itself in a command line, a file, a log, a feedback text or a comment. Never print the environment, for example with `env`, `printenv` or `set`, because it can hold a credential, for example the access token in `GH_TOKEN`. The assistant tools start a new shell for each tool call, and a shell variable lives only in its own shell. As a result, set the variable and use it in the same tool call. Never print the full command line of the sandbox, for example with `ps -o args`. The sandbox of a `claude` run is a `bwrap` process. Its command line holds a user name and a password of the local proxy of that run. On 2026-10-14, an agent printed them in its tool output with `ps`. To find a bind or a path in the command line, search it for only that item, and print only the match. For example, `ps -o args= -p <pid> | grep -o -F -- '<path>'` prints only `<path>`, and only when the command line holds it. This rule does not cover the code of tasker, which already keeps the access token out of its errors and logs.

### The issue-link rule

In each reply to the user, the orchestrator writes each mention of an issue as a markdown link. The link target is the page of the issue in its tracker. The link text is the issue key, in this form:

- For an issue of this repo, the text is the short form `#<N>`, for example `[#159](https://github.com/codeguru42/tasker/issues/159)`.
- For an issue of another repo, the text is the full key, for example `[owner/repo#12](https://github.com/owner/repo/issues/12)`.

The rule covers the replies of the orchestrator to the user only. The text on GitHub keeps the plain key, because GitHub links it. The messages to an agent and to another orchestrator keep the plain key, because a session reads them as text. A key inside a code span or a code block stays as it is, for example a command line with an issue key.

The reason: the user opens the issue by hand. On GitHub, `#159` is a link, but in the terminal it is plain text.

### The own-worktree rule

The orchestrator and the agents must not read the files that tasker keeps in its data folder. Never read, search or run anything in a worktree of tasker, also not with a read-only command such as `grep`. Do not change the repo or the worktrees of tasker by hand. Only `tasker` commands change them. The one exception to the read is a fetch through the read-only `tasker` remote, which reads the clone of tasker and changes nothing there. The worktrees of tasker are under `<dataRoot>/repos/<owner>-<repo>/worktrees/`.

To read or run the code of a task, the agent uses its task worktree. The task worktree is the one worktree of an agent for its task. It is a worktree of the local clone of the orchestrator, in the folder that the folder bullet of [Limits](#limits) gives for the task worktree. It is on a local branch with the same name as the task branch. The task branch is on the `branch:` line of `tasker show <issue>`.

- Make: the agent makes the task worktree one time, after `tasker start` in step 2 of "Run one ticket" or in the comeback rule. If the local clone has no `tasker` remote, add it as steps 1 and 2 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md#procedure) say. Then run `git fetch tasker`. If the fetch fails, stop and report. Nothing changes. Then run `git worktree add -b <task branch> <path> tasker/<task branch>`. If it fails for a reason other than the branch-exists case, stop and report. No worktree exists.
- The path: the agent keeps `<path>` from the make until the remove at the end. The agent keeps `<path>` as an absolute path, because git resolves a relative path against the current folder of each command. Each later step uses that path. This includes the `<path>` of steps 6, 18 and 19 of rebase-conflicts.md.
- Use: each step that reads or runs the code of the task uses the task worktree, after the update rule.
- The branch-exists case: the make fails with `fatal: a branch named '<task branch>' already exists` and exit 255. Git makes no folder. The local branch can hold commits that tasker does not hold, for example after a stop of the manual fix. Do these steps before the first update:
  1. Read `<hash>` with `git rev-parse --verify tasker/<task branch>`. Then run `git merge-base --is-ancestor <task branch> <hash>`.
  2. If the exit code is 1, the local branch holds a commit that tasker does not hold, or tasker rewrote the task branch after the last update, for example with a rebase or an autosquash. The step cannot tell the two apart. Stop and report. The branch and each worktree of the branch stay.
  3. If the exit code is neither 0 nor 1, or a command fails, stop and report.
  4. If the exit code is 0, run `git worktree list --porcelain`. If an entry has the line `branch refs/heads/<task branch>`, use the `worktree <path>` line of that entry as the task worktree.
  5. If no entry has that line, run `git worktree add <path> <task branch>`, with no `-b` and no `--detach`. For a branch that no worktree holds, this makes a worktree on the branch.
  6. Then do the update rule.
- The remove: the agent removes the task worktree only at the end of its work. The end is after step 10 of "Run one ticket", after `tasker abort`, or when the orchestrator tells the agent to stop. Run `git worktree remove <path>`. Do not use `--force`. If the remove fails, stop and report, as step 19 of rebase-conflicts.md says. The worktree and the local task branch stay. Then delete the local task branch with `git branch -D <task branch>`. If the delete fails, stop and report. The worktree is gone, and the local task branch stays. The agent reports to the orchestrator, and the orchestrator reports to the user.
- Exceptions to the remove: if the agent followed rebase-conflicts.md, steps 18 to 20 of that page do the remove. The agent does not do it again. While the local-commit rule holds, the worktree and the local branch stay. They also stay after a step of rebase-conflicts.md stops. The final report names each path that stays.
- Worktree commands change no task. The task keeps its state.

### The update rule

tasker changes the task branch in its own clone, for example with `tasker execute`, `tasker refine` and `tasker update-branch`. The task worktree does not follow by itself. Before each use, the agent does these steps in the task worktree:

1. Run `git fetch tasker`.
2. Read `<hash>` with `git rev-parse --verify tasker/<task branch>`. The hash lives only for this update.
3. Run `git status --porcelain`. If it prints a line, stop and report. Nothing changes. Test the output, because the command exits with 0 also when it prints lines. Ignored files such as `node_modules/` do not print.
4. Run `git reset --keep <hash>`.

`git reset --keep` moves the branch for a fast-forward. It also moves a branch that a rebase of tasker rewrote, where `git merge --ff-only` fails with exit 128. For a change in a file that the update changes, `--keep` refuses with exit 128 (`error: Entry '<file>' not uptodate. Cannot merge.`), and the branch and the change stay. Step 3 already stops for each uncommitted change. As a result, no update runs over one. Do not use `--hard`, because it deletes changes that are not committed. If a step fails, the step that uses the worktree gives the failure path. The commands of the update rule change no task.

### The local-commit rule

The local task branch holds no commit of its own, with two exceptions. The first is the manual fix, from its step 2 to step 11 of rebase-conflicts.md. The second is rebase-conflicts.md after a rebase conflict of `tasker update-branch`, from step 7 (the rebase) to step 11 (`--take-remote`). In that time, the agent does not run the update rule. If the agent stops in that time, for example after a failed push at step 10, the worktree and the local branch stay. After step 11, tasker holds the local tip (`<taken>`), and the rule ends. The manual fix and rebase-conflicts.md link to this rule.

### The shared-clone rule

Every orchestrator and every agent on the machine run git in one local clone. As a result, a git command of any session, for example `git fetch`, can run between two commands of a step. On 2026-10-15, `git worktree list` in the local clone listed the worktrees of the agents of other orchestrator sessions. A remote-tracking ref is the copy of a branch of a remote in the local clone, for example `origin/<branch>` or `tasker/<branch>`. If a step uses a remote-tracking ref in more than one command, the step reads the full hash of the ref one time, with `git rev-parse --verify <ref>`. Each later command of the step uses that hash, not the ref. For example, if step 10 of "Run one ticket" read `origin/<task branch>` for the check and again for the delete, a fetch between the two reads can move the ref, and the delete then acts on a commit that the check did not see. Use `--verify`, because plain `git rev-parse` also prints the name on its output when it fails. If `git rev-parse --verify` fails, for example because the ref does not exist, it exits with 128 and prints `fatal: Needed a single revision`. The step then stops, as the failure cases of that step say. If a step uses a remote-tracking ref in only one command, the step needs no hash read. The update rule reads `tasker/<task branch>` one time and resets to that hash.

### The doc-read rule

The local `main` can be older than `origin/main`. The local clone of the orchestrator stays on `main`, because each other branch is checked out in a worktree. `git merge --ff-only origin/main` fast-forwards the branch that is checked out, not `main`. Before the orchestrator or an agent reads a doc, it runs `git fetch origin` in the local clone. Then it runs `git symbolic-ref --short HEAD` in the local clone. If the output is not `main`, it does not run the merge. An agent then stops and reports the branch name that it found to the orchestrator. Otherwise, it runs `git merge --ff-only origin/main`. If a command fails, an agent stops and reports the error to the orchestrator. For the orchestrator, [the re-read rule](#the-re-read-rule) gives the failure path and the hash for the merge.

### The address rule

The agent sends each message to the orchestrator with `SendMessage` and `to: "main"`. The agent puts `"main"` in the `to` option of `SendMessage`, not in the text of the message. The session name of the orchestrator, for example `orchestrator-m8`, is not the address. The rule covers each message that the agent sends while it works. Examples are the run-start and run-end reports of "When there is no reset time yet" in "Quota", the reports of the stop cases, the list of files after `tasker approve` and the questions. The rule does not cover the final report (see [the final report](#the-final-report)). The agent of #153 learned this rule on 2026-10-15.

### The answer-wait rule

When the agent must wait for an answer or a next step from the orchestrator, the agent sends its report or its question with `SendMessage`, as [the address rule](#the-address-rule) says. Then the agent gives its final answer, which ends its turn. The final answer is not the final report (see [the final report](#the-final-report)). The agent does not wait in a loop. The message of the orchestrator with the answer or the next step starts the agent again. The reason: a message to an agent that has ended starts the agent again, and the agent keeps its context (see "Terms" in "Quota"). On #153, the agent waited about 25 minutes in a loop for an answer, then ended its turn with a stop report. The message with the answer started the agent again, and the agent went on with its work. The rule also covers each stop after which the agent runs no other `tasker` command until the orchestrator tells it the next step. While the agent waits, the task keeps its state. For a resume message during the wait, see the resume rule in "When the job fires". The rule does not cover a wait that reads a state, for example the "To wait" bullet of "Land the work" or the wait bullet of [the command rules](#the-command-rules).
