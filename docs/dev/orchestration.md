# Orchestration

This page gives the rules for an orchestrator. The orchestrator is the assistant session that picks tickets, starts one agent for each ticket, moves the cards, sets the landing order and writes memory.

A ticket is an issue on the project board. An agent is an assistant session that the orchestrator starts for one ticket. The agent runs the steps of ["Run one ticket"](run-one-ticket.md#run-one-ticket) for that ticket. The user is the person who runs the orchestrator. A task is the record that tasker keeps for one ticket. tasker moves the task from state to state, for example from `awaiting_plan_review` to `approved`.

Memory is the files where an assistant keeps notes between sessions. Memory is not in the repo.

tasker also starts its own sessions for plan, execute and review. They run in a worktree of the tasker clone. They are not agents and they do not run the steps on [the orchestration pages](orchestration.md).

The orchestrator and its agents run tasker from the local clone of the orchestrator. For one ticket, the agent of that ticket is the operator that [docs/dev/rebase-conflicts.md](rebase-conflicts.md) names.

Every `tasker` command on [the orchestration pages](orchestration.md) is the installed `tasker`: the `tasker` command on the PATH from a global install. It is not the tasker that this repo builds. For this reason, `skills/tasker/SKILL.md` does not list its commands. See the `npm link` bullet under Limits.

The orchestration pages are `docs/dev/orchestration.md` and the pages of this list, "The pages":

- [docs/dev/pick-the-tickets.md](pick-the-tickets.md): "Pick the tickets", the stacking rule, the stacked-ticket rule, the parent-hold rule, the link offer, the defer rule and "The prompt of an agent".
- [docs/dev/doc-reads.md](doc-reads.md): the re-read rule, the notice rule and the doc-read rule.
- [docs/dev/run-one-ticket.md](run-one-ticket.md): "Run one ticket", the final report, the comeback rule, the base rule, the add-work rule, the diff read and the measure rule.
- [docs/dev/plan-review.md](plan-review.md): the repo-files rule, the fact test, the issue check, the stop rule, the design-gap rule and the quote check.
- [docs/dev/tasker-commands.md](tasker-commands.md): the plain-form rule, the tool-block rule, the command rules, the facts of the installed tasker and the run times.

### The CI wait

After `tasker merge` in step 9 of [Run one ticket](run-one-ticket.md#run-one-ticket), the agent of the ticket waits for the CI runs of the landed commit. `tasker verify` runs on the local machine, and the `Check` workflow on GitHub can still fail. For example, the local Node version can differ from the Node version of CI. The runs that count are the runs of the `Check` workflow on `main` for the landed commit, because they test the merged result. The agent runs each command of the CI wait in the local clone of the orchestrator. During the whole CI wait, the task stays in `landed`. The step numbers in the list below name the steps of the CI wait, not the steps of "Run one ticket". The agent does these steps:

1. Right after `tasker merge`, run `git fetch --multiple tasker origin`. The `tasker` remote is the read-only remote of [the diff read](run-one-ticket.md#the-diff-read). Then run `git rev-parse tasker/<task branch>`. The task branch is on the `branch:` line of `tasker show <issue>`. `tasker merge` lands the work as a fast-forward, so the tip of the task branch is the landed commit. The command prints the landed commit as a full hash of 40 characters. Use the full hash in the next steps, because `gh run list --commit` finds no run for a short hash.
2. Make sure that `main` contains the landed commit: `git merge-base --is-ancestor <landed commit> origin/main`. The check also passes when other tickets landed on top of the landed commit after `tasker merge`. If the exit code is not 0, `origin/main` does not contain the work of the ticket. In that case, report this to the orchestrator and stop.
3. Find the run with this command: `timeout 300 bash -c 'while :; do n=$(gh run list --workflow Check --branch main --commit <landed commit> --json databaseId -q length) || exit 2; [ "$n" != 0 ] && exit 0; sleep 30; done'`. GitHub can start the run some seconds after the push, so the list can be empty at first. The command reads the list every 30 seconds for at most 5 minutes. It exits with 0 when the list has a run. If it exits with 124, no run showed after 5 minutes. In that case, report to the orchestrator that no run showed, and stop. If it exits with 2, `gh run list` failed. In that case, report the error to the orchestrator and stop.
4. Run `gh run list --workflow Check --branch main --commit <landed commit> --json databaseId,status,conclusion`. If the command fails, report the error to the orchestrator and stop. The run id of each run is its `databaseId`. The list can have more than one run, because GitHub can record one push twice and start a run for each record. Take the runs in the order of the list. For each run, do step 5 of the CI wait. When step 5 or step 6 finds that the run passed, do step 5 for the next run of the list.
5. Wait for the run: `timeout 580 gh run watch <run id> --exit-status`. A `Check` run takes about 2 minutes, but it can take longer than one tool call of the agent. The agent cannot run a foreground `sleep`, so it waits with `timeout`. Exit code 0 means that the run passed. Exit code 124 means that the run is still in progress. In that case, run the same command again. The 30-minute limit counts from the first `gh run watch` of the CI wait, for all the runs of the list together. If a run is not complete when the 30 minutes end, report to the orchestrator and stop. Any other exit code means that the run failed, or that `gh` failed. In that case, go to step 6 of the CI wait.
6. Run `gh run view <run id> --json status,conclusion,url,jobs`. If the command fails, report the error to the orchestrator and stop. If `status` is `completed` and `conclusion` is `success`, the run passed. If `status` is not `completed`, `gh run watch` failed and the run is still in progress. In that case, do step 5 of the CI wait again. If `status` is `completed` and `conclusion` is not `success`, the run failed. In that case, go to step 7 of the CI wait.
7. If a run failed, do not fix the failure, and do not wait for the other runs of the list. Read the names of the failed jobs and steps from `jobs` (the entries with the `conclusion` `failure`). Read the names of the failed tests from `gh run view <run id> --log-failed`. With gh 2.101.0, `--log-failed` labels each line `UNKNOWN STEP`, so the step names come from `jobs`. If `gh run view --log-failed` fails, write down the error for the report of step 11 of the CI wait, and go to step 8 of the CI wait.
8. Run the failed tests on the local machine, on the landed commit, in the task worktree. Do not change `main`. Do [the update rule](#the-update-rule) in the task worktree. Then compare `git rev-parse --verify HEAD` with the full hash of step 1 of the CI wait. After `tasker merge`, the tip of the task branch is the landed commit, as step 1 says. If a step of the update rule fails, or HEAD is not the landed commit, write down the error, skip the local run, and go to step 9 of the CI wait. Otherwise, run `node --version`. Then run `npm ci` as the npm ci bullet of "Limits" says. Then run `npm test -- <test file> -t "<test name>"` for each failed test. The report gives the Node version, because the Node version of CI can differ. The local run is evidence only, and a failure in this step does not stop the CI wait. If `npm ci` or the test command cannot run, write down the error, and go to step 9 of the CI wait. The commands of this step change no task.
9. Rerun the failed jobs of the run one time: `gh run rerun <run id> --failed`. Do not rerun a second time. Exit code 0 means that GitHub accepted the rerun. Any other exit code means that the rerun did not start, and nothing changed on GitHub. With gh 2.101.0, the command exits with 0 when GitHub accepts the rerun. It exits with 1 when GitHub refuses it, for example while the run is still running, or when the run does not exist. If the rerun did not start, write down the error, and go to step 10 of the CI wait. If the rerun started, wait for it as steps 5 and 6 of the CI wait do. A new 30-minute limit counts from the first `gh run watch` of the rerun. When step 5 or step 6 finds that the rerun passed, or step 6 finds that it failed, go to step 10 of the CI wait, not to step 7. If the rerun is not complete when the 30 minutes end, go to step 10 of the CI wait. If `gh run view` fails in step 6, that is a stop, as step 6 says.
10. Decide the verdict. The verdict is flaky when the rerun passes. The verdict is broken for every other result: the rerun fails again, the rerun does not start, or the rerun does not complete in its 30 minutes. The local run of step 8 of the CI wait is evidence for the report. It does not change the verdict.
11. Report to the orchestrator: the run URL (`url`), the names of the failed jobs, steps and tests, and the verdict. The report also gives the result of the rerun: passed, failed again, did not start (with its error), or did not complete in 30 minutes. It also gives the result of the local run with the Node version, and each error of steps 7 to 9 of the CI wait. Then wait for the answer of the orchestrator, as [the answer-wait rule](#the-answer-wait-rule) says. While the agent waits, the task stays in `landed`. This wait is not a stop. The steps of the orchestrator are in "A failed CI run".
12. When the orchestrator answers with the number of the new issue, run `tasker finish`. The task goes to `finished`, and the issue closes. Then do steps 10 and 11 of "Run one ticket". The comment of step 11 also names the failed run, the verdict and the new issue.

The CI wait passes only when each run of the list passed in step 5 or step 6 of the CI wait. A rerun that passes in step 9 of the CI wait does not make the CI wait pass. The agent still does steps 10 to 12 of the CI wait. Other agents can land on `main` during the wait. The agent waits only for the runs of its own landed commit, not for a later run on `main`. If a git command of the CI wait fails, the agent reports the error to the orchestrator and stops. To stop means that the agent does not run `tasker finish` and does not do steps 10 and 11 of "Run one ticket". The agent runs no other `tasker` command until the orchestrator tells it the next step. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. In each case where the agent stops, the task stays in `landed`. The wait of step 11 of the CI wait is not a stop. If the agent gets a resume message while the task is in `landed` (see "When the job fires" and "What the agent does" in "Quota"), the rule depends on what the agent did before. If the agent did not run `gh run rerun` yet, it does the CI wait again from step 1 of the CI wait. If it ran `gh run rerun` and did not send the report of step 11 yet, it does not run `gh run rerun` again. If the rerun did not start, it goes to step 10 of the CI wait with the result "did not start". Otherwise, it waits for the rerun as step 9 says, with a new 30-minute limit from its first `gh run watch` after the resume. Then it goes on with step 10. If it sent the report of step 11, it does not do the CI wait again. It waits for the answer of the orchestrator, as [the answer-wait rule](#the-answer-wait-rule) says. If it got the number of the new issue, it goes on with step 12 of the CI wait.

### The verify-failure rule

This rule applies to each `tasker verify` on [the orchestration pages](orchestration.md), in step 5 of [Run one ticket](run-one-ticket.md#run-one-ticket), in step 9 and after `tasker update-branch` in "Land the work". If `tasker verify` fails, the task goes to `failed`. In `failed`, `tasker show <issue>` lists `refine`, `update-branch`, `retry` and `abort`. A fix of a failed `tasker verify` does not count as a loop of "Review findings". The limits of this rule count each refine and each retry after the last `tasker verify` that passed, for any cause. If the task is in `failed` after a command other than `tasker verify` or `tasker retry`, this rule does not apply. In that case, the agent follows the paragraph after this list, which starts "If a command fails". The agent reads the output of `tasker verify` and finds the cause of the failure. Then the agent does the first case of this list that applies:

- If the failure comes from the code and the agent already sent the refine of the next case, the agent stops. The agent reports to the orchestrator that it stopped, and the task stays in `failed`. Then the agent waits as [the answer-wait rule](#the-answer-wait-rule) says.
- If the failure comes from the code, the agent runs one `tasker refine <issue> "<feedback>"`. `tasker refine` accepts a task in `failed` only when the task has a plan revision. The feedback gives the cause of the failure. It tells the plan to go through the commits of the task branch one at a time. It also tells the plan to fix each broken commit in that commit, not in a new commit on top. More than one commit can be broken, so the refine fixes all of them. The broken-commit steps give the git commands for this feedback. The agent adds [the repo-files rule](plan-review.md#the-repo-files-rule) to the feedback text. The task goes to `awaiting_plan_review`. Then the agent does steps 3 and 4 for the new plan, and steps 5 to 8 again, starting with `tasker approve`. As the other choice, the agent does not refine. The agent stops for a manual fix and reports to the orchestrator that it stopped. The task stays in `failed`. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. If the orchestrator then tells the agent to do the manual fix, the agent follows the broken-commit steps. For a failure from the code, the agent does not run `tasker retry`, because the same check fails again on the same code. The agent also does not run `tasker retry --resume-execute`. That flag resumes execute with no new feedback, so the plan does not get the cause of the failure.
- If the agent already ran `tasker retry`, the agent stops and reports to the orchestrator that it stopped. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. If the `tasker verify` that `tasker retry` ran failed, the task stays in `failed`. If `tasker retry` itself failed, the task stays in the state that `tasker show <issue>` prints.
- If the failure does not come from the code, the agent runs `tasker retry <issue>` one time. For example, a test failed one time for a reason outside the code. `tasker retry` accepts a task in `failed`. By default, `tasker retry` runs `tasker verify` again on the same code. If that verify passes, the agent runs `tasker show <issue>`, and the task is in the state that it prints. Then the agent runs the command that comes after `tasker verify` in the place that ran it. In each place on [the orchestration pages](orchestration.md), that command is `tasker review`.

If a command fails or the task is in another state, run `tasker show <issue>` and follow the commands that it prints.

To find the next command, use these:

- `tasker --help` lists the commands.
- `tasker <command> --help` shows the states where the command is valid.
- `tasker show <issue>` shows the state of the task and the next commands.

### The broken-commit steps

These steps give the git commands for a failure from the code in the verify-failure rule. A broken commit is an implementation commit that fails `npm run check`, or the tip of the task branch when it fails `npm run check`. The tip has no next commit, so it must pass, whatever its prefix. The cause commit of a broken commit is the commit that adds the cause of its failure. It is the broken commit itself, an earlier broken commit, or an earlier commit that the check skips, for example a `test:` commit that adds a test configuration. It is never under the last commit that passed the check, or under the base commit. The Commits section of [docs/dev/rules.md](rules.md) defines an implementation commit and gives the rule. The fix of a broken commit goes into its cause commit, not into a new commit on top. The steps do not change the limits or the cases of the verify-failure rule.

The base commit is the commit under the first commit of the task branch. `tasker update-branch` moves the task branch onto a newer base, so the base commit changes. For this reason, each [commit check](#the-commit-check) of the agent finds the base commit again. The refine feedback gives the base commit of the last commit check, and the session steps use the base commit of the feedback. The one exception is the refine of step 4 of [Run one ticket](run-one-ticket.md#run-one-ticket) after a `tasker update-branch`: there the base commit comes from `git merge-base` directly, not from a commit check.

In the refine of the verify-failure rule, the agent first does the commit check on the local task branch, in the task worktree. If the commit check finds no broken commit, each implementation commit and the tip pass, so the failure does not come from the code. The agent does not send the refine. It follows the cases of the verify-failure rule for a failure that does not come from the code. Otherwise, the feedback names each broken commit of the check, by its hash and its subject. The commit check names each broken commit, but not its cause commit. A named `feat:`, `fix:` or `refactor:` commit is not the cause when its failure comes from an earlier commit that the check skips. For this reason, the feedback also names the commits that the check skipped under each broken commit, back to the last commit that passed the check or to the base commit. These commits and the earlier broken commits of the list are the other candidates for the cause commit. It gives the base commit of the check. If the agent runs `tasker update-branch` after it sends the refine and before `tasker approve`, the agent does not run the commit check again. The hashes and the base commit in the feedback are then out of date. The session finds the broken commits again with its own commit check, so the names in the feedback only describe the failure. In the refine of step 4, the agent gives the new base commit: the agent runs `git fetch --multiple tasker origin`, then `git merge-base tasker/<task branch> origin/<base branch>` with the base of [the base rule](run-one-ticket.md#the-base-rule). If a command fails, the agent stops and reports to the orchestrator, and the task stays in `awaiting_plan_review`. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. This refine of step 4 is part of the same fix, not a new refine of the verify-failure rule, so the limits of that rule do not change. Then the agent continues as usual. `tasker verify` runs after `tasker approve` and `tasker execute`, as the steps of "Run one ticket" say. If that `tasker verify` fails, the agent follows the verify-failure rule, which looks for broken commits again. If it passes, the agent continues as usual. The feedback tells the session (the execute session that tasker starts) to fix the cause commits with these steps:

1. Do [the session check](#the-session-check). The result is the list of broken commits, oldest first. If the session check stops, stop and report, as the session check says.
2. If the list is empty, the session ends. Each commit passes, whatever repaired it, for example an earlier fix or `tasker update-branch`.
3. On the task branch, take the oldest commit on the list. In the first round, find its position. The position of a commit is the number that `git rev-list --count <base commit>..<commit>` prints (1 for the first commit after the base commit). A later commit has a higher position. The hashes change after each autosquash, so the session compares positions, not hashes. If the command fails, stop and report. The task branch stays as it was. In later rounds, keep the position that step 5 found. Then read the failure of the oldest commit and find its cause commit, as the definition above says. Stage the fix and run `git commit --fixup=<cause commit>`. This also applies when the cause commit is the tip or a `test:` commit. If the command fails, stop and report. The staged fix stays, and git makes no fixup commit.
4. At once, run `GIT_SEQUENCE_EDITOR=: git rebase --autosquash <base commit>` on the task branch. `GIT_SEQUENCE_EDITOR=:` makes sure that the rebase does not wait for an editor. With git 2.47.3, the `--autosquash` flag works without `-i`, and the rebase does not depend on the `rebase.autoSquash` configuration. The rebase squashes the fixup commit into the commit that it names. As a result, the fix is part of the history before the session looks at the next commit. If the rebase fails, for example with a conflict, run `git rebase --abort`, then stop and report. The branch goes back to its state before the rebase, with the fixup commit on top.
5. Do step 1 again. A commit that is not on the new list needs no fix. If the new list is empty, go to step 2. Otherwise, find the position of the oldest commit on the new list with the command of step 3, and keep it for the next round. If the oldest commit on the new list is not later on the branch than the oldest commit of the list before, the session stops and reports. The fixes so far stay in their commits. Otherwise, do steps 2 to 5 again. The position test ends the session after at most as many rounds as the task branch has commits after the base commit.

If the session stops, the execute run fails. The agent then follows the verify-failure rule as it already says. For a task in `failed` after a command other than `tasker verify` or `tasker retry`, that rule sends the agent to the paragraph that starts "If a command fails".

After the refine, the agent continues as the verify-failure rule says. When the `tasker verify` after the fix passes, the agent does the commit check before `tasker review`, unless the agent ran `tasker update-branch` after the failed `tasker verify`. This check runs only because a `tasker verify` failed before the fix. When `tasker verify` passes and no failed `tasker verify` came before it, the agent runs no commit check. After `tasker update-branch`, the agent runs no commit check until `tasker verify` fails. `tasker verify` runs after `tasker update-branch` as step 9 and "Land the work" say. If the commit check fails, the agent stops and reports the list of broken commits to the orchestrator. The agent does not run another refine, because the verify-failure rule permits one refine. The task stays in `awaiting_work_review`. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says.

The pushed-branch rule covers a task whose task branch was pushed to `origin` at step 9 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). After that push, a fixup commit and an autosquash rebase change the task branch of tasker, and `origin` keeps the pushed commits. The fix of a broken commit under the tip still goes into its cause commit. On #201, the next `tasker update-branch` worked again only after the old task branch on `origin` was deleted with a lease. The agent does the rule after step 11 of that page. It does the rule before each later `tasker update-branch` of the task, until step 21 of that page ends. The `tasker update-branch <issue> --take-remote` of step 11 is not a command of the rule. The rule applies to each change of the pushed commits, whatever its cause.

The agent of the ticket does each step in the local clone of the orchestrator, on `main`. No step runs in the tasker clone or in a worktree of tasker. The git commands change no task, for example a task in `awaiting_work_review`, `reviewed`, `awaiting_plan_review` or `failed`. At each stop, the agent runs no `tasker update-branch`. The agent reports to the orchestrator and waits as [the answer-wait rule](#the-answer-wait-rule) says. The task keeps its state. The agent does these steps:

1. Run `git fetch --multiple tasker origin`. If the fetch fails, stop. Nothing changes.
2. Run `git ls-remote --exit-code --heads origin refs/heads/<task branch>`. [Step 10 of "Run one ticket"](run-one-ticket.md#run-one-ticket) gives its exit codes. If the exit code is 2, `origin` has no task branch. Go to step 7. If the exit code is 0, go on with step 3. If the exit code is another code, stop. Nothing changes.
3. Read `<commit>` with `git rev-parse --verify origin/<task branch>`. Read `<current>` with `git rev-parse --verify tasker/<task branch>`. The next steps use these hashes, as [the shared-clone rule](#the-shared-clone-rule) says. If a read fails, stop. Nothing changes.
4. Run `git merge-base --is-ancestor <commit> <current>`. If the exit code is 0, the task branch of tasker contains the pushed commits. Go to step 7. If the exit code is 1, tasker changed the pushed commits. Go on with step 5. If the exit code is another code, stop. Nothing changes.
5. Make sure that `<commit>` is the same hash as the `<taken>` of the last step 11 of rebase-conflicts.md. If that step recorded no `<taken>`, stop. If the two hashes differ, stop. Nothing changes.
6. Delete the task branch on `origin` with a lease: `git push --force-with-lease=refs/heads/<task branch>:<commit> origin --delete <task branch>`. If the push fails, for any reason, stop. [Step 10 of "Run one ticket"](run-one-ticket.md#run-one-ticket) gives two examples: a stale lease, and a branch that is already gone. For another failure, the task branch on `origin` can still exist. The agent holds no `<deleted>`. If the push succeeds, keep `<commit>` as `<deleted>`. `<deleted>` lives until step 21 of rebase-conflicts.md ends, or until the next push of step 9 of that page. That push ends the old `<deleted>`, and the agent holds no `<deleted>` until a later delete of this rule.
7. Run the `tasker update-branch` that the step that started the rule asked for, as [the plain-form rule](tasker-commands.md#the-plain-form-rule) says. That step gives the state of the task after the command.

Right after step 6, `origin` has no task branch. While the agent holds `<deleted>`, [the take check](rebase-conflicts.md#the-take-check) in step 17 of rebase-conflicts.md uses it. If nobody pushed the task branch again, step 21 of that page finds exit code 2 in [step 10 of "Run one ticket"](run-one-ticket.md#run-one-ticket), so that step is complete. If the agent holds no `<deleted>`, steps 15 to 21 of that page run as they are written.

### The session check

The session check runs the rebase of the commit check directly on the task branch. The check commands only run the tests and change no commit. The last paragraph of [the commit check](#the-commit-check) gives the facts of this rebase during and after its run. At the end, HEAD is on the task branch. If the rebase stops for another reason, `git rebase --abort` puts the task branch back at its tip, with HEAD on the task branch.

If the session stops in the middle of the rebase, the worktree stays in the rebase. Step 2 covers this case when the session goes on.

The session does these steps in its worktree, on the task branch, with the base commit of the feedback:

1. Do steps 5, 6 and 8 of [the commit check](#the-commit-check): the `git rebase --exec` command, the notes and `git rebase --continue`, and the tip check. Step 2 takes the place of step 7 of the commit check. If the rebase exits with 0, the result is the list of broken commits, oldest first. The list can be empty. Then no rebase is in progress, so step 2 does nothing, and step 3 does not stop. If the rebase stops for another reason, or another error occurs, for example the rebase does not start or a command of step 8 of the commit check cannot run, go on with step 2.
2. If a rebase is still in progress after step 1, run `git rebase --abort`. A rebase is in progress when the folder `$(git rev-parse --git-path rebase-merge)` exists. If the abort fails, stop and report. The worktree stays in the rebase, and the task branch stays at its tip.
3. If step 1 ended with such a stop or error, stop and report. The task branch stays at its tip, with HEAD on the task branch.

### The manual fix

The agent does the manual fix only when the orchestrator tells it to, after the stop for a manual fix in the verify-failure rule. The agent never changes the tasker clone (the clone of this repo that tasker keeps, see [docs/dev/rebase-conflicts.md](rebase-conflicts.md)) or its worktrees by hand (see [the own-worktree rule](#the-own-worktree-rule)). After each stop of the manual fix, the agent waits as [the answer-wait rule](#the-answer-wait-rule) says. The agent does these steps:

1. Do steps 1 to 6 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The agent works in the task worktree. Step 6 of that page uses it. [The local-commit rule](#the-local-commit-rule) holds from step 2 of this list. If a step fails, stop and report to the orchestrator. The task stays in `failed`.
2. Do the commit check on the local `<task branch>` to find the broken commits and the base commit. If the check finds no broken commit, report this to the orchestrator. The orchestrator gives the next step. If the check stops with an error, stop and report to the orchestrator. In both cases, the worktree and the local task branch stay, and the task stays in `failed`.
3. In the worktree, do the session steps of [the broken-commit steps](#the-broken-commit-steps) on the local `<task branch>`, with the base commit of the last commit check. If the session steps stop, stop and report to the orchestrator. The worktree and the local task branch stay, and the task stays in `failed`.
4. Do the commit check on the local `<task branch>` again. This check also covers step 8 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md), because it checks the tip. If the check lists a broken commit, fix the cause commits of the listed commits one time with step 3, with the base commit of this check. Then do the commit check one more time. If that check still lists a broken commit, stop and report the list to the orchestrator. If a check stops with an error, stop and report to the orchestrator. In each of these cases, the worktree and the local task branch stay, and the task stays in `failed`. Nothing reached tasker yet.
5. Do steps 9 to 21 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md): the push to `origin`, `tasker update-branch <issue> --take-remote`, the next commands, and the cleanup after `tasker finish`.

### The commit check

The commit check makes sure that each implementation commit and the tip of the task branch pass `npm run check`. It gives the list of broken commits and the base commit. The agent does it in the task worktree, on the local task branch:

1. Do steps 1 to 4 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The clone gets the read-only `tasker` remote, and the agent reads the base branch. If a step fails, stop and report to the orchestrator. Nothing changes.
2. Run `git fetch --multiple tasker origin`. If the fetch fails, stop and report to the orchestrator. Nothing changes.
3. Work in the task worktree, on the local task branch. This step makes no worktree. Outside the manual fix, do [the update rule](#the-update-rule). In the manual fix, the local-commit rule holds, so run no update. If a step fails, stop and report to the orchestrator. Nothing changes.
4. In the task worktree, find the base commit: `git merge-base HEAD origin/<base branch>` with the base of [the base rule](run-one-ticket.md#the-base-rule). If the command fails, stop and report to the orchestrator.
5. Run `git rebase --exec 'L=$(git rev-parse --git-path npm-ci-lock); { cmp -s "$L" package-lock.json || { npm ci && cp package-lock.json "$L"; }; } && case "$(git log -1 --format=%s)" in feat:*|fix:*|refactor:*) npm run check ;; esac' <base commit>`. The command runs after each commit. It runs `npm ci` when `package-lock.json` differs from the copy of the last install. It keeps that copy in the git folder of the worktree (`git rev-parse --git-path npm-ci-lock`), so `git status` stays clean. Then it runs `npm run check` after each implementation commit. The rebase skips `test:` and `docs:` commits. If `npm ci` fails, the command fails after that commit, and step 6 notes that commit. Because the branch already starts on the base commit, the rebase keeps the same commits.
6. If the rebase stops and prints `warning: execution failed`, the command failed after the commit that `git log -1 --format='%h %s'` names. Note that commit as a broken commit. Then run `git rebase --continue`, and the rebase checks the next commits. Do this step again each time the rebase stops this way. A commit after a broken commit can fail only because of the earlier commit. The session fixes the oldest broken commit first and then runs the check again, so a fix of the earlier commit can also remove a later commit from the list.
7. If the rebase stops for another reason, run `git rebase --abort`. The worktree goes back to the branch at the old tip. Then stop and report the error to the orchestrator. If the abort fails, the ref of the branch is still at the old tip, and the worktree stays in the rebase. Stop and report the output of `git -C <path> status`.
8. When the rebase exits with 0, it kept the same commits, and the worktree is at the tip. If the tip is not an implementation commit, run `npm run check` one time in the worktree. The worktree already has the packages of the tip, because the rebase ran the command after the tip too. If `npm run check` fails, note the tip as a broken commit.
9. The commit check passes when it noted no broken commit. Otherwise, the check fails and gives the list of broken commits and the base commit of step 4. The step that ran the check gives the next step.

After each stop of the commit check, the agent waits as [the answer-wait rule](#the-answer-wait-rule) says.

During the rebase, HEAD is detached inside the task worktree, and the branch ref stays at the old tip. When the rebase ends, it keeps the same commits, so the branch is at the same tip.

## Review findings

- One loop is one `tasker review` and the work on its findings. The agent runs at most 5 review loops.
- The same-patch rule: this rule covers a task in `awaiting_work_review` when the agent of the ticket runs `tasker update-branch`. The agent reads two patch ids in the local clone of the orchestrator, with the remotes of [the diff read](run-one-ticket.md#the-diff-read). A patch id is the first field of the output of `git patch-id --stable` for the diff of the task branch against its base. The output has the form `<patch id> 0000000000000000000000000000000000000000`. The first patch id: while the task is in `awaiting_work_review`, right before `tasker update-branch`, the agent runs `git fetch --multiple tasker origin`. Then it runs `set -o pipefail; git diff origin/<base branch>...tasker/<task branch> | git patch-id --stable` with the base of [the base rule](run-one-ticket.md#the-base-rule). This case covers a stacked task whose parent branch moved after the start of the task, for example after a rewrite or a rebase of the parent. In this case, the first patch id uses the start base of the task in place of `tasker/<parent branch>`. The reason: the parent ref moved, so the three-dot diff against it holds the old commits of the parent, and the patch id covers more than the work of the task. On #182, the parent #172 rewrote its commits in a fix round after the start of #182. The start base of a task is the commit that the task branch pointed to right after `tasker start`. For a stacked task, it is the tip of the parent branch at that time. The agent reads it right after `tasker start` with the commands of the base-commit hint of [All tickets](first-refine.md#all-tickets). The agent runs these commands in the local clone of the orchestrator. The start base lives until the next read of the start base. The agent reads the start base again only after a `tasker update-branch` that moved the task branch with no rebase conflict and keeps the task stacked. The task stays stacked when the `base branch:` line of `tasker show <issue>` still has the form `refs/heads/<parent branch>`. For this read, right after the update, the agent runs `git fetch tasker` and then `git merge-base tasker/<task branch> tasker/<parent branch>` in the local clone of the orchestrator. After a `tasker update-branch` that reports a rebase conflict, the start base of the last read stays. The same-patch case and the case of step 7 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md#procedure) use the start base of the last read. On #262, the agent ran `tasker update-branch` one time before the parent landed. The right start base was then the tip of the parent under the task branch, not the commit of the start. If a command of a read of the start base fails, the agent holds no start base. For the same-patch case, that is a failed command of this rule, as the bullet "The review after `tasker update-branch` counts as a loop" says. The second patch id: after `tasker update-branch`, while the task is in `executed` and before `tasker verify`, the agent runs the same two commands again. The three dots diff against the merge base. As a result, the first patch id uses the old base, and the second patch id uses the new base. The agent must run the fetch before each read.
- The same-patch review is the first `tasker review` after that `tasker update-branch` when the two patch ids are the same. A same-patch review does not count as a loop, also when it has findings. For this one review, the same-patch rule wins over the loop definition of the first bullet. If the same-patch review has no findings, the task stays in `awaiting_work_review`. If it has findings, the task goes to `reviewed`, and the agent works on them with steps 6 to 8 of ["Run one ticket"](run-one-ticket.md#run-one-ticket). After the 5th loop, the bullet "After the 5th loop" wins. If a real finding of a same-patch review is still open, the agent stops as that bullet says. If the agent dismisses all the findings in step 7, the task goes to `awaiting_work_review`. In each case, the agent then continues as the place that ran `tasker update-branch` says. Work can follow the same-patch review, for example the refine of step 8 or the work of [the add-work rule](run-one-ticket.md#the-add-work-rule). Then the next `tasker review` counts as a loop.
- The review after `tasker update-branch` counts as a loop in each of these cases. The two patch ids differ, for example because the rebase solved a conflict. `tasker update-branch` reported a rebase conflict. An output of `git patch-id` is empty, because an empty output gives no patch id. The agent did not read the first patch id. A command of this rule fails, for any reason. A failed command of this rule changes nothing in the repo or in the worktrees of tasker, and the task keeps its state. The work changes between `tasker update-branch` and the review, for example with a refine after a failed `tasker verify`.
- The limit of 5 loops counts all other reviews, as before. For a task in `reviewed`, the bullet of "Land the work" that starts "If the task was in `reviewed`" gives the count. On #92, `main` moved two times during the review loops. Each `tasker update-branch` from `awaiting_work_review` forced a new review, and each review counted as a loop. As a result, 2 of the 5 loops had no change to the work.
- The early update: this rule covers a task in `reviewed` when the earlier ticket of a landing order shares a file with the task. Before each refine of step 8, the later agent reads the state of the issue of the earlier ticket one time with `gh issue view <number> --json state -q .state`. If the state is `CLOSED` and the later agent did not run `tasker update-branch` after the close, it runs `tasker update-branch` first. This rule adds to the bullet of "Land the work" that starts "If a refine, or the `tasker review <issue> "<feedback>"` of the add-work rule, must change a file". The review right after this update and the review before it count as one loop, as the bullet of "Land the work" that starts "If the task was in `reviewed`" says. The review after the refine of step 8 is the next loop. So the early update costs no extra loop. If the later agent ran the early update after the close, it runs no second `tasker update-branch` when it reaches the bullet "When the issue of the earlier ticket is closed" of "Land the work", as that bullet says. Without the early update, the update runs later from `awaiting_work_review`, and there a review after a rebase conflict counts as a loop. On #129, such a review was loop 5, so a finding in it got no fix.
- The no-loop-left rule: this rule covers a task in `awaiting_work_review` after the 5th loop, when a step needs `tasker update-branch`, for any reason. The agent reports to the orchestrator before `tasker update-branch`. The agent runs no `tasker update-branch` and no `tasker accept`. The task stays in `awaiting_work_review`. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. The orchestrator asks the user. This rule wins over each step that runs `tasker update-branch` from `awaiting_work_review`, for example step 9 and [the diff read](run-one-ticket.md#the-diff-read), and the bullet "When the issue of the earlier ticket is closed" of "Land the work". A same-patch review costs no loop (the same-patch rule of this section). For example, if the patch ids differ or the rebase has a conflict, the review counts as a loop (the bullet "The review after `tasker update-branch` counts as a loop"). As a result, after the 5th loop, such a review is over the limit.
- After the 5th loop, if a real finding is still open, or the diff read finds work, the agent stops and reports to the orchestrator. The agent runs no refine, no `tasker review <issue> "<feedback>"` and no `tasker accept`. The task keeps its state, for example `reviewed` or `awaiting_work_review`. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says. The orchestrator reports to the user.
- On the 5th loop, the agent dismisses cosmetic findings with a reason.
- If a finding is an edge case outside the issue, and it is not a security gap and not a bug in the core path, the agent dismisses it in step 7. The core path is the main use that the issue describes. The reason says that the edge case is outside the issue. The agent lists the finding in its final report, and the ticket does not grow. A refactor or duplication finding is not such an edge case.
- If a finding contradicts an exact rule of the issue, the agent dismisses it in step 7. The reason quotes that rule of the issue.
- The security report: if the agent dismisses a finding in step 7 because the finding contradicts the issue, and the finding points to a possible security gap, the agent also reports the gap to the orchestrator in the same step. A security gap is a way to harm the user or the system. For example, text of a third party, such as an issue body, reaches a prompt as an instruction. The report gives the finding, the rule of the issue and the risk. The orchestrator tells the user, because the decision belongs to the user. Then the agent stops before its next `tasker approve` or `tasker accept` and waits for the answer, as [the quote check](plan-review.md#the-quote-check) and [the answer-wait rule](#the-answer-wait-rule) say. If the user decides to close the gap, the orchestrator first posts a comment that starts with `## Change of scope`, as for the fifth case of [the stop rule](plan-review.md#the-stop-rule). Then the agent does [the issue check](plan-review.md#the-issue-check) again and copies the text of the comment, as [the stop rule](plan-review.md#the-stop-rule) says. After that, the agent adds the work with the step that fits the state of the task: the refine of step 4 or step 8, or the add-work rule. If the report comes in the 5th loop, a decision to close the gap counts as a real finding that is still open, and the second bullet of this section applies. The security report does not cover a security gap in a plan before `tasker approve`. The third case of the stop rule covers that gap.
- A refactor or duplication finding is not cosmetic. The agent refines a refactor finding in the ticket that added the code. The agent fixes a duplication finding (the same code or text in more than one place) at once, in the ticket that adds the duplicated code. The finding comes from a review or from [the diff read](run-one-ticket.md#the-diff-read). The agent fixes a finding from a review with the refine of step 8, and a finding from the diff read with the add-work rule. The agent does not dismiss a real duplication finding.
- When the agent sends a fix in the refine text, it writes "apply everywhere it fits". Otherwise the next review finds the same problem in other places.

The missed-finding rule: a review or the diff read can miss a refactor or duplication finding. When someone finds it later, the fix goes to the first place of this list that applies:

1. The ticket that adds the code, inside the 5 review loops of this section. While that ticket is open, the orchestrator does not move the fix into another ticket. On #71, on 2026-10-13, the user replaced the extra loop after the last loop with "up to 5 loops, then report".
2. If that ticket already landed, a ticket that changes the same code. For a ticket in progress, the orchestrator tells its agent to add the fix to its next refine. For a ticket that has not started, the orchestrator edits its issue body.
3. If no such ticket exists, the orchestrator files a new issue to fix it.

## Land the work

The steps to land a ticket are in ["Run one ticket"](run-one-ticket.md#run-one-ticket). This section gives the rules between tickets.

- After `tasker approve`, each agent sends the orchestrator the list of files that the plan changes. `tasker refine` and `tasker approve` also print a warning when another task in progress changes the same file.
- If the edit of a shared file is not required, the agent removes it in a refine. If it is required, the orchestrator sets the landing order.
- When the orchestrator sets the landing order, it tells the later agent which ticket must land first. The earlier ticket is the ticket that must land first. The later agent is the agent of the ticket that lands after it. The earlier agent is the agent of the earlier ticket.
- The later agent does the steps of "Run one ticket" up to `tasker accept` in step 9. Before it runs `tasker accept`, it waits until the issue of the earlier ticket is closed. While the later agent waits, the task is in `awaiting_work_review`.
- The start state is the state of the earlier task before a wait on a landing order of the overlap rule. Before the orchestrator tells the later agent to wait, it reads this state with `tasker show <issue>`. The orchestrator reads it before each wait, also before a new wait. If the earlier task is far from landing, for example in `awaiting_plan_review`, the orchestrator tells the user. If the start state is before `awaiting_work_review`, [the hold rule](#the-hold-rule) also applies. If `tasker show <issue>` fails, the orchestrator tells the user, and the start state is unknown.
- To wait, the later agent reads the state of the issue of the earlier ticket one time: `gh issue view <number> --json state -q .state`. If the state is `OPEN`, the later agent reads it again every 30 seconds until it is `CLOSED`. The later agent waits at most 60 minutes from the first read.
- If the state is still `OPEN` 60 minutes after the first read, the later agent stops waiting. To stop waiting means that the later agent stops reading the issue state.
- If the earlier agent stops before the issue of the earlier ticket closes, the orchestrator tells the later agent to stop waiting. Then the later agent stops waiting. For example, the earlier agent stops after its last loop of "Review findings". Or it reports a rebase conflict that it does not fix (see [docs/dev/rebase-conflicts.md](rebase-conflicts.md)). Or it stops in the CI wait, for example when no run showed.
- This bullet covers two tickets of the orchestrator. If the earlier agent stops to wait for a decision of the user, the orchestrator changes the landing order at once. It changes the order as the bullet "If the orchestrator changes the landing order" says. It does not let the later agent wait until the end of its 60 minutes. In one milestone, two waits of 60 minutes were lost this way. For a landing order of the overlap rule, the bullet "Only the user changes a landing order of the overlap rule" applies.
- If the later agent stops waiting, for either reason, it does not run `tasker accept`. The task stays in `awaiting_work_review`. The later agent reports to the orchestrator that it stopped waiting, and why. Then the later agent runs no other `tasker` command until the orchestrator tells it the next step. The later agent waits as [the answer-wait rule](#the-answer-wait-rule) says.
- After the later agent reports that it stopped waiting, the orchestrator decides the next step and tells the user. For a landing order between two tickets of the orchestrator, the orchestrator tells the later agent to wait again. Or it changes the landing order so that the later ticket lands first. For a landing order of the overlap rule, [the stuck-task rule](#the-stuck-task-rule) gives the next step.
- Only the user changes a landing order of the overlap rule, because the earlier ticket belongs to another orchestrator. If the user swaps the order, the user tells each orchestrator the new order. Each orchestrator tells its own agent, as the overlap rule says. Then the two tickets swap roles, as the sentences of the bullet "If the orchestrator changes the landing order" from "Then the two tickets swap roles." say. The first sentence of that bullet, where the orchestrator tells both agents, covers only two tickets of the orchestrator. If the user postpones the earlier ticket, the user does this through the orchestrator of that ticket. That orchestrator does the steps of [the defer rule](pick-the-tickets.md#the-defer-rule). The task of the earlier ticket becomes a parked task, and the paragraph of [the defer rule](pick-the-tickets.md#the-defer-rule) that starts "A parked task stays in flight" applies. The user tells the orchestrator of the later ticket that the earlier ticket is postponed, as in the swap case. That orchestrator then tells the later agent to continue step 9 of "Run one ticket" from `tasker accept`. Another orchestrator can relay a change of a landing order from the user. Then the orchestrator that gets the relay asks its own user to confirm the change before it tells its agent, as [A decision of the user](working-with-the-user.md#a-decision-of-the-user) says. Until the user confirms, the old order stays: the landing order before the relay. The reason: a message from another session is not an answer of the user. The relayed order can also differ from an answer that the user gave before to the orchestrator that gets the relay. When the user confirms, the orchestrator that gets the relay tells its agent the new order, as the overlap rule says. The orchestrator that gets the relay also tells the other orchestrator with `SendMessage` that its user confirmed. The orchestrator that relays the change does not tell its own agent the new order until the other orchestrator reports that its user confirmed. Otherwise the two agents follow opposite orders for a time. If the user of the orchestrator that gets the relay rejects the change, that orchestrator tells the other orchestrator with `SendMessage`. Then the old order stays for both orchestrators.
- If the orchestrator tells the later agent to wait again, or to start the wait under the hold rule, the later agent starts a new wait as in the "To wait" bullet. The new limit is 60 minutes from the new first read. The task stays in `awaiting_work_review`.
- If the orchestrator changes the landing order, it tells both agents the new order. Then the two tickets swap roles. The ticket that was the later ticket becomes the earlier ticket, and its agent becomes the earlier agent. The ticket that was the earlier ticket becomes the later ticket, and its agent becomes the later agent. From then on, "earlier" and "later" name the roles in the new landing order. If the new earlier agent waits before `tasker accept`, its task is in `awaiting_work_review`, and it continues step 9 of "Run one ticket" from `tasker accept`. Otherwise, it continues its steps of "Run one ticket", and it does not wait before `tasker accept`. Step 9 gives the state after each command. Before the new later agent runs `tasker accept` in step 9, it follows the wait rules of this section, from the bullet "The later agent does the steps of ...". The orchestrator changes a landing order only between two of its own tickets. For a landing order of the overlap rule, the bullet "Only the user changes a landing order of the overlap rule" applies.
- When the issue of the earlier ticket is closed, the later agent runs `tasker update-branch`. The task goes from `awaiting_work_review` to `executed`. For a stacked task, this `tasker update-branch` moves the task onto the base of the parent if the update has no conflict, and the task is then no longer stacked. The later agent then reads the `base branch:` line again, as [the base rule](run-one-ticket.md#the-base-rule) says. Then the later agent continues step 9 of "Run one ticket" from its `tasker verify`. If `tasker verify` fails, the later agent follows [the verify-failure rule](#the-verify-failure-rule). If the later agent already ran `tasker update-branch` after the earlier ticket landed, the sentences above do not apply. The later agent runs no second `tasker update-branch` and continues step 9 of "Run one ticket" from `tasker accept`. The `git merge-base --is-ancestor origin/<base branch> tasker/<task branch>` of [the diff read](run-one-ticket.md#the-diff-read) right before `tasker accept` finds a later move of the base branch. On 2026-10-17, the agent of #248 updated its branch from `executed` after its parent #252 landed, and then asked the orchestrator about a second update.
- The later agent of a stacked task never runs `tasker merge` before the issue of the parent is closed, because `tasker merge` refuses a stacked task.
- If a refine, or the `tasker review <issue> "<feedback>"` of the add-work rule, must change a file that another ticket changed and landed after this task started, the agent runs `tasker update-branch` first. Otherwise the new work uses the old text of the file, and the rebase at landing can conflict.
- If the task is in `reviewed` (a refine of step 8) or in `awaiting_work_review` (work for the add-work rule), `tasker update-branch` moves the task to `executed`. Then the agent runs `tasker verify`. If the verify passes, the task goes to `awaiting_work_review`, and the agent runs `tasker review`. If it fails, the agent follows [the verify-failure rule](#the-verify-failure-rule).
- The new review is a full review pass. It reports the open findings again as still open, and it can also report new findings.
- If the new review has findings, the task goes to `reviewed`, and the agent goes to step 6. Steps 6 to 8 then read, dismiss and refine all the open findings. If the agent must also add work (the task was in `awaiting_work_review`), the agent puts that work in the feedback of the refine of step 8. If the agent dismisses all the findings in step 7 instead, the task goes to `awaiting_work_review`, and the agent follows the add-work rule instead of going to step 9.
- If the new review has no findings, the task stays in `awaiting_work_review`, and `tasker refine` refuses to run. In that case, if the agent still must make the change, it follows [the add-work rule](run-one-ticket.md#the-add-work-rule). Otherwise, the agent goes to step 9.
- If the task was in `reviewed`, the review before `tasker update-branch` and the review after it count as one loop of "Review findings".
- If the task is in `awaiting_plan_review` (a refine of step 4), `tasker update-branch` keeps the task in `awaiting_plan_review`. Then the agent runs the refine of step 4.
- If `tasker update-branch` reports a rebase conflict, the agent follows [docs/dev/rebase-conflicts.md](rebase-conflicts.md). The agent does not copy that procedure.
- Before the orchestrator sends added work or an answer to an agent, the orchestrator reads the state of the task with `tasker show <issue>`. The orchestrator runs this command itself. It does not send a message to the agent only to learn the state, because a message to an agent that has ended starts the agent again (see "Terms" in "Quota"). The message with the work or the answer names the state that the orchestrator found. The state can change while a message waits, and the next command then depends on the new state.
- When the orchestrator edits an issue body, or posts a comment that starts with `## Change of scope`, while the agent of that ticket runs, the orchestrator sends all the changes together, before the next refine of the agent. On #117, edits that arrived one by one cost extra refines.
- This bullet covers a change to an issue in flight by an orchestrator. The orchestrator that wants the change does not edit the body. The orchestrator of the task is the orchestrator of the milestone of the issue. Before it changes an issue, the orchestrator that wants the change first runs `tasker status` and looks for the full issue key in the output. The orchestrator that wants the change counts the issue as in flight when the output lists a task for it. If the output lists no task for the issue, the orchestrator that wants the change does not follow this bullet. If `tasker status` fails, the orchestrator that wants the change posts no comment, files no issue, leaves the body as it is and tells the user the command and the error. If the issue is in flight, the orchestrator that wants the change chooses by the kind of change: it puts a correction of what the ticket builds in a comment on the issue, and a new requirement in a new issue. For a correction, the orchestrator that wants the change first asks its user, as [the stop rule](plan-review.md#the-stop-rule) says. Then the orchestrator that wants the change posts a comment that starts with `## Change of scope`, as [the stop rule](plan-review.md#the-stop-rule) says. Then the orchestrator that wants the change reads the milestone of the issue with `gh issue view <number> --json milestone -q '.milestone.title'`. If `gh issue view` fails, the orchestrator that wants the change leaves the comment on the issue and the body as it is, and it tells the user the command and the error. If the command prints an empty line (the issue has no milestone), the orchestrator that wants the change leaves the comment on the issue and the body as it is, and it tells the user. If the issue is of the own milestone of the orchestrator that wants the change, that orchestrator is the orchestrator of the task. In that case, the orchestrator of the task sends no message. If the issue is of another milestone, the orchestrator that wants the change sends the orchestrator of the task one message with `SendMessage` that gives the link of the comment. The orchestrator that wants the change sends the message to the session name of the form `orchestrator-<milestone>` of [the notice rule](doc-reads.md#the-notice-rule). The orchestrator that wants the change counts a missing session with the name of the milestone as a failed message. If `SendMessage` fails, the orchestrator that wants the change leaves the comment on the issue and the body as it is, and it tells the user. Before the orchestrator of the task sends the link of the comment, the orchestrator of the task reads the state of the task with `tasker show <issue>`, as the bullet "Before the orchestrator sends added work or an answer to an agent" of [Land the work](#land-the-work) says. If `tasker show <issue>` fails, the orchestrator of the task sends no link to its agent. The orchestrator of the task tells the user the command and the error. The comment stays on the issue. If the task is in `accepted` or a later state (`merging`, `landed`, `finishing`, `cleanup_failed` or `finished`), the orchestrator of the task sends no link to its agent. The orchestrator of the task tells the user and the orchestrator that wants the change that no step takes the correction. If the issue is of the own milestone of the orchestrator that wants the change, the two orchestrators are one session, and the orchestrator of the task tells only the user. If the two orchestrators are not one session, the orchestrator of the task tells the orchestrator that wants the change with `SendMessage`, to the session of the orchestrator that wants the change. If `SendMessage` fails, the orchestrator of the task tells the user. The comment stays on the issue, and the body stays as it is. The user decides the next step, for example a new issue after the landing. Otherwise, the orchestrator of the task sends the link of the comment to its agent before the next refine of the agent, as the bullet before this one says. The agent of the task then does the issue check again for the claims and the requirements of the comment, as [the issue check](plan-review.md#the-issue-check) says. The agent of the task copies the full text of the comment into the feedback text of the step that fits the state of the task (the refine of step 4 or step 8, or the add-work rule), as [the stop rule](plan-review.md#the-stop-rule) and the security report of [Review findings](#review-findings) say. The orchestrator of the task makes no decision about an edit. For a new requirement, the orchestrator that wants the change files a new issue with the steps of [Before a post](issues.md#before-a-post) of issues.md, in the milestone that [The milestone of an issue](planning.md#the-milestone-of-an-issue) of planning.md gives. The orchestrator that wants the change sends no message for a new requirement. On 2026-10-15, orchestrator-m8 edited one bullet of the body of #194 (Docs) while the task of #194 was in review loop 1, and orchestrator-docs learned of the edit only from a later message.
- When the final report of the agent of a ticket says that the ticket landed, the orchestrator of the ticket does these steps in this order. The final report says this when the agent ran `tasker finish`, which closes the issue. First, the orchestrator deletes the jobs of the ticket, as [Delete the job](#delete-the-job) says. Then the orchestrator does [the re-read rule](doc-reads.md#the-re-read-rule). Then the orchestrator does the memory step. Then the orchestrator does [the notice rule](doc-reads.md#the-notice-rule). Last, the orchestrator reads the board for the next ticket, as [Pick the tickets](pick-the-tickets.md#pick-the-tickets) says. In the memory step, the orchestrator searches its memory files for the number of the issue. If the search finds no file with the number, the memory step is complete. In each file that names the issue, the orchestrator deletes the lines that the landed docs now hold. The orchestrator reads the landed docs in its local clone, after the re-read rule. If no line is left besides the frontmatter and the links, the orchestrator deletes the file and its line in the index of the memory. If a search, an edit or a delete of a memory file fails, the orchestrator tells the user the step and the error. The memory file then stays as it was, and the orchestrator continues with the next step of the order. The orchestrator does these steps for each ticket, also for a ticket of the milestone "Docs". The user decided the memory step on 2026-10-17 and the order on 2026-10-18.

### The overlap rule

Several orchestrators can run at the same time, for example one for each milestone. Before a ticket starts, and each time an agent sends the list of files after `tasker approve`, the orchestrator compares the files with each task in flight of every milestone, not only of its own milestone. Before the start, the files are the files that the issue names. `tasker status` lists the tasks in flight, and `tasker show-plan <issue>` gives the files of each plan. `gh issue view <number> --json milestone` gives the milestone of a task.

For a shared file, the overlap rule sets a landing order. A ticket of an earlier milestone lands first. A ticket of the same milestone or of no milestone follows the bullets of [Land the work](#land-the-work). For a ticket of the milestone "Docs" and a ticket of a numbered milestone, [the Docs rule](#the-docs-rule) applies instead. Each orchestrator tells its own agent the landing order, also when its ticket lands first. For a stacked ticket and its parent, [the stacked-ticket rule](pick-the-tickets.md#the-stacked-ticket-rule) wins over the sentence "A ticket of an earlier milestone lands first".

### The Docs rule

This rule covers only a shared file between a ticket of the milestone "Docs" and a ticket of a numbered milestone. The orchestrator of each ticket still does the compare of the overlap rule. For these two tickets, the orchestrator of each ticket sets no landing order for the shared file. The orchestrator of each ticket sends no landing order to the other orchestrator. When the orchestrator of a ticket finds such a shared file, it tells its own agent that the Docs rule covers that file and that the fourth case of [the stop rule](plan-review.md#the-stop-rule) does not apply to that file. If the agent already stopped under the fourth case for that file, this message is the answer, and the agent continues with step 4 of [Run one ticket](run-one-ticket.md#run-one-ticket). For these two tickets, the Docs rule wins over the second sentence of the bullet "If the edit of a shared file is not required". The first sentence of that bullet still applies. Each ticket lands when it is ready. If the other ticket lands first, the agent of the ticket that lands second runs `tasker update-branch` as [the diff read](run-one-ticket.md#the-diff-read) says. For these two tickets, these rules do not apply: the bullet "When the orchestrator sets the landing order", the wait rules, the bullet "When the issue of the earlier ticket is closed", the early update of [Review findings](#review-findings) and, for the shared file, the fourth case of [the stop rule](plan-review.md#the-stop-rule). The wait rules are the bullets of [Land the work](#land-the-work) from "The later agent does the steps of ..." to "If the orchestrator changes the landing order", [the hold rule](#the-hold-rule) and [the stuck-task rule](#the-stuck-task-rule). These bullets include the start-state bullet ("The start state is ..."), the bullet "To wait" and the bullet "Only the user changes a landing order of the overlap rule". The user decided this rule on 2026-10-15. For a stacked ticket and its parent, [the stacked-ticket rule](pick-the-tickets.md#the-stacked-ticket-rule) wins over this rule.

### The hold rule

This rule covers a landing order of the overlap rule when the start state is before `awaiting_work_review`, for example `awaiting_plan_review` or `executing`. The later orchestrator is the orchestrator of the later ticket. The later orchestrator tells the later agent not to start the wait of the "To wait" bullet. The later agent stops before `tasker accept`, reports to the later orchestrator and waits, as [the answer-wait rule](#the-answer-wait-rule) says. The later task stays in `awaiting_work_review`. When the hold starts, the later orchestrator sends one message with `SendMessage` to the orchestrator of the earlier ticket. The message asks for a report when the earlier task reaches `awaiting_work_review` or a later state, and when the issue of the earlier ticket closes. The orchestrator of the earlier ticket sends each of these reports to the later orchestrator with `SendMessage`. If a message of this rule fails, the orchestrator that sends it tells the user, as [the notice rule](doc-reads.md#the-notice-rule) says for a failed message. The later orchestrator reads the state of the earlier task again with `tasker show <issue>` when the orchestrator of the earlier ticket or the user reports a change. It also reads it each time it reads the board after a landing ([Pick the tickets](pick-the-tickets.md#pick-the-tickets)). When the earlier task is in `awaiting_work_review` or a later state, the later orchestrator tells the later agent to start the wait. The earlier task can go back to a state before `awaiting_work_review` while the later agent waits. Then the later orchestrator tells the later agent to stop waiting. Then the hold rule applies again, and the later task stays in `awaiting_work_review`. On 2026-10-15, #123 went from `reviewed` to `refining` while #168 waited. If the earlier task is in `failed`, `quota_blocked` or `interrupted` when the hold starts or during the hold, the later orchestrator tells the user. The hold stays until the user decides. When the issue of the earlier ticket is closed, the later orchestrator tells the later agent to continue as the bullet "When the issue of the earlier ticket is closed" says. On #129, a wait of 60 minutes ran out while the earlier task #95 stayed in `awaiting_plan_review`.

### The stuck-task rule

This rule covers a landing order of the overlap rule, after the later agent reports that it stopped waiting. The orchestrator reads the state of the earlier task again with `tasker show <issue>`. If the state is the same as the start state, the orchestrator asks the user. If the start state is unknown, or if `tasker show <issue>` fails, the orchestrator also asks the user. The user can swap the landing order, postpone the earlier ticket, or tell the later agent to wait again. The orchestrator does not tell the later agent to wait again without the user. If the state changed, the orchestrator can tell the later agent to wait again, and it tells the user. If the new state is before `awaiting_work_review`, the hold rule applies instead of a new wait. The stuck-task rule does not cover a later agent under the hold rule, because that agent started no wait and has no 60-minute limit. On #101, the later agent waited two hours, in two waits of 60 minutes, for #34 of another milestone. During that time, #34 stayed in `awaiting_plan_review`.

## A failed CI run

This section gives the steps of the orchestrator after an agent reports a failed run in step 11 of [the CI wait](#the-ci-wait). The orchestrator does all the steps for each failed run that an agent reports. The repo has three priority labels: `priority: high`, `priority: medium` and `priority: low`. An issue of a failed CI run gets `priority: high`. The priority rule of [Pick the tickets](pick-the-tickets.md#pick-the-tickets) makes that issue start before the tickets with a lower priority.

1. File a new issue: `gh issue create --title "<title>" --body-file <file> --label "priority: high" --milestone "<milestone in progress>"`. The milestone in progress is the current milestone of ["Pick the tickets"](pick-the-tickets.md#pick-the-tickets). The body gives the run URL, the failed tests, the verdict and the evidence of the agent (the result of the rerun and of the local run). The body asks for the cause and a fix. It must not ask only for a retry or a longer timeout. If `gh issue create` fails, no issue exists. Tell the user. The agent keeps waiting, and the task stays in `landed`.
2. If the verdict is broken, the new issue blocks all further work. List the open issues: `gh issue list --state open --limit 1000 --json number,milestone`. An issue has not started when `tasker status` lists no task for it. Leave out the new issue itself. For each issue that has not started, in every milestone, run `gh issue edit <number> --add-blocked-by <new issue>`. Tell the user at once. If an edit fails, the issues already edited keep the link, and the rest have no link. Tell the user the numbers of the issues without a link.
3. If the verdict is flaky, the new issue blocks nothing.
4. Send the agent the number of the new issue. The bullet of "Land the work" that reads the state with `tasker show <issue>` first applies to this message.

The broken-test rule: a broken-test issue is the new issue of step 1 when the verdict is broken. The rule has two actors: the orchestrator that files the broken-test issue, and each other orchestrator. The notice rule defines the other orchestrators (see [the notice rule](doc-reads.md#the-notice-rule)).

After step 2, the orchestrator that filed the broken-test issue sends a broken-test notice to each other orchestrator. It sends a notice for the verdict broken only. The notice gives the number of the broken-test issue. The orchestrator lists the other orchestrators with step 3 of the notice rule and sends the notice with `SendMessage`, as step 4 of the notice rule says. If the session list or a message fails, the orchestrator tells the user, as [the notice rule](doc-reads.md#the-notice-rule) says for a failed message. When another orchestrator gets a broken-test notice, it keeps the number of the issue and follows the ban.

The ban: an orchestrator that knows of an open broken-test issue starts no ticket, except the broken-test issue itself. The orchestrator knows of the issue because it filed the issue or because it got the notice. Before each start, the orchestrator reads the state of the issue with `gh issue view <number> --json state -q .state`. The command prints `OPEN` for an open issue and `CLOSED` for a closed issue. When the output is `CLOSED`, the ban ends. If the command fails, the orchestrator starts no ticket and tells the user the command and the error.

The ban covers only the start of a ticket. A task in flight is not a start, so the ban does not stop it. The rule gives no steps for two broken-test issues open at the same time. A second failed run most likely has the same cause, and the open broken-test issue covers the fix.

## Quota

The quota belongs to the whole account. If a task stops in `quota_blocked`, the orchestrator and all the agents also have no tokens. No session can act until the quota resets. For this reason, the orchestrator must plan the resume before the quota runs out. The orchestrator does this with up to two cron jobs for each agent: a five-hour job and a seven-day job.

### Terms

- The reset time is the time when the quota of the account becomes available again. The quota resets at the exact reset time.
- A cron job (a job, on this page) is a prompt that the orchestrator schedules for a time. A one-shot job fires one time and then deletes itself. A job fires only while the orchestrator is idle. A job lives only in the session of the orchestrator.
- The five-hour job is the job for the five-hour reset time. The seven-day job is the job for the seven-day reset time. On this page, "an agent has a job", "has no job" and "an agent without a job" mean the five-hour job. A seven-day job alone does not count.
- An agent is running while it works on its turn. An agent has ended when its turn is over, for example after a tasker command stops in `quota_blocked` or `interrupted`. A message to an agent that has ended starts the agent again, and the agent keeps its context.
- `tasker show-quota` prints the last quota event of each repo as a JSON list. It has no `--json` flag. Each entry has `repo`, `provider`, `receivedAt` and `event`. `event` is the raw `rate_limit_event` of the assistant. For example:

  ```json
  [{"repo":"codeguru42/tasker","provider":"claude-code","receivedAt":"2026-10-12T00:23:23.713Z",
    "event":{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","rateLimitType":"five_hour","resetsAt":1791778800,
      "unifiedWindows":{"five_hour":{"utilization":0.39,"resetsAt":1791778800},"seven_day":{"utilization":0.39,"resetsAt":1792206000}}}}}]
  ```

- To read the reset time, the orchestrator takes the entry with the latest `receivedAt`, because all repos share the quota of the account. Then it reads `event.rate_limit_info.unifiedWindows.five_hour.resetsAt`. The value is in Unix seconds. The orchestrator converts it with `date -d @<seconds>`. For example:

  ```bash
  tasker show-quota | jq -r 'max_by(.receivedAt).event.rate_limit_info.unifiedWindows.five_hour.resetsAt'
  ```

- The orchestrator reads the seven-day reset time from the same entry, at `event.rate_limit_info.unifiedWindows.seven_day.resetsAt`. The value is in Unix seconds. For example:

  ```bash
  tasker show-quota | jq -r 'max_by(.receivedAt).event.rate_limit_info.unifiedWindows.seven_day.resetsAt'
  ```

- The event is the last one that tasker saw, so its reset time can be in the past. A reset time in the past, or no entry, means "no reset time yet". A seven-day reset time in the past, or no entry, means "no seven-day reset time yet".
- The assistant sends a quota event early in each run, also when the usage is low. As a result, a reset time is known soon after a run starts.
- If a task is in `quota_blocked`, `tasker show <issue>` prints the reset time of that stop in a line `resets at: <ISO time>`.

### The delay of each agent

Each running agent has a slot and a delay. The delay is the number of minutes between a reset time and the job of the agent for that reset. The delays prevent a resume of all the agents at the same time.

- There are 3 slots, one for each agent that can run at the same time. Slot 1 has a delay of 0 minutes. Slot 2 has a delay of 1 minute. Slot 3 has a delay of 2 minutes.
- If the reset time falls on :00 or :30, the delay of each slot is 1 minute longer: 1, 2 and 3 minutes. The cron scheduler can fire a one-shot job on :00 or :30 up to 90 seconds early. That fire is before the reset, so it has no tokens, and the job is then gone.
- The job time of a job is its reset time plus the delay of the agent. The reset time falls on a full 10 minutes, for example 11:30. So the job time is a full minute.
- If the reset time is not a full minute, the orchestrator must round the job time up to the next full minute.
- When the orchestrator starts an agent, the orchestrator must give the agent the free slot with the lowest number.
- When the orchestrator schedules a job for an agent, a five-hour job or a seven-day job, the agent keeps the same slot.
- The agent keeps its slot until the orchestrator frees it, as "Delete the job" says. Then the next agent that starts takes the slot.

### Schedule a job when an agent starts

1. When the orchestrator starts an agent, the orchestrator must run `tasker show-quota` and read the reset time, as "Terms" says. The orchestrator also applies [the seven-day rule](#the-seven-day-rule).
2. If there is a reset time, the orchestrator must schedule a one-shot five-hour job for the job time of that agent. The orchestrator also follows the schedule-all rule in "When there is no reset time yet".
3. If there is no reset time yet, the orchestrator starts the agent without a job and tells the agent that it has no job. For example, there is no reset time before the first run in the project. "When there is no reset time yet" gives the next steps.

- When the orchestrator schedules a job, the prompt of the job must name the issue and the agent. The prompt must tell the orchestrator to do the steps of "When the job fires".
- The orchestrator must keep the id of each job of a ticket. A ticket has at most one five-hour job and one seven-day job.
- For a seven-day job, the orchestrator must keep the seven-day reset time of the job with its id.
- Each id, and the time stored with it, lives until its one-shot job fires or until CronDelete deletes it. A one-shot job deletes itself when it fires. After that, the ticket has no job of that kind.
- A job that has not fired is a job whose id still lives.

### The seven-day rule

Each time the orchestrator runs `tasker show-quota` and reads the reset time, as "Terms" says, the orchestrator also reads the seven-day reset time and applies this rule. This holds whether or not a five-hour reset time exists.

- If the seven-day reset time is in the future, the orchestrator schedules a seven-day job for each agent that has none, except an agent that the schedule-all rule leaves out (see [When there is no reset time yet](#when-there-is-no-reset-time-yet)), however far away the reset is. The job is a one-shot job for the job time of the seven-day reset. The delay and the rounding come from [The delay of each agent](#the-delay-of-each-agent).
- The reason: after the seven-day quota runs out, no session has tokens for a later read. As a result, the orchestrator schedules the job at the first read that gives the time.
- The prompt of the job names the issue, the agent and the window `seven_day`. The prompt tells the orchestrator to do the steps of "When the job fires".
- If the ticket has a seven-day job that has not fired, and the seven-day reset time did not change, the orchestrator schedules no second one. To compare, the orchestrator uses the seven-day reset time that it stored with the job id.
- If the seven-day reset time changed, the orchestrator deletes the old seven-day job with CronDelete. Then the orchestrator schedules the new one.

The rule has three failure cases:

- If `tasker show-quota` fails, or the `jq` read of `seven_day` gives `null`, there is no seven-day reset time yet. No seven-day job changes. If `tasker show-quota` itself fails, the orchestrator tells the user the command and the error.
- If CronCreate of a seven-day job fails, the orchestrator tells the user the tool and the error. The agent has no seven-day job. The next read tries again, because the rule schedules a seven-day job for each agent that has none.
- If CronDelete of the old seven-day job fails, the orchestrator tells the user the tool and the error. The old job and its id stay. The orchestrator does not schedule the new job at that read. The next read tries again, because the time still differs.

### When there is no reset time yet

- Each agent must tell the orchestrator each time a tasker run ends. If an agent has no job, the agent must also tell the orchestrator each time a tasker run starts. The runs are `tasker plan`, `tasker refine`, `tasker execute`, `tasker review` and `tasker resume`.
- If the orchestrator gets a run-start report and the ticket already has a job that has not fired, the orchestrator does not schedule another job.
- While any agent has no job and the schedule-all rule does not leave it out, the orchestrator runs `tasker show-quota` and reads the reset time each time an agent without a job reports that a tasker run starts. The orchestrator also does this each time any agent reports that a tasker run ends. If there is no reset time, nothing else changes.
- The schedule-all rule: each time the orchestrator runs `tasker show-quota` and reads a reset time, as "Terms" says, the orchestrator also schedules a job for each agent without a job. The rule leaves out an agent whose last job fired in a case of "When the job fires" that scheduled no new job for that agent. The orchestrator schedules no job for a left-out agent under the schedule-all rule or under the seven-day rule. A fire of either job, in a case that schedules no new job, leaves the agent out. If a case of "When the job fires" says that the orchestrator schedules the next job, the agent of the fired job is no longer left out. This applies from the start of the paragraph after the list. As a result, that paragraph schedules the next five-hour job, and the seven-day rule covers the agent at the read of that paragraph. The agent stays left out until the orchestrator starts it as "Schedule a job when an agent starts" says, or until the end condition above. A message to the agent does not end this.
- When the orchestrator schedules the job of an agent that had no job, the orchestrator tells the agent that it has a job. If the agent gets this message, the agent stops the run-start reports. The agent keeps the run-end reports.
- If the orchestrator must tell an agent that it has a job or that it has no job, and the agent is running, the orchestrator tells the agent at once. If the agent has ended, the orchestrator does not send a message only for this. The orchestrator puts this information in the next message that it sends to that agent, for example the resume message.
- If the quota runs out before the orchestrator schedules a job, no job resumes the agent. In that case, the orchestrator tells the user when the orchestrator has tokens again.

### When the job fires

When a seven-day job fires, the orchestrator first runs CronList. The orchestrator deletes with CronDelete each job of the ticket whose time is in the past. After the delete, the ticket has no job of that kind, as [Schedule a job when an agent starts](#schedule-a-job-when-an-agent-starts) says for a deleted id. Then the orchestrator does the steps of this section one time. The reason is that the time of such a job can fall inside a stop of the seven-day window. No session has tokens then, so the job does not fire. Such a job can fire late, next to the seven-day job, and send a second resume message. If CronList or CronDelete fails, the orchestrator tells the user the tool and the error. Then it does the steps of this section.

When a job of a ticket fires, a five-hour job or a seven-day job, the orchestrator runs `tasker status --issue <issue>` and `tasker show <issue>`. Apart from the CronList step of the paragraph above, the steps are the same for both jobs. Then exactly one of these cases applies:

- If the task is in `quota_blocked` and the `resets at:` line is missing or in the past, the orchestrator sends the agent a resume message with SendMessage. Then the orchestrator schedules the next job, as the paragraph after this list says. The task stays in `quota_blocked` until the agent runs `tasker resume`.
- If the task is in `quota_blocked` and its `resets at:` time is in the future, the stop is in a longer window, for example `seven_day`. The orchestrator does not resume the agent. The orchestrator tells the user. The job of this case is the seven-day job for the job time of that `resets at:` time, and the orchestrator schedules it one time. For a seven-day job of the ticket that has not fired, [the seven-day rule](#the-seven-day-rule) applies: the same time means no new job, and another time means delete and replace. The seven-day job of the ticket for that `resets at:` time counts as the job that this case schedules, also when the orchestrator keeps an existing job. As a result, this case never leaves the agent out of the schedule-all rule. The task stays in `quota_blocked`.
- If the task is in `interrupted`, the orchestrator sends the agent a resume message, as in the first case. Then the orchestrator schedules the next job, as the paragraph after this list says. The task stays in `interrupted` until the agent runs `tasker resume`.
- If the task is in `awaiting_quota_approval`, the quota use passed the approval threshold. The orchestrator tells the user and does not resume the task. The orchestrator does not run `tasker approve-credits` (see "Limits"). The orchestrator does not schedule another job for that task. The task stays in `awaiting_quota_approval` until the user decides.
- If the task is in `failed` or `landed`, the orchestrator reads the last report of the agent. In `landed`, the agent does [the CI wait](#the-ci-wait). If that report does not say that the agent stopped, the orchestrator schedules the next job, as the paragraph after this list says. The agent keeps its slot. A report of a failed run (step 11 of the CI wait) is not a stop, so the agent keeps its slot also then. If the agent stopped, the orchestrator schedules no new job and tells the user. The orchestrator frees the slot only in a case of "Delete the job".
- If the task is in `finishing`, `cleanup_failed`, `finished` or `cancelled`, or `tasker status --issue <issue>` lists no task, the orchestrator schedules no new job. The orchestrator frees the slot of the agent, as "Delete the job" says. By default, `tasker status` lists only the tasks in flight, so it does not list a `finished` or `cancelled` task.
- If the task is in a state that no other case names, the task did not stop for the quota. For example, the task is in `planning`, `executing`, `awaiting_plan_review` or `reviewed`. The orchestrator schedules the next job, as the paragraph after this list says. The agent keeps its slot.

If a case says that the orchestrator schedules the next job, the orchestrator first applies the resume rule. The resume rule: if the case sent no resume message, the agent has ended (see "Terms"), and the agent does not wait for an answer or a next step from the orchestrator, the orchestrator sends the agent a resume message, as in the first case. The agent waits for the orchestrator after a stop, a question or a request for the next step, until the orchestrator sends the answer or the next step. The reason: the quota can end the session of the agent between two `tasker` commands, and then no other case resumes the agent. Then the orchestrator runs `tasker show-quota` and reads the reset time, as "Terms" says. The orchestrator also applies [the seven-day rule](#the-seven-day-rule). If there is a reset time, the orchestrator schedules the next five-hour job for the job time of that agent, but only if the ticket has no five-hour job that has not fired. The orchestrator also follows the schedule-all rule in "When there is no reset time yet". If there is no reset time yet, the orchestrator tells the agent that it has no job. Then "When there is no reset time yet" applies to that agent.

### What the agent does

- If a tasker command of the agent stops in `quota_blocked` or `interrupted`, the agent ends its turn. The agent does not wait, sleep or schedule anything. The task stays in that state. This end of the turn is a wait point of [the answer-wait rule](#the-answer-wait-rule).
- If the orchestrator tells the agent to resume, the agent runs `tasker status --issue <issue>`.
- If the task is in `quota_blocked` or `interrupted`, the agent runs `tasker resume <issue>`. The task goes back to the state before the run that stopped, and tasker runs the same command again. After that command, the task reaches the state that ["Run one ticket"](run-one-ticket.md#run-one-ticket) gives for its step. Then the agent continues with the next step of "Run one ticket".
- If the task is in `awaiting_quota_approval`, the agent does not run `tasker resume` or `tasker approve-credits`. The agent reports to the orchestrator. Then the agent waits as [the answer-wait rule](#the-answer-wait-rule) says.
- If the task is in a different state, the agent does not run `tasker resume`. The agent continues from that state.

### Delete the job

- When the agent reports that it ran `tasker finish`, for example in its final report, the orchestrator must delete each job of that ticket whose id still lives with CronDelete. A task in `landed` keeps its jobs and its slot until then, unless another bullet of this section applies, for example after a stop in the CI wait. A report of a failed run is not a stop, so the jobs stay until `tasker finish`.
- When the orchestrator cancels an agent, the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- If an agent stops for another reason and the orchestrator does not start it again, the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- When the user defers a ticket that has a task in flight (see [the defer rule](pick-the-tickets.md#the-defer-rule)), the orchestrator must delete each job of that agent whose id still lives with CronDelete.
- In each of these cases, the orchestrator frees the slot of the agent. This also applies when the agent has no job. The schedule-all rule also leaves out this agent until the orchestrator starts it again, as "Schedule a job when an agent starts" says.
- If CronDelete fails, the orchestrator tells the user the tool and the error. The job stays. When the job fires, the case of "When the job fires" for its state applies. An example is the case of a finished task, which schedules nothing.

### Do not use these

- The orchestrator must not use `/loop` or ScheduleWakeup for the wait. One wake-up waits at most one hour. A wake-up before the reset has no tokens to act.
- An agent cannot make a job, because the agent does not have the tool for that. Only the orchestrator schedules jobs.

## The handoff

A long-running orchestrator is the orchestrator of a milestone that stays open while other sessions add issues to it, for example "Docs" (see [docs/dev/planning.md](planning.md)). In a handoff, the old orchestrator gives its work to a new orchestrator in a new session.

The rules of this section cover only a long-running orchestrator. An orchestrator of a numbered milestone stops when the Todo column of its milestone is empty, as [Pick the tickets](pick-the-tickets.md#pick-the-tickets) says. The rules of this section do not cover it.

Only the user starts a handoff. The user can ask the old orchestrator for a handoff at any time. The reason: the old orchestrator has no tool that shows its context use. On 2026-10-16, the Docs orchestrator guessed that about 20% of its context was used and started a handoff. The session used 6%.

The old orchestrator can suggest a handoff to the user. The suggestion does not start the handoff. The handoff starts only when the user agrees to the suggestion or asks for a handoff. In an answer to [a question of the user](working-with-the-user.md#a-question-of-the-user), the old orchestrator suggests a handoff only when the suggestion is relevant to that question.

After the start, the old orchestrator does these steps:

1. Start no new ticket.
2. Wait until each task in flight lands. For each landing, do the usual steps: delete the jobs (see [Delete the job](#delete-the-job)), do [the re-read rule](doc-reads.md#the-re-read-rule), do the memory step of the bullet "When the final report of the agent of a ticket says that the ticket landed" of [Land the work](#land-the-work) and do [the notice rule](doc-reads.md#the-notice-rule). The reason: a job lives only in the session of the orchestrator (see [Terms](#terms)). If a task is still in flight at the handoff, nobody resumes it after a quota stop.
3. Run the review rounds of the last bullet of [Pick the tickets](pick-the-tickets.md#pick-the-tickets), until a round finds nothing new. The user asked for this rule on 2026-10-17. Then write the handoff file `$HOME/Documents/tasker/handoff/<date>-<role>.md`, for example `2026-10-15-docs-orchestrator.md`. If a file with that name exists, add a number, for example `2026-10-15-docs-orchestrator-2.md`.
4. Give the path of the file in the reply to the user.

Only the user ends a handoff that started. The handoff ends when the user clears the old session and starts the new session with the prompt of the handoff file. Until then, the old orchestrator starts no new ticket, also after step 4. On 2026-10-17, the Docs orchestrator saw that its handoff started too early. It then started a new ticket without the word of the user.

The old orchestrator puts these items in the handoff file:

- The prompt for the new session, in a code block. The prompt names the milestone, the session name and the first step: the start of the re-read rule. The prompt also names the docs to read and the state at the handoff. Its last step is to watch the board for new issues.
- The state at the handoff: the tasks in flight of other milestones that share a file with an open issue of the milestone, the parked tasks and the other sessions.
- What the old orchestrator did, and each decision of the user from its session.
- A table of the open issues of the milestone, with the columns issue, topic, blockers and files.
- Each finding of the review rounds, with its state, handled or open.

The old orchestrator puts no rule in the handoff file. The rules stay in the docs, and the prompt points to them.

The user pastes the prompt as the first message of the new session. The user names the session `orchestrator-<milestone>`, for example `orchestrator-docs`, as [the notice rule](doc-reads.md#the-notice-rule) says. The new orchestrator then starts with the re-read rule. Right after the first doc read, the new orchestrator does the check of the handoff folder that follows.

The new orchestrator does this check before any other step of the prompt. It lists the folder `$HOME/Documents/tasker/handoff/` with `ls`.

The files of its role are the files whose names step 3 gives for that role. The new orchestrator orders them as step 3 says. A file with a later date is newer. A file with no number is the first file of its date. For two files of the same date, the file with the higher number is newer.

The file of the first message is the handoff file whose path the first message names.

The new orchestrator then does the case of this list that applies:

- If the file of the first message is the newest file of the role, the new orchestrator works from that file.
- If the newest file of the role is newer than the file of the first message, the new orchestrator tells the user. Then it works from the newest file.
- If the list holds no file of the role, no newer file exists. The new orchestrator works from its first message.
- If the list holds a file of the role and the first message names no path of a file of the role, the new orchestrator tells the user the newest file of its role. Then it works from that file.
- If the list fails, for example because the folder is missing, the new orchestrator tells the user the command and the error. Then it works from the file of its first message. If the first message names no path of a file of the role, the new orchestrator works from its first message.

The reason: on 2026-10-16, the new Docs orchestrator got the handoff file of 01:12 in its first message. A newer handoff file of 09:09 for the same role existed. Most issues of the table of the old file had closed.

## Limits

These limits apply to the orchestrator and to the agents, except where a bullet or a rule names one actor.

- The agent reads the output of a task with the `tasker show` commands, for example `tasker show`, `tasker show-plan`, `tasker show-verify` and `tasker show-review`. [The own-worktree rule](#the-own-worktree-rule) gives the rule for a direct read of a file of the data folder of tasker, for example a transcript or a log file.
- To read the commits of a task branch, the agent runs `git fetch tasker` in the local clone of the orchestrator. If the clone has no `tasker` remote, the agent adds it as [the own-worktree rule](#the-own-worktree-rule) says. Then the agent runs `git log` or `git show` on `tasker/<task branch>`. For a diff of the task, the agent uses the command with three dots of [the diff read](run-one-ticket.md#the-diff-read). If a command fails, the agent stops and reports the error to the orchestrator. Nothing changes. The agent waits as [the answer-wait rule](#the-answer-wait-rule) says.
- A new worktree has no `node_modules`, and the local clone can have none. The task worktree lives long, and an update can change `package-lock.json`. Before a test on the local machine that runs the code of the repo, the agent runs `npm ci` in the task worktree when it has no `node_modules`. The agent also runs `npm ci` when `package-lock.json` differs from the copy of the last install. Use the copy of the commit check: `L=$(git rev-parse --git-path npm-ci-lock); cmp -s "$L" package-lock.json || { npm ci && cp package-lock.json "$L"; }`.
- The agent uses only the issue, the files of the repo, its own tests on the local machine and the answers of the orchestrator as sources. If the issue does not give a detail that the work needs, the agent asks the orchestrator. Then the agent waits for the answer, as [the answer-wait rule](#the-answer-wait-rule) says. Before `tasker approve`, [the stop rule](plan-review.md#the-stop-rule) and [the design-gap rule](plan-review.md#the-design-gap-rule) give the steps and say who answers. After `tasker approve`, the orchestrator asks the user. When the agent asks the orchestrator a question, the agent gives the options, with its suggestion for each.
- The agent changes only its own issue. On GitHub issues, labels and the project board, the comment of step 11 of ["Run one ticket"](run-one-ticket.md#run-one-ticket) is the only write of the agent. The agent does not edit an issue body, a label or the project board. This rule does not cover the git commands and the `tasker` commands of the steps on [the orchestration pages](orchestration.md), for example `tasker merge` and the delete of the task branch in step 10. On GitHub Actions, the rerun of step 9 of the CI wait (`gh run rerun <run id> --failed`) is the only write of the agent.
- If tasker stops for a quota, follow "Quota". Never run `tasker approve-credits`.
- Do not run `npm link` or a global install from a task worktree. The global `tasker` runs the tickets, and the install replaces it.
- Only the orchestrator writes memory, so that two agents do not write the same file. Agents report what they learn to the orchestrator in their final report (see [the final report](run-one-ticket.md#the-final-report)). For this reason, an agent does not run a skill that writes memory, for example `/session-review`. The bullet "When the final report of the agent of a ticket says that the ticket landed" of [Land the work](#land-the-work) says when the orchestrator deletes a note.
- The orchestrator and each agent load the simple-english skill and follow the simple-english bullet of [Docs](rules.md#docs) of rules.md.
- The folder of an agent is `$HOME/Documents/tasker/agents/<session name>`. The session name is the name of the session of the agent from ["The prompt of an agent"](pick-the-tickets.md#the-prompt-of-an-agent), for example `codeguru42-tasker-43`. The task worktree of [the own-worktree rule](#the-own-worktree-rule) is `../tasker-worktrees/<session name>`, relative to the root of the local clone of the orchestrator. That path is a folder with the session name in the folder `tasker-worktrees`, next to the local clone of the orchestrator. The task worktree is not in the folder of the agent and not in the clone. The orchestrator makes the folder of the agent before the agent starts, as ["The prompt of an agent"](pick-the-tickets.md#the-prompt-of-an-agent) says. The agent keeps each other file that it writes in the folder of the agent, for example the feedback files and the notes. Two agents that run at the same time keep their files in different folders. Before an agent runs `tasker refine` or `tasker review <issue> "<feedback>"` with feedback text from a file, the agent makes sure that the file holds the text for its own ticket. [The plain-form rule](tasker-commands.md#the-plain-form-rule) gives the form of the command. If two agents use the same file name, the refine or the review of one ticket can send the text of another ticket. The folder of the agent stays after the work. The agent removes only the task worktree, as the own-worktree rule says.
- Do not use `pkill` or `killall`. To stop a process that it started, the orchestrator or the agent uses `kill` with the process id that it saved. `pkill` matches by name, so it can stop a process of another session of the same user.
- Never print a credential, for example an access token, a password or a key. If a command gives a credential, store its output in a shell variable, for example `token="$(gh auth token --hostname github.com --user <account>)"`. Do not print the variable. To make sure that the command succeeded, use its exit code or a test of the variable that prints nothing, for example `[ -n "$token" ]`. Pass the variable to later commands, for example `GH_TOKEN="$token" gh api user`. Do not put the credential itself in a command line, a file, a log, a feedback text or a comment. Never print the environment, for example with `env`, `printenv` or `set`, because it can hold a credential, for example the access token in `GH_TOKEN`. The assistant tools start a new shell for each tool call, and a shell variable lives only in its own shell. As a result, set the variable and use it in the same tool call. Never print the full command line of the sandbox, for example with `ps -o args`. The sandbox of a `claude` run is a `bwrap` process. Its command line holds a user name and a password of the local proxy of that run. On 2026-10-14, an agent printed them in its tool output with `ps`. To find a bind or a path in the command line, search it for only that item, and print only the match. For example, `ps -o args= -p <pid> | grep -o -F -- '<path>'` prints only `<path>`, and only when the command line holds it. This rule does not cover the code of tasker, which already keeps the access token out of its errors and logs.

### The issue-link rule

In each reply to the user, the orchestrator writes each mention of an issue as a markdown link. The link target is the page of the issue in its tracker. The link text is the issue key, in this form:

- For an issue of this repo, the text is the short form `#<N>`, for example `[#159](https://github.com/codeguru42/tasker/issues/159)`.
- For an issue of another repo, the text is the full key, for example `[owner/repo#12](https://github.com/owner/repo/issues/12)`.

The rule covers the replies of the orchestrator to the user only. The text on GitHub keeps the plain key, because GitHub links it. The messages to an agent and to another orchestrator keep the plain key, because a session reads them as text. A key inside a code span or a code block stays as it is, for example a command line with an issue key.

The reason: the user opens the issue by hand. On GitHub, `#159` is a link, but in the terminal it is plain text.

### The own-worktree rule

The orchestrator and the agents must not read the files that tasker keeps in its data folder. Never read, search or run anything in a worktree of tasker, also not with a read-only command such as `grep`. Do not change the repo or the worktrees of tasker by hand. Only `tasker` commands change them. The read has two exceptions. The first exception is a fetch through the read-only `tasker` remote, which reads the clone of tasker and changes nothing there. The second exception is a read that the user permits. A read of a file of the data folder, for example the database `tasker.db`, a log or an archived prompt, is allowed only when the user permits that read. The second exception does not cover a worktree of tasker. Before the read, the orchestrator asks the user, with the fact that it needs and the command that it plans. An agent asks the orchestrator, as the sources bullet of [Limits](#limits) says, and the orchestrator then asks the user. For an agent, the orchestrator does the read and gives the fact to the agent as an answer. Without that permission, the `tasker` commands are the only way to read the state of a task. For an agent, the first bullet of [Limits](#limits) names these commands. The reason: a `tasker` command does not give every fact, for example the time of an event, and a direct read without permission is a read of data that the user owns. On 2026-10-17, an orchestrator read event times from `tasker.db` with `sqlite3 -readonly`, and the user said: "you need to ask permission before accessing any tasker resources". The worktrees of tasker are under `<dataRoot>/repos/<owner>-<repo>/worktrees/`.

To read or run the code of a task, the agent uses its task worktree. The task worktree is the one worktree of an agent for its task. It is a worktree of the local clone of the orchestrator, in the folder that the folder bullet of [Limits](#limits) gives for the task worktree. It is on a local branch with the same name as the task branch. The task branch is on the `branch:` line of `tasker show <issue>`. After each stop of the make or of the branch-exists case, the agent waits as [the answer-wait rule](#the-answer-wait-rule) says.

- Make: the agent makes the task worktree one time, after `tasker start` in step 2 of ["Run one ticket"](run-one-ticket.md#run-one-ticket) or in [the comeback rule](run-one-ticket.md#the-comeback-rule). If the local clone has no `tasker` remote, add it as steps 1 and 2 of [docs/dev/rebase-conflicts.md](rebase-conflicts.md#procedure) say. Then run `git fetch tasker`. If the fetch fails, stop and report. Nothing changes. Then run `git worktree add -b <task branch> <path> tasker/<task branch>`. If it fails for a reason other than the branch-exists case, stop and report. No worktree exists.
- The path: the agent keeps `<path>` from the make until the remove at the end. The agent keeps `<path>` as an absolute path, because git resolves a relative path against the current folder of each command. Each later step uses that path. This includes the `<path>` of steps 6, 18 and 19 of rebase-conflicts.md.
- Use: each step that reads or runs the code of the task uses the task worktree, after the update rule.
- The branch-exists case: the make fails with `fatal: a branch named '<task branch>' already exists` and exit 255. Git makes no folder. The local branch can hold commits that tasker does not hold, for example after a stop of the manual fix. Do these steps before the first update:
  1. Read `<hash>` with `git rev-parse --verify tasker/<task branch>`. Then run `git merge-base --is-ancestor <task branch> <hash>`.
  2. If the exit code is 1, the local branch holds a commit that tasker does not hold, or tasker rewrote the task branch after the last update, for example with a rebase or an autosquash. The step cannot tell the two apart. Stop and report. The branch and each worktree of the branch stay.
  3. If the exit code is neither 0 nor 1, or a command fails, stop and report.
  4. If the exit code is 0, run `git worktree list --porcelain`. If an entry has the line `branch refs/heads/<task branch>`, use the `worktree <path>` line of that entry as the task worktree.
  5. If no entry has that line, run `git worktree add <path> <task branch>`, with no `-b` and no `--detach`. For a branch that no worktree holds, this makes a worktree on the branch.
  6. Then do the update rule.
- The remove: the agent removes the task worktree only at the end of its work. The end is after step 10 of "Run one ticket", after `tasker abort`, or when the orchestrator tells the agent to stop. Run `git worktree remove <path>`. Do not use `--force`. If the remove fails, stop and report, as step 19 of rebase-conflicts.md says. The worktree and the local task branch stay. Then delete the local task branch with `git branch -D <task branch>`. If the delete fails, stop and report. The worktree is gone, and the local task branch stays. The agent reports to the orchestrator, and the orchestrator reports to the user.
- Exceptions to the remove: if the agent followed rebase-conflicts.md, steps 18 to 20 of that page do the remove. The agent does not do it again. While the local-commit rule holds, the worktree and the local branch stay. They also stay after a step of rebase-conflicts.md stops. The final report names each path that stays.
- Worktree commands change no task. The task keeps its state.

### The update rule

tasker changes the task branch in its own clone, for example with `tasker execute`, `tasker refine` and `tasker update-branch`. The task worktree does not follow by itself. Before each use, the agent does these steps in the task worktree:

1. Run `git fetch tasker`.
2. Read `<hash>` with `git rev-parse --verify tasker/<task branch>`. The hash lives only for this update.
3. Run `git rev-parse --git-path rebase-merge`. If the command fails, or the folder that it names exists, stop and report. Nothing changes. For example, the worktree stays in a rebase when `git rebase --abort` fails in step 7 of [the commit check](#the-commit-check).
4. Run `git status --porcelain`. If it prints a line, stop and report. Nothing changes. Test the output, because the command exits with 0 also when it prints lines. Ignored files such as `node_modules/` do not print.
5. Run `git reset --keep <hash>`.

`git reset --keep` moves the branch for a fast-forward. It also moves a branch that a rebase of tasker rewrote, where `git merge --ff-only` fails with exit 128. For a change in a file that the update changes, `--keep` refuses with exit 128 (`error: Entry '<file>' not uptodate. Cannot merge.`), and the branch and the change stay. Step 4 already stops for each uncommitted change. As a result, no update runs over one. Do not use `--hard`, because it deletes changes that are not committed. If a step fails, the step that uses the worktree gives the failure path. The commands of the update rule change no task.

### The local-commit rule

The local task branch holds no commit of its own, with two exceptions. The first is the manual fix, from its step 2 to step 11 of rebase-conflicts.md. The second is rebase-conflicts.md after a rebase conflict of `tasker update-branch`, from step 7 (the rebase) to step 11 (`--take-remote`). In that time, the agent does not run the update rule. If the agent stops in that time, for example after a failed push at step 10, the worktree and the local branch stay. After step 11, tasker holds the local tip (`<taken>`), and the rule ends. The manual fix and rebase-conflicts.md link to this rule.

### The shared-clone rule

Every orchestrator and every agent on the machine run git in one local clone. As a result, a git command of any session, for example `git fetch`, can run between two commands of a step. On 2026-10-15, `git worktree list` in the local clone listed the worktrees of the agents of other orchestrator sessions. A remote-tracking ref is the copy of a branch of a remote in the local clone, for example `origin/<branch>` or `tasker/<branch>`. If a step uses a remote-tracking ref in more than one command, the step reads the full hash of the ref one time, with `git rev-parse --verify <ref>`. Each later command of the step uses that hash, not the ref. For example, if step 10 of ["Run one ticket"](run-one-ticket.md#run-one-ticket) read `origin/<task branch>` for the check and again for the delete, a fetch between the two reads can move the ref, and the delete then acts on a commit that the check did not see. Use `--verify`, because plain `git rev-parse` also prints the name on its output when it fails. If `git rev-parse --verify` fails, for example because the ref does not exist, it exits with 128 and prints `fatal: Needed a single revision`. The step then stops, as the failure cases of that step say. If a step uses a remote-tracking ref in only one command, the step needs no hash read. The update rule reads `tasker/<task branch>` one time and resets to that hash.

### The address rule

The agent sends each message to the orchestrator with `SendMessage` and `to: "main"`. The agent puts `"main"` in the `to` option of `SendMessage`, not in the text of the message. The session name of the orchestrator, for example `orchestrator-m8`, is not the address. The rule covers each message that the agent sends while it works. Examples are the run-start and run-end reports of "When there is no reset time yet" in "Quota", the reports of the stop cases, the list of files after `tasker approve` and the questions. The rule does not cover the final report (see [the final report](run-one-ticket.md#the-final-report)). The agent of #153 learned this rule on 2026-10-15.

### The answer-wait rule

When the agent must wait for an answer or a next step from the orchestrator, the agent sends its report or its question with `SendMessage`, as [the address rule](#the-address-rule) says. Then the agent gives its final answer, which ends its turn. This final answer is an interim report (see [the final report](run-one-ticket.md#the-final-report)). The agent does not wait in a loop. The message of the orchestrator with the answer or the next step starts the agent again. The reason: a message to an agent that has ended starts the agent again, and the agent keeps its context (see "Terms" in "Quota"). On #153, the agent waited about 25 minutes in a loop for an answer, then ended its turn with a stop report. The message with the answer started the agent again, and the agent went on with its work. The rule also covers each stop after which the agent runs no other `tasker` command until the orchestrator tells it the next step. While the agent waits, the task keeps its state. For a resume message during the wait, see the resume rule in "When the job fires". The rule does not cover a wait that reads a state, for example the "To wait" bullet of "Land the work" or the wait bullet of [the command rules](tasker-commands.md#the-command-rules).

A wait point is a place where the agent waits for an answer or a next step from the orchestrator. At each wait point, the orchestrator expects an interim report from the agent. The harness is the tool that runs the agent. The harness can deliver the final answer of the agent to the orchestrator in the same way as the final report. At a wait point, the agent starts its interim report with a line that says that the report is not the final report. That line also names what the agent waits for.

On [the orchestration pages](orchestration.md), the agent waits for the orchestrator at these wait points:

- [The parent-hold rule](pick-the-tickets.md#the-parent-hold-rule): before a command that moves the task out of a ready state, and when the hold message comes during a wait
- Step 2 of [Run one ticket](run-one-ticket.md#run-one-ticket): each stop at `tasker start` and after a failed make of the task worktree
- [The comeback rule](run-one-ticket.md#the-comeback-rule): each stop of the agent
- [The diff read](run-one-ticket.md#the-diff-read): each stop of the agent
- Step 11 of [the CI wait](#the-ci-wait), and each stop of the CI wait
- [The stop rule](plan-review.md#the-stop-rule): each stop case
- [The quote check](plan-review.md#the-quote-check): before `tasker approve` or `tasker accept`
- [The verify-failure rule](#the-verify-failure-rule): each stop of the agent
- [The plain-form rule](tasker-commands.md#the-plain-form-rule) and [the tool-block rule](tasker-commands.md#the-tool-block-rule): a denied tool call
- [The broken-commit steps](#the-broken-commit-steps): the stop at the new base commit, the stop after a failed commit check and each stop of the pushed-branch rule
- [The manual fix](#the-manual-fix): each stop of the agent
- [The commit check](#the-commit-check): each stop
- The security report of [Review findings](#review-findings)
- The no-loop-left rule and the bullet "After the 5th loop" of [Review findings](#review-findings)
- [Land the work](#land-the-work): after the later agent stops waiting
- [docs/dev/rebase-conflicts.md](rebase-conflicts.md): each stop of its procedure, when a step of [the orchestration pages](orchestration.md) sends the agent there
- [The hold rule](#the-hold-rule): before `tasker accept`
- [What the agent does](#what-the-agent-does) in "Quota": the end of the turn after a stop in `quota_blocked` or `interrupted`, and the report for `awaiting_quota_approval`
- A question of the agent, in the sources bullet of [Limits](#limits)
- The read bullet of [Limits](#limits): a failed command
- [The own-worktree rule](#the-own-worktree-rule): each stop of the make and of the branch-exists case
- [The doc-read rule](doc-reads.md#the-doc-read-rule): each stop of an agent

The orchestrator does not treat an interim report as the end of the ticket. For an interim report alone, the orchestrator does not free the slot, delete a quota job or read the board for the ticket. The orchestrator still follows the bullets of [Delete the job](#delete-the-job). The orchestrator still does each read that a rule gives after a report of an agent, for example in [the parent-hold rule](pick-the-tickets.md#the-parent-hold-rule). On #160, #161 and #221, the agents ended their turns at a wait point, and a message of the orchestrator resumed each one.
